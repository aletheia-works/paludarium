# 設計の判断

paludarium を作る中で決めた、大きな判断とその理由です。

## 既存の部品の使い方

外部の crate や道具は、基本的に使ってよいことにしています。ただし、ライセンスが
Apache-2.0 と両立するかを先に確かめます。著作権やライセンスに関わるもの、不具合や
合わないところがあるものは、その部分を自作します。依存は crates.io からだけ取り、
`cargo deny` で確かめています。

ほかのエミュレータのコードは写しません。blink などの動作と設計は参考にしますが、
実装は一から書いています。履歴にマルウェアが見つかった blink の派生（`lanmower/blink`
とその系列）は、参照も依存もしません。

## デコーダは既存の crate を包む

最初は「デコーダも自作する」と決めていましたが、外部の部品の方針を見直したときに、
[iced-x86](https://github.com/icedland/iced)（MIT）を使うことにしました。
`paludarium-decoder` で包み、ほかの crate には自前の命令の型だけを見せています。
合わないところが見つかったら、デコーダの中だけで差し替えたり一部を自作したりできます。

## ソフトウェア MMU

WebAssembly（wasm32）のメモリは 4 GB までなので、ゲストの 64-bit のアドレス空間を
そのまま置けません。そこで、4 KiB のページの 2 段のページテーブルを持つソフトウェア MMU を
すべてのホストで使っています。アクセスはすべて検査し、ページがないときや権限が違うときは
ゲストの例外にします。最後に使ったプライベートなページをキャッシュ（1024 エントリの
ソフトウェア TLB）に覚えておき、次にそのページへアクセスするときは、保護だけを確かめて
ページテーブルを引きません。マッピングやページの項目が変わりうるときは、いつも空にします。

エントリはページのフレームのバイトを持ちますが、セッションのメモリメーター
（`memory.current`）への計上は持ちません。計上を持つのはページテーブルと共有メモリです。
スレッドが TLB を空にするのは次のアクセスのときなので、待っているスレッドは、なくなった
ページのバイトを持っていることがあります。それはもう数えられず、新しいフレームはすぐに
場所を得られます。全体を持つのは、TLB が覚えたときにまだバイトのなかったフレームだけです。
それを共有するほかの空間が、この空間のロックなしにバイトを与えうるからです。

ゲストのスレッドはそれぞれ自分の TLB を持ちます。TLB にあるページへの読み込み・書き込み・
命令の取り出しと、8 バイトの 1 ワードに収まる lock 付きの命令は、ロックを取らずにこれを
使うので、スレッドどうしは互いを待ちません。TLB は、それを埋めたときのエポックが
アドレス空間で変わらないあいだだけ有効です。エポックはマッピングやページの項目が変わりうる
ときに進み、アクセスのたびに比べます。書き込みは、途中のあいだどのエポックの下にいるかを
示し、エポックを進める側は、古いエポックの下の書き込みがなくなるまで待ちます。これで
Linux の TLB シュートダウンと同じく、`mprotect` や `fork` が戻った後に、ほかのスレッドが
古いページへ書き込むことはありません。待つのはふつう各スレッドの書き込み 1 つ分ですが、
ワードにまたがる書き込みは、同じページへのほかの書き込みの後ろで順番を待つので（下記）、
その列の長さだけかかることがあります。

ファイルのプライベートなマッピングのページも TLB に入ります。書き込むまでマッピングが見せる
ファイルのページキャッシュのページと、書き込んで作ったコピーです。これらのファイルは、
どのプロセスからでも `ftruncate` でアドレス空間のロックなしに縮みうるので、TLB を通した
アクセスは、ページがファイルの終わりより完全に後ろにないこと（後ろなら SIGBUS）と、
コピーなら TLB が覚えてからファイルが縮んでいないこと（縮んだなら Linux はコピーを
捨てているかもしれません）も確かめます。そうでなければロックを取り、ロックの側で両方を
扱います。アクセスのたびに両方を自分で確かめるので、切り詰めがどちらを先に変えるかは
関係ありません。どちらの変化も見なかったアクセスは、切り詰めの途中に走っていたものとして
切り詰めより前に来ます。切り詰めで終わりより後ろになったコピーは、次のロックを取った
アクセスで置き換わるので、そこに入った書き込みが見えることはありません。切り詰めが戻った
後に始まるアクセスは、そのページを使いません。ロックを取ったアクセスは、ページの項目を
新しくした後でもう一度ファイルの終わりを確かめます。その 2 つのあいだに切り詰めが入りうる
からです。ページキャッシュは、縮んだ回数を数えるより先に新しいサイズを示し、その後ろを 0 に
します。ページキャッシュのページのコピーは、コピーする前に読んだ回数を記録します。そのため、
新しい回数を記録した項目は新しいサイズが見えた後に作られたことになり、縮む前のバイトを
取ったコピーは古い回数を記録するので、ページが終わりより後ろなら捨てられます。

共有マッピング（`MAP_SHARED` のメモリやファイル、System V の共有メモリ）のページも、それが
見せるメモリと一緒に TLB に入ります。TLB を通した書き込みは、ロックを取ったときと同じことを
します。バイトの前と後にメモリの世代を進め、そのあいだにページを dirty にします。書き戻しは
ページを clean にしてから読むので、その書き込みを渡すか、次の書き戻しのために dirty のまま
残すかのどちらかになります。メモリを共有するほかのプロセスは、もともとこの空間のロックなしに
書き込んでいたので、ここでロックを取らなくても、そちらから見えることは変わりません。ほかの
空間がコードを実行しうる共有マッピングへの書き込みは、これまでどおりその空間のコードの世代を
進めます。

TLB のエントリは、ファイルもメモリの持ち主も持ちません。持つのは、ファイルがそのために
別に置いているサイズと縮んだ回数、それにメモリの世代だけです。ファイルを持つと、
`munmap` の後もそのスレッドが次にアクセスするまでファイルが開いたままになり、System V の
共有メモリは、それを持つものの数で接続数（`shm_nattch`）を数えるからです。

1 ワードに収まる lock 付きの命令は、そのワードの 1 回の compare-and-swap なので、ロックを
取らない書き込みに対しても不可分で、完全なフェンスになります。2 ワードにまたがる split lock
と `CMPXCHG16B` はロックを取り、先にエポックを進めます。これで途中の書き込みを待ち、次の
書き込みをロックへ回します。終わるまでロックなしで動くのは読み込みだけで、両方のワードに
かかる読み込みは、片方のワードだけが先に書かれたところを見ることがあります。ただし、
そろった 16 バイトの読み込みは別です（下記）。

ゲストのスレッドどうしには、x86 と同じ順序（TSO）でメモリが見えます。スレッドの読み書きは
順番のままで、前の書き込みを後の読み込みが追い越すことだけがあります。ページの中身を acquire
で読み、release で書くので、Arm のホストでもロックなしでこの順序が保たれます。実行可能な
ページのうち、命令を取り出したことのあるページへの書き込みは、バイトを書いた後でコードの世代を
進めます。新しい世代が見えれば、新しいコードも見えます。ページから初めて取り出すときは、
ロックを取り、エポックを進めてから印を付けるので、TLB を通した書き込みは印を読むだけで
済みます。書き込みが印を見るか、取り出しがそのバイトを見るかのどちらかになります。

x86-64 の CPU は、そろった 16 バイトの読み込み（`MOVDQA` など）を 1 回のアクセスで
行うので、ほかのスレッドの `CMPXCHG16B` や 16 バイトの書き込みは、まるごと見えます。
エミュレータはページの中身を 8 バイトのワードで持ち、読み込みはロックを取らないので、
ページごとに、2 ワード以上にまたがる書き込みの始まった数と終わった数を数えています。
そのような書き込みが 2 ワードの間に入ったかもしれないときは、読み込みは 2 ワードを
読み直します。ほかの読み込みと書き込みには、この手間はかかりません。書き込みはロックを
取らないので、この数でページへのそのような書き込みを順番に 1 つずつ行います。2 つの
16 バイトの書き込みが、片方の下のワードともう片方の上のワードを残すことはありません。

## 待機の仕組みを自分で持つ

`futex`・`epoll`・`eventfd`・`timerfd` は、ホストの同じ機能を使わず、paludarium の Kernel の中で
実装しています。macOS と Windows には Linux の `futex` がなく、WebAssembly で待つ手段は
`Atomics.wait` と `notify` しかないからです。ホストからは「待つ・起こす・期限つきで眠る」
という最小の道具だけを使います。代わりに、待ち行列の競合に気をつけて作っています。

## CPU と Kernel を分ける

CPU は、システムコールや例外に当たると、止まった理由を返して止まるだけで、Kernel を
知りません。スレッドの状態は Kernel が持ちます。こうすると、CPU と Kernel をそれぞれ
単独でテストでき、JIT とインタプリタを入れ替えやすくなります。

## Kernel とファイルシステムを分ける

「ゲストが指定したディレクトリの外に出られない」という保証を、`paludarium-vfs` だけで
確かめられるように、ファイルシステムを Kernel から分けています。ファジングの対象も
絞れます。ホストのディレクトリは、Session を作るときに開いたディレクトリの capability
からの相対でだけ操作します（ネイティブでは cap-std を使います）。

## WebAssembly のスレッド

いちばん大きな不確実性の 1 つだったので、最初の段階のうちに小さく試しました。
共有のメモリを持つ 2 つの Worker で `memory.atomic.wait32` と `notify` が、Node.js・
Chromium・Firefox・本物の Safari で動くことを確かめてから、作り始めています。

- Worker を作るのは起動用の JavaScript です。WebAssembly から直接 Worker を作れず、
  主スレッドでは待てず、止めるときにまとめて止められるからです。
- WebKit では、ランチャーはゲストを動かす前に共有メモリを上限の 1 GiB まで grow しておきます。
  WebKit では、ほかのスレッドが動いている共有メモリを grow すると、そのスレッドが「Out of bounds
  memory access」で失敗したり、ページがクラッシュしたりすることがあります。スレッドを作っては
  終わらせながらメモリを grow するテストのプログラムでは、2,700 回中 13 回起きました。先に grow
  しておくと 2,700 回中 0 回でした。アロケーターは grow でしかメモリを増やさないので、ランチャーは
  ヒープを割り当ててすぐ解放します。その領域には書き込まないので、macOS ではページは使われるまで
  物理メモリを使いません。ほかのブラウザでは必要になったときに grow します。Windows と、Linux の
  Firefox では、grow したメモリがすぐにシステムのコミットの上限に数えられるからです。WebKit の
  ブラウザはユーザーエージェントで見分けます。`AppleWebKit/` があって `Chrome/` がないものです。
  iOS のブラウザはすべてこれに当たります。このクラッシュは
  [WebKit のバグ 330591](https://bugs.webkit.org/show_bug.cgi?id=330591) として、paludarium
  なしで再現するページとともに報告しています。これが直れば、WebKit でもこの処理は要らなく
  なるかもしれません。
- 終わった Worker は次のスレッドを待ち、ランチャーとともに終わります。WebKit では、共有メモリの
  インスタンスを持つ Worker が終わるときに別のスレッドがそのメモリを grow すると、ページが
  クラッシュします。
- エミュレータ全体（Rust のヒープと std）を Worker の間で共有するために、std も atomics
  付きで作り直し、Worker ごとにスタックと TLS を分けています。

## JIT を独立した部品にする

JIT は、インタプリタとは別の部品にしています。設定で JIT の有無を切り替えられ、
ありとなしを同じテストで比べられます。命令の意味を CPU と JIT の 2 か所に持つことになるので、
差分テストでそろえています。

JIT の変換は Rust が行い、WebAssembly のバイト列を作ります。それをゲストの Worker の中の
JavaScript がコンパイルして実行します。生成したコードは、MMU の権限と範囲の検査を保ち、
書き換えられたページの変換結果は捨てます。

## Cranelift によるネイティブの JIT

ネイティブ版には、WebAssembly 向けの JIT とは別の JIT を持たせます。WebAssembly 向けの
JIT は、出力をコンパイルするのに JavaScript のエンジンを必要とするからです。コンパイルには
Cranelift を使います。Rust で書かれたコード生成器で、小さな関数なら数十から数百マイクロ秒で
コンパイルできます。LLVM はコンパイルがずっと遅く、Rust のライブラリでもないので使いません。
コンパイルするのは、インタプリタがデコードのときに求めておく形で、JIT 独自の命令の解釈では
ありません。そのため、コンパイルする命令の意味はインタプリタのもの 1 つだけです。それを、
ランダムな状態からの単体テスト、ファジングの対象、すべてのブロックをコンパイルした
差分テストで確かめます。

独立した crate にしたのは、コードをマップして呼び出すのに `unsafe` が要るからです。ホストの
crate 以外は、どれも `unsafe` を禁じています。コンパイルは、インタプリタが実行を続ける
あいだに専用のスレッドで行います。ブロックを実行するスレッドでコンパイルすると、多くの
ブロックを数百回ずつしか実行しない短いプログラムが、最大で 2 倍ほど遅くなったからです。
Cranelift の `speed` は、`none` よりコンパイルに時間がかかりますが、速いコードを作ります。
別のスレッドでコンパイルするなら、その時間はかけられます。レジスタは Cranelift の変数ではなく
メモリに置きます。そうすると途中で抜けるたびにすべてのレジスタを写す必要がなくなり、
コンパイルが約 3 倍速くなって、コードも速くなりました。

CI（x86-64 の Linux）の同じランナーで、JIT なしのインタプリタと比べると、`--jit` で Perl の
ハッシュと文字列のベンチマークが 15% と 27%、LuaJIT が 15%、OCaml が 8% 速くなりました。
Debian のプログラムは、どれもネイティブの Linux と同じ結果のままです。短い時間で終わる
プログラムの変化は、測定のばらつきの範囲でした。もっと効果が示せるまでは、既定では使いません。

## ファイルシステムを作る方法は 1 つ

snapshot は、別の復元用の呼び出しではなく、`createFileSystem` の `entries` として
渡します。そうすると `files` と組み合わせられ、`run()` も同じように受け付けます。
aube のように更新時刻で状態の新しさを判断するプログラムがあるので、更新時刻は
引き継ぎます。inode の番号は引き継がず、どのパスが同じ inode かだけを保ちます。
Linux と同じく、ハードリンクはシンボリックリンクも指せるので、ゲストが作れる状態は
すべて作り直せます。ディレクトリへのハードリンクは断ります。

## 3 つの入口

ライブラリ、コマンド、WebAssembly の 3 つの使い方を用意しました。使う人ごとに合う入口があり、
差分テストではコマンドを使えます。代わりに、互換を保つ対象が増えます。

## CPU ごとの違いを明示する

`REP` の命令が途中でフォールトしたときのフラグは、Intel と AMD で違いました。
paludarium は、ホストの CPU を見て動きを変えることはせず、モデルを明示して扱います。
既定は Intel の設計どおりです。`CPUID` は glibc のために AMD を名乗りますが
（[機能](../guide/features)）、この名乗りで動きは変わりません。

## ブラウザのネットワークは中継を通す

ブラウザは TCP の接続を張れず、名前も引けないので、ブラウザのゲストは WebSocket の
中継を通してネットワークを使います。接続 1 本ごと、名前を引くこと 1 回ごとに
WebSocket を 1 本使い、多重化はしません。そのためどちらの側も、その間で状態を持たず、
流れの制御も接続ごとです。名前は中継が引き、渡すアドレスごとにチケットで署名します。
ゲストはそのあとアドレスに接続するので、中継（別の台かもしれません）は、それが
どの許された名前から来たかを知る必要があるからです。最初に決めるのは今までどおり
カーネルの許可リストです。ページにあるものは誰にでも見えるので、中継も自分の
リストを持ちます。

## ゲスト自身のループバック

ゲストは自分の TCP と UDP のサーバーを動かせますが、相手は自身のソケットだけです。
ゲストのソケットが、ゲストのソケットの待ち受けているループバックのアドレスに接続すると、
カーネルが中で、ホストのものと同じメモリの上のストリーム 2 本をつなぎます。
データグラムは、受け取るソケットにそのまま届きます。どちらもホストには届きません。ホストやほかのマシンにサービスすると、ゲストが利用者のマシンにポートを
開けることになり、それは許可リストでは決められないので、扱いません。何もゲストの外に
出ないので、ゲスト自身のループバックも許可リストでは決めません。ゲストのソケットが
待ち受けていないループバックのポートは、Linux のループバックと同じく拒みます。ただし、
リストがホストのものを許していれば、ホストに届きます。

## 公開は Trusted Publishing だけ

crates.io と npm への公開は、長く有効なトークンを保存しない Trusted Publishing（OIDC）
だけで行います。npm のパッケージには provenance を付けます。公開済みの版は消せないので、
問題があれば crates.io の yank と npm の deprecate で対応し、修正版を出します。
