# テストと検証

paludarium の正しさは、「本物の x86-64 Linux と同じ結果になるか」で決めます。

## 差分テスト

同じゲストのプログラムを、本物の x86-64 Linux と paludarium の両方で動かし、結果を比べます。
期待する結果はリポジトリに保存せず、CI を動かすたびに、x86-64 Linux のランナーで
新しく作ります。

- **命令の単位**：レジスタ、フラグ、メモリを比べます。
- **プログラムの単位**：標準出力、標準エラー、終了状態をバイト単位で比べます。
- x86 で結果が決まっていないフラグや値（論理演算の後の AF、`div` の後のフラグなど）は、
  命令ごとの表に従って比べません。
- pid、時刻、乱数、アドレスのように実行ごとに変わる値は、比べる前にそろえるか、
  比べる対象から外します。
- 新しい命令やシステムコールは、実装の前にテストのケースを用意して、本物の Linux での
  結果を先に決めてから作ります。
- 各ケースには 30 秒の時間切れがあります。`TIME_WAIT` のような Linux 自身のタイマーを
  待つケースは、それより長くなります。
- プログラムのケースでは、エミュレーターの側は仮想の時計（`RecordingHost`）で動きます。
  スリープも時間を限った待ちも、ほかのスレッドから起こされるのを実時間で最大 10 ms
  （待つ時間がそれより短ければその時間）待ってから、期限まで時計を進めます。そのため、
  長いスリープを始めたところへほかのプロセスが送ったシグナルも、Linux と同じように
  スリープが終わる前に届きます。この時計はゲストのすべてのプロセスとスレッドで
  共通なので、どれかがスリープすると、ほかのものの見る時刻も進みます。そのためケースは
  時刻を出力せず、待った時間を比べるのは、その間にほかのプロセスやスレッドがスリープ
  しないときだけです。ほかのプロセスを待つときは、スリープではなく、パイプや、時間を
  限らずに待つディスクリプタを使います。
- コアダンプのケースでは、Linux がカーネルの既定の `core_pattern`（`core` で、
  `core_uses_pid` は 0）のままである必要があります。CI では `sysctl` で設定します。
  それ以外の環境では、クラッシュの処理系に送られたコアと比べず、そう伝えて止まります。
- AF_UNIX のデータグラムのケースでは、カーネルの既定の `net.unix.max_dgram_qlen` の
  10 である必要があります。多くのホストでは systemd がこれを大きくします。CI では
  `sysctl` で設定します（コンテナ自身のネットワークの名前空間ではこの値です）。それ以外の
  環境では、そう伝えて止まります。
- native の側は、本物の x86-64 Linux でなければなりません。Arm の Mac の Docker は、
  x86-64 のプログラムを QEMU のユーザーモードのエミュレーションで動かします。QEMU は
  シグナルを自分で扱うので、そこでは native の結果も Linux と違うことがあります。
  たとえば、`SA_NOCLDSTOP` を付けた親にも、止めて再開した子の SIGCHLD が届きます。
  Linux なら届きません。そのような実行は、どちらの向きにも証拠になりません。
  main でも、そこではプロセスのケースの 27 件とネットワークのケースの 5 件がこうした
  理由で失敗します。QEMU は次のように振る舞います。
  - 知らないソケットのオプション（`SO_PEEK_OFF`、`SO_PASSPIDFD`、`SO_PASSRIGHTS`、
    `SO_TIMESTAMP_NEW` など）を断り、`SO_TIMESTAMPING` を `int` として返します。
  - `recvmsg` のフラグに `MSG_CTRUNC` を入れません。
  - `SA_NOCLDSTOP`、`SA_NOCLDWAIT`、`F_SETSIG`、コアダンプ、`sigqueue` を自分で
    扱います。
  - 自分のスレッドとタイマーの番号が見えます。
  - `FIOQSIZE` を通しません。
  - Linux が `EINVAL` で断る `socket` の種類のフラグを受け付けます。

  Docker 自身のカーネルはデータグラムのバッファの数え方が違い、遅い native の側は
  時間切れになることがあります。コンテナの musl は Debian のもの（Debian 13 の
  1.2.5）で、ランナーのもの（1.2.4）とは違うので、musl のラッパーが変わったところ
  （`accept4`）では、ゲストはシステムコールを直接呼んでカーネルを確かめます。
  `mise run linux-dev-compare` は、そこでテストをチェックアウトと main の両方で、
  それぞれ自分の `ci/linux-dev/Dockerfile` が作るイメージの中で動かし（イメージを
  変えるチェックアウトでは、その変化も結果に出ます）、結果の違うケースだけを
  挙げます。
  チェックアウトでだけ失敗するケースは、もう一度動かします。そこで成功すれば、
  QEMU の下ではタイミングが揺れるケースもあるので不安定なものとして挙げ、また
  失敗すれば、このタスクは失敗します。main では動いたのにチェックアウトでは
  動かなかったケース（途中で止まったテスト）があるときも失敗します。
- native の結果は、CI のランナーのカーネル（`ci.yml` と `quality.yml` の `differential` と
  `coverage` のジョブに `ubuntu-latest` ではなく指定した `ubuntu-26.04` の Linux 7.0）のものです。
  決まったプログラムを比べるジョブは `ubuntu-latest` のままです。
  UDP のデータグラムが受信バッファから取る量のように、Linux がバージョンやビルドで
  変わるところでは、エミュレータはそのカーネルに合わせます（そのカーネルは Hyper-V の
  ネットワークのため小さなヘッドのキャッシュが 704 バイトで、Docker では 640 です）。ほかのカーネルの
  ランナーでは、そのケースが失敗することがあります。
  接続済みの AF_UNIX ソケットへの `listen` もその一つです。2026 年の Linux の修正どおり
  `EINVAL` にしています。これを書いた時点の `ubuntu-24.04` の 7.0.0-1017-azure では、
  まだ成功していました。
- `tests/guests/processes/cases.json` に載っているプロセスのケースと、`diff_processes`
  が動かすケースがちょうど同じかをテストで確かめます。載せたのに動かないケースは
  作れません。
- ネットワークのケース（`diff_network`）では、テスト自身が 127.0.0.1 でゲストの相手を
  します。そのため、native の Linux とエミュレータは同じサーバーと話します。
  エミュレータに許すのは、そのサーバーのポートと、何も待っていないポートだけです。
  `listen` と `udp` のケースはゲスト自身のループバックで待ち受け、Linux はネットワークの
  スタックで、エミュレータはカーネルの中で、それぞれ動かします。
  Linux での名前解決は、実行するマシンのファイルとサーバーによって変わるので、
  エミュレータの上でだけ、`localhost` を相手に確かめます。UDP は musl のリゾルバを
  通して、TCP は自前の問い合わせで確かめます。
- WebAssembly のパッケージのネットワークは、Node.js（`wasm-network.test.mjs`）と
  [中継](../guide/relay) を通したもの（`wasm-relay.test.mjs`）で確かめます。どちらも、
  単独で動くゲストが、テストが 127.0.0.1 で動かすサーバーに届き、`localhost` を
  引きます。中継のテストは、中継の許可リストとチケット、両方向の流れの制御
  （すべて書いてからでないと読まない相手も含む）、カーネルの規則と同じであることを
  確かめます。CI では `wasm-browser-network.mjs` が、Chromium、Firefox、WebKit、Safari で
  ゲストに中継を通させます。
- 毎晩、Debian の動的リンクのプログラムを、Debian のコンテナの中で本物の Linux と
  エミュレーターの両方で動かし、終了コードと標準出力を比べます
  （`tests/guests/distro/compare.py`）。シェル（fish も含む）、awk、Perl、Python、Ruby、PHP、Lua、Tcl、
  Node.js、Go、Java、Erlang、LuaJIT、OCaml、R、Guile、SBCL、pandoc、Emacs、BusyBox、SQLite、PostgreSQL、Redis、memcached、nginx、圧縮のツール、Git、OpenSSL、GnuPG、rsync、
  make、CMake、Ninja、gcc、g++、binutils などです。シグナルとタイマー、子プロセスとスレッド、ループバックのソケット、
  netlink（`lo` に対する iproute2 の `ip` と glibc の `getifaddrs`）、
  ファイルのロック（複数のプロセスが書き込む SQLite の WAL）、`/proc` を使うケースもあります。エミュレーターではコンテナのルートをマウントして動かすので、
  両方とも同じライブラリを読みます。どのケースも自分のディレクトリに書き、時刻を
  出さないので、出力を伏せるところはありません。どのケースも本物の Linux では成功します。
  そこで失敗したケースは、失敗どうしを比べてもあまり確かめられないので、失敗と数えます。
  コンテナの glibc は runner のものより
  古いことがあるので、エミュレーターは musl の静的なビルドを使います。Debian のイメージと
  パッケージは固定しません。Debian が今出しているものでエミュレーターを確かめるためです。
  この比較はリリースの前の検査にも入るので、Debian の更新でプログラムが動かなくなると、
  エミュレーターを直すまでリリースできません。パッケージの版は結果と一緒に残します。

## ファジング

decode、ELF の読み込み、システムコールの引数、ファイルシステムのパス、MMU の操作、CPU、
スレッド、futex、イベント、ソケット、2 つの JIT の 14 の対象を、AddressSanitizer と
LeakSanitizer を付けて、それぞれ 600 秒動かします。夜間の CI で毎日動かしています。

決まった時間のファジングは、どんな入力でも安全だという証明ではありません。それでも、
ゲストからのどんな入力でも panic しないことを、継続して確かめる手段にしています。

## メモリーの順序

リトマステスト（`crates/paludarium-cpu/tests/litmus.rs`）は、メモリーを共有する 2〜4 の
ゲストのスレッドで、`MOV`・`MFENCE`・`XCHG`・`LOCK OR` の小さなプログラムを何度も動かし、
x86 が許さない結果が出たら失敗します。MP、LB、フェンスの種類ごとの SB、2+2W、S、IRIW
です。CI のすべてのホストで動き、エミュレータ自身が x86 の順序を守らなければならない
Arm のホスト（macOS）でも動きます。

ねらいは、書き込みを遅らせる、古い値を持ち続けるといった、エミュレータの処理そのものが
壊す順序です。ホストのフェンスが抜けたことは、ほとんど見つけられません。エミュレートした命令 1 つには時間がかかるので、次の命令が
動く前にホストの書き込みは見えるようになっています。試した Arm のマシンでは、`MFENCE` や
lock 付きの命令のフェンスを外しても、テストはすべて通りました。

## カバレッジと静的な検査

- 行カバレッジの下限は 80% です。公開の前の測定では、workspace 全体で約 94% でした。
- `cargo fmt --check`、clippy（警告はエラー）、`cargo deny`（ライセンス、取得元、
  既知の脆弱性）を、プルリクエストごとに動かします。clippy は、`rust-version` が指す stable の Rust
  （最新の版で、毎週上げます）でも Linux・macOS・Windows のターゲットに動かし、ネイティブの crate が stable でもビルドできることを
  保ちます。テストは、固定した nightly だけで動かします。
- GitHub Actions の action は、すべてコミットの SHA で固定しています。

ゲストのプログラムは、ビルドの前に、依存がルートの方針の `cargo deny` を通らなければ
なりません。例外があるのは aube だけです。2 つのクレートのライセンスと、今のところ

## 公開の前の受け入れの確かめ

新しい版を公開する前に、公開するのとまったく同じコードで、次のことがそろっていることを
確かめます。そろわなければ公開しません（[リリースの流れ](../release)）。

- probe の 8 項目が、Linux・macOS・Windows と、Node.js・Chromium・Firefox・Safari の
  すべてで通る。
- aube の 4 つの操作が、すべての環境で、本物の x86-64 Linux と同じ標準出力と終了コードになる。
  4 つの WebAssembly の環境では、操作のたびにファイルシステムを snapshot から作り直しても
  一致し、作り直したファイルシステムの snapshot は元と同じになる。
- 4 つの WebAssembly の環境で、JIT ありとなしの両方の結果が一致する。
- JIT ありのほうが、統計的に意味のある差で速い（下を参照）。

## JIT とインタプリタ {#jit-and-the-interpreter}

JIT は、インタプリタと同じ意味でなければなりません。JIT だけの意味論は持たず、同じ差分テストを
JIT ありとなしの両方で動かして比べます。JIT が変換できない命令はインタプリタで動き、
その実行は「JIT の成功」に数えません。4 つの WebAssembly の環境では、probe、aube、
ripgrep の検索をすべて両方で動かし、JIT ありの実行では、変換したコードが実際に動いたことも
確かめます。

### ネイティブの JIT

ネイティブの JIT も、独自の意味論を持ちません。単体テストは、コンパイルするすべての形と、
それをランダムに並べたものを、ランダムなレジスタ、フラグ、メモリから実行し、レジスタ、
フラグ、メモリをインタプリタのものと比べます。命令の手前で止まったときは、インタプリタが
その命令で fault を起こすことも求めます。プルリクエストごとに、すべてのブロックを最初の
実行でコンパイルした差分テストも動かします（`PALUDARIUM_TEST_JIT=1`、`differential-jit`
ジョブ）。ファジングの対象 `jit_native` は、任意の命令のバイト列について、コンパイルした
コードとインタプリタを比べます。

### 速さの測り方

Node.js の Worker で、probe 全体を JIT ありとなしで 10 回ずつ、決まった順番で交互に動かします。
毎回新しい Session を使い、JIT の変換の時間も含めます。1024 通りの符号の入れ替えによる
片側の正確な検定で p < 0.05 であり、平均で JIT ありのほうが速いことを求めます。
外れ値を外したり、合格するまで測り直したりはしません。

公開の前の測定（Node.js 26.12.0）では、平均で JIT なしが 5.75 秒、JIT ありが 4.55 秒
（約 21% 速い）、p = 1/1024 でした。ほかの CPU やブラウザでも速くなるとは主張していません。
