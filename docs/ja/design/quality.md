# テストと検証

paludarium の正しさは、「本物の x86-64 Linux と同じ結果になるか」で決めます。

## 差分テスト

同じゲストのプログラムを、本物の x86-64 Linux と paludarium の両方で動かし、結果を比べます。
期待する結果はリポジトリに保存せず、CI を動かすたびに、x86-64 Linux のランナーで
新しく作ります。

- **命令の単位**：レジスタ、フラグ、メモリを比べます。

- **プログラムの単位**：標準出力、標準エラー、終了状態をバイト単位で比べます。

- x86 で結果が決まっていないフラグや値（論理演算の後の AF、`div` の後のフラグなど）は、
  命令ごとの表に従って比べません。

- x86 が結果の範囲だけを決めていて、Intel と AMD の CPU で結果が異なるところ（`RCPPS`
  など、x87 の超越関数の命令の最後のビット）では、ケースはビットそのものではなく、参照の
  値からその範囲内にあるか（どの CPU の結果も範囲内です）を出力します。CPU どうしが一致
  するところは、すべてのビットを出力します。そのような箇所は、すべて制限のページに書いて
  あります。

- pid、時刻、乱数、アドレスのように実行ごとに変わる値は、比べる前にそろえるか、
  比べる対象から外します。

- 新しい命令やシステムコールは、実装の前にテストのケースを用意して、本物の Linux での
  結果を先に決めてから作ります。

- 各ケースには 30 秒の時間切れがあります。`TIME_WAIT` のような Linux 自身のタイマーを
  待つケースは、それより長くなります。

- プログラムのケースでは、エミュレーターの側は仮想の時計（`RecordingHost`）で動きます。
  スリープも時間を限った待ちも、ほかのスレッドから起こされるのを実時間で最大 10 ms
  （待つ時間がそれより短ければその時間）待ってから、期限まで時計を進めます。そのため、
  長いスリープを始めたところへほかのプロセスが送ったシグナルも、Linux と同じように
  スリープが終わる前に届きます。この時計はゲストのすべてのプロセスとスレッドで
  共通なので、どれかがスリープすると、ほかのものの見る時刻も進みます。そのためケースは
  時刻を出力せず、待った時間を比べるのは、その間にほかのプロセスやスレッドがスリープ
  しないときだけです。ほかのプロセスを待つときは、スリープではなく、パイプや、時間を
  限らずに待つディスクリプタを使います。

- コアダンプのケースでは、Linux がカーネルの既定の `core_pattern`（`core` で、
  `core_uses_pid` は 0）のままである必要があります。CI では `sysctl` で設定します。
  それ以外の環境では、クラッシュの処理系に送られたコアと比べず、そう伝えて止まります。

- AF_UNIX のデータグラムのケースでは、カーネルの既定の `net.unix.max_dgram_qlen` の
  10 である必要があります。多くのホストでは systemd がこれを大きくします。CI では
  `sysctl` で設定します（コンテナ自身のネットワークの名前空間ではこの値です）。それ以外の
  環境では、そう伝えて止まります。

- perf の抑制のケースでは、Linux がティックのどの割り込みでも抑えるよう
  `kernel.perf_event_max_sample_rate` を 1 にし、あとで値を戻します。ケースが戻せない
  ときはハーネスも戻します。この sysctl はカーネル全体のものなので、ケースを動かせるのは
  CI のワークフローが許すとき（`PALUDARIUM_PERF_SAMPLE_RATE_WRITES=1`）だけです。CI では
  ケースを一つずつ動かすので、ほかの perf のケースがこの値を見ることはありません。それ以外の
  環境では、ホストの値に触れず、そう伝えて止まります。

- `chroot` のケースは、自分のユーザー名前空間で `CAP_SYS_CHROOT` を使います。Linux は
  これを許します。Ubuntu の AppArmor は、`kernel.apparmor_restrict_unprivileged_userns`
  が 1 のあいだ、そこでのケーパビリティをすべて拒みます（`unprivileged_userns` の
  プロファイル）。そのため CI では `sysctl` で 0 にします。それ以外の環境では、そういう
  ホストの native の結果とは違います。

- native の側は、本物の x86-64 Linux でなければなりません。Arm の Mac の Docker は、
  x86-64 のプログラムを QEMU のユーザーモードのエミュレーションで動かします。QEMU は
  シグナルを自分で扱うので、そこでは native の結果も Linux と違うことがあります。
  たとえば、`SA_NOCLDSTOP` を付けた親にも、止めて再開した子の SIGCHLD が届きます。
  Linux なら届きません。そのような実行は、どちらの向きにも証拠になりません。
  main でも、そこではプロセスのケースの 27 件とネットワークのケースの 5 件がこうした
  理由で失敗します。QEMU は次のように振る舞います。
  - 知らないソケットのオプション（`SO_PEEK_OFF`、`SO_PASSPIDFD`、`SO_PASSRIGHTS`、
    `SO_TIMESTAMP_NEW` など）を断り、`SO_TIMESTAMPING` を `int` として返します。
  - `recvmsg` のフラグに `MSG_CTRUNC` を入れません。
  - `SA_NOCLDSTOP`、`SA_NOCLDWAIT`、`F_SETSIG`、コアダンプ、`sigqueue` を自分で
    扱います。
  - 自分のスレッドとタイマーの番号が見えます。
  - `FIOQSIZE` を通しません。
  - Linux が `EINVAL` で断る `socket` の種類のフラグを受け付けます。

  Docker 自身のカーネルはデータグラムのバッファの数え方が違い、遅い native の側は
  時間切れになることがあります。コンテナの musl は Debian のもの（Debian 13 の
  1.2.5）で、ランナーのもの（1.2.4）とは違うので、musl のラッパーが変わったところ
  （`accept4`）では、ゲストはシステムコールを直接呼んでカーネルを確かめます。
  Docker は `/proc/sys` を読み取り専用でマウントします。`mise run linux-dev` は、
  コンテナ自身の名前空間に属する sysctl（`net.*`、`fs.mqueue.*`、`kernel.*` の
  うち IPC と UTS のもの）だけを書き込めるようにするので、native の実行はそれらを
  設定できます。残りの、Docker のホスト自身のものは読み取り専用のままです。
  `mise run linux-dev-compare` は、そこでテストをチェックアウトと main の両方で、
  それぞれ自分の `ci/linux-dev/Dockerfile` が作るイメージの中で動かし（イメージを
  変えるチェックアウトでは、その変化も結果に出ます）、結果の違うケースだけを
  挙げます。
  チェックアウトでだけ失敗するケースは、もう一度動かします。そこで成功すれば、
  QEMU の下ではタイミングが揺れるケースもあるので不安定なものとして挙げ、また
  失敗すれば、このタスクは失敗します。main では動いたのにチェックアウトでは
  動かなかったケース（途中で止まったテスト）があるときも失敗します。

- native の結果は、CI のランナーのカーネル（`ci.yml` と `quality.yml` の `differential` と
  `coverage` のジョブに `ubuntu-latest` ではなく指定した `ubuntu-26.04` の Linux 7.0）のものです。
  決まったプログラムを比べるジョブは `ubuntu-latest` のままです。
  UDP のデータグラムが受信バッファから取る量のように、Linux がバージョンやビルドで
  変わるところでは、エミュレータはそのカーネルに合わせます（そのカーネルは Hyper-V の
  ネットワークのため小さなヘッドのキャッシュが 704 バイトで、Docker では 640 です）。ほかのカーネルの
  ランナーでは、そのケースが失敗することがあります。
  接続済みの AF_UNIX ソケットへの `listen` もその一つです。2026 年の Linux の修正どおり
  `EINVAL` にしています。これを書いた時点の `ubuntu-24.04` の 7.0.0-1017-azure では、
  まだ成功していました。

- `tests/guests/processes/cases.json` に載っているプロセスのケースと、`diff_processes`
  が動かすケースがちょうど同じかをテストで確かめます。載せたのに動かないケースは
  作れません。

- ネットワークのケース（`diff_network`）では、テスト自身が 127.0.0.1 でゲストの相手を
  します。そのため、native の Linux とエミュレータは同じサーバーと話します。
  エミュレータに許すのは、そのサーバーのポートと、何も待っていないポートだけです。
  `listen` と `udp` のケースはゲスト自身のループバックで待ち受け、Linux はネットワークの
  スタックで、エミュレータはカーネルの中で、それぞれ動かします。
  Linux での名前解決は、実行するマシンのファイルとサーバーによって変わるので、
  エミュレータの上でだけ、`localhost` を相手に確かめます。UDP は musl のリゾルバを
  通して、TCP は自前の問い合わせで確かめます。

- WebAssembly のパッケージのネットワークは、Node.js（`wasm-network.test.mjs`）と
  [中継](../guide/relay) を通したもの（`wasm-relay.test.mjs`）で確かめます。どちらも、
  単独で動くゲストが、テストが 127.0.0.1 で動かすサーバーに届き、`localhost` を
  引きます。中継のテストは、中継の許可リストとチケット、両方向の流れの制御
  （すべて書いてからでないと読まない相手も含む）、カーネルの規則と同じであることを
  確かめます。CI では `wasm-browser-network.mjs` が、Chromium、Firefox、WebKit、Safari で
  ゲストに中継を通させます。

- 毎晩、Debian の動的リンクのプログラムを、Debian のコンテナの中で本物の Linux と
  エミュレーターの両方で動かし（エミュレーターではネイティブの JIT なしとありで 1 回ずつ）、終了コードと標準出力を比べます
  （`tests/guests/distro/compare.py`）。シェル（fish も含む）、awk、Perl、Python、Ruby、PHP、Lua、Tcl、
  Node.js、Go、Java、Erlang、LuaJIT、OCaml、R、Guile、SBCL、pandoc、Emacs、BusyBox、SQLite、PostgreSQL、Redis、memcached、nginx、圧縮のツール、Git、OpenSSL、GnuPG、rsync、
  make、CMake、Ninja、gcc、g++、binutils などです。シグナルとタイマー、子プロセスとスレッド、ループバックのソケット、
  netlink（`lo` に対する iproute2 の `ip` と glibc の `getifaddrs`）、
  ファイルのロック（複数のプロセスが書き込む SQLite の WAL）、`/proc` を使うケースもあります。エミュレーターではコンテナのルートをマウントして動かすので、
  両方とも同じライブラリを読みます。どのケースも自分のディレクトリに書き、時刻を
  出さないので、出力を伏せるところはありません。どのケースも本物の Linux では成功します。
  そこで失敗したケースは、失敗どうしを比べてもあまり確かめられないので、失敗と数えます。
  コンテナの glibc は runner のものより
  古いことがあるので、エミュレーターは musl の静的なビルドを使います。Debian のイメージと
  パッケージは固定しません。Debian が今出しているものでエミュレーターを確かめるためです。
  この比較はリリースの前の検査にも入るので、Debian の更新でプログラムが動かなくなると、
  エミュレーターを直すまでリリースできません。パッケージの版は結果と一緒に残します。

## ファジング

decode、ELF の読み込み、システムコールの引数、ファイルシステムのパス、MMU の操作、CPU、
スレッド、futex、イベント、ソケット、BPF のソケットフィルター、2 つの JIT の 15 の対象を、AddressSanitizer と
LeakSanitizer を付けて、それぞれ 600 秒動かします。夜間の CI で毎日動かしています。

決まった時間のファジングは、どんな入力でも安全だという証明ではありません。それでも、
ゲストからのどんな入力でも panic しないことを、継続して確かめる手段にしています。
どの対象もカーネルを `fuzzing` feature 付きでビルドします。そのため、検証器が受け入れた BPF のプログラムが指す先の外を読み書きすると、どの対象でも、デバッグビルドと同じく panic します。

プルリクエストでも、そのうち 7 つ（`vfs_paths`、`load_elf`、`syscall_args`、`kernel_threads`、`kernel_futex`、`kernel_events`、`kernel_sockets`）を、同じ 600 秒、同じサニタイザーで、`-seed=1` と空のコーパスから動かします。シードとコーパスが決まっているので、変えたコードをリンクしない対象は main と同じ探索を繰り返すだけです。そのため、変更が届く対象だけを動かします。対象がリンクするのは、ソース（`#[path]` で取り込むモジュールも含む）が名前を挙げる workspace のパッケージと、その依存です。依存は `scripts/ci-changes.py` が `cargo metadata` から読みます。それらのパッケージを変えると、その対象が動きます。マニフェスト、`Cargo.lock`、`rust-toolchain.toml`、`fuzz/`、`fuzz-pr.yml`、選ぶスクリプト、ほかにファジングの群が要るものを変えたときと、main への push では、7 つすべてを動かします。どの対象にも変更が届かないときは、ファジングのジョブを飛ばします。そのときも、15 の対象すべてがビルドできることは、別のジョブが確かめます。

## メモリーの順序

リトマステスト（`crates/paludarium-cpu/tests/litmus.rs`）は、メモリーを共有する 2〜4 の
ゲストのスレッドで、`MOV`・`MFENCE`・`XCHG`・`LOCK OR` の小さなプログラムを何度も動かし、
x86 が許さない結果が出たら失敗します。MP、LB、フェンスの種類ごとの SB、2+2W、S、IRIW
です。CI のすべてのホストで動き、エミュレータ自身が x86 の順序を守らなければならない
Arm のホスト（macOS）でも動きます。

ねらいは、書き込みを遅らせる、古い値を持ち続けるといった、エミュレータの処理そのものが
壊す順序です。ホストのフェンスが抜けたことは、ほとんど見つけられません。エミュレートした命令 1 つには時間がかかるので、次の命令が
動く前にホストの書き込みは見えるようになっています。試した Arm のマシンでは、`MFENCE` や
lock 付きの命令のフェンスを外しても、テストはすべて通りました。

## カバレッジと静的な検査

- 行カバレッジの下限は 80% です。公開の前の測定では、workspace 全体で約 94% でした。`ci.yml` の `coverage` ジョブは、5 つのゲートをこの下限で確かめ、それぞれ自分のテストだけを数えます。workspace 全体、コアのパッケージ（harness のテストは走らせ、harness 自身のファイルは除く）、WebAssembly のビルドが使う Rust のクレート、端末を支えるクレート、encodings のテストの下の CPU とデコーダーです。
- コアと workspace のゲートは、計装したビルドとテストの実行をそれぞれ 1 回で共有します。先にコアのパッケージと harness のテストを走らせ、コアのゲートはそのプロファイルで報告します。次に残りのパッケージのテストがプロファイルを足し、workspace のゲートはその全部で報告します。2 回の実行で Cargo がビルドするユニットは workspace 全体を 1 回で走らせるときと同じなので、どちらの数字も別々に走らせたときの数字と同じです。報告はターゲットのディレクトリにあるテストのバイナリをすべて数えるので、ほかの 3 つのゲートはそれぞれ自分でクリーンして自分のテストを走らせます。端末のゲートの前には、コアのゲートの外のパッケージのテストのバイナリを消し、以前コアの実行が最後だったときと同じく、コアの実行が残したものから始めます。`quality.yml`（毎晩と公開の前）にあるこのジョブの写しも、同じようにゲートを走らせます。`mise run coverage` も、コアと workspace のゲートをこのように走らせます。同じコミットで比べると、別々に走らせたときと共有したときで、どのゲートも数える行は同じでした。通らなかった行の違いは、スレッドのタイミングに依存する数行だけでした。
- 各ゲートが出す表は、ゲートが測るのと同じパッケージとファイルを数えます。`-p` のない `cargo llvm-cov report` は、テストのバイナリがリンクするコードを持つ workspace のメンバーをすべて数えます。そのため端末と encodings の表は、`paludarium` のバイナリと harness がリンクする `paludarium-jit-native` を 0% で足していて、合計が測った率より低く出ていました（80.83% が 79.86%）。前の段階のバイナリではなく、クリーンしたターゲットのディレクトリからゲートを始めても、数える行も率も同じで、違うのはスレッドのタイミングに依存する行だけでした。
- 端末のゲートは、ライブラリーの単体テストを走らせ、harness の差分テストは走らせません。差分テストが確かめるシステムコールがそこでも数えられるように、カーネルの単体テストの一部（`crates/paludarium-kernel/src/` の `replay_tests.rs`、`ptrace_replay_tests.rs`、`bpf_tests.rs`、`bpf_prog_tests.rs`、`mqueue_tests.rs`、`pty_tests.rs`、`mctp_tests.rs`、`seccomp_tests.rs`、`perf_sample_tests.rs` と `perf_side_band_tests.rs`）は、差分テストのゲストと同じ順でその呼び出しをし、ゲストがネイティブの Linux で出す行と比べます。その行は、Linux 7.0 で出したもの、または差分テストが Linux と同じだと確かめているケースでは、エミュレーターの上で出したものです。ゲスト全体は、今も毎回の差分テストが Linux と比べます。
- カバレッジのジョブの要約には、lcov を書くゲート（WebAssembly、端末、encodings）ごとに、lcov の実行された行と測った行、その率、80% の下限（行単位で切り上げ）より何行多く実行されているかを出します。そのため、プルリクエストは、ゲートが落ちる前に余裕が減るのを見られます。`--fail-under-lines` は lcov のファイルを読みません。cargo-llvm-cov は、同じテストのバイナリ、プロファイル、除くファイルから llvm-cov が出す JSON の行の合計と比べます。これは lcov と同じ行を数えるので、要約の率はゲートが比べた率です。コアと workspace のゲートは lcov を書かず、表の TOTAL の行が示す合計と比べます。表も出すゲート（端末と encodings）では、その TOTAL の行が同じ実行された行と測った行を数えているかも要約に出します。main（run 44284364893）では、どちらも同じでした。TOTAL が違うのは、`report` がゲートの実行と違うバイナリやファイルを読むときだけです。前に、端末と encodings の表が `paludarium-jit-native` を足していたときがそうでした（上）。
- `cargo fmt --check`、clippy（警告はエラー）、`cargo deny`（ライセンス、取得元、
  既知の脆弱性）を、プルリクエストごとに動かします。clippy は、`rust-version` が指す stable の Rust
  （最新の版で、毎週上げます）でも Linux・macOS・Windows のターゲットに動かし、ネイティブの crate が stable でもビルドできることを
  保ちます。テストは、固定した nightly だけで動かします。どちらの clippy も、それだけで workspace になっている `fuzz/` の crate も検査します（stable のほうは Linux のターゲット）。`mise run lint:all`（`rust:check`）は、同じ clippy を手元でも動かし、stable のほうは `scripts/stable-cargo.sh` を通します。`lint:all` を動かす CI のワークフローは、stable のほうを `stable-clippy` に任せます。
- GitHub Actions の action は、すべてコミットの SHA で固定しています。

| 毎日 | 定期実行のワークフローが時間どおりに始まったかを確かめます。始まらなかった、動かなかった、無効になっていたときは Issue を立てます |

| 公開の前 | 公開する同じコードで、上のすべて（下を参照） |

プルリクエストと main への push では、重いジョブ（差分テスト、カバレッジ、ファジング、ゲストのプログラム、WebAssembly の検査）は、速い段階が通ってから始まります。速い段階は、lint、clippy（stable の Rust でも）、polyglot lint、Linux の単体テストで、2〜4 分です。これに落ちた head や、その間に後の push で置き換わった head は、重いジョブのランナーを使いません。速い段階の検査のうち変更が要らないもの（main への push での polyglot lint、Rust を変えないときの lint と clippy）は飛ばされます。飛ばされたことは、それを待つジョブへ伝わって、そのジョブも飛ばしてしまいます。そのため、重いジョブは速い段階のジョブ自身の結果を見ます。必須の検査の `ci-ok` は、すべてのジョブを自分で待ちます。そのため、速い段階が落ちて飛ばされたジョブがあっても `ci-ok` は通りません。そうなっていない `ci.yml` は `scripts/ci-changes.py --self-test` が拒みます。Dependency Review は、Cargo か npm のマニフェストかロックファイル、ワークフロー、ローカルのアクションを変えるプルリクエストでだけ走ります。

macOS のランナーは足りなくなることがあるため、2 種類のジョブは、変更がその検査するものに届くときだけ走ります。単体テストのジョブ（Linux・macOS・Windows）が走るのは、変更が、それの検査するクレート（harness はライブラリーだけ）、マニフェスト、ロックファイル、ツールチェーンに触れるとき、またはクレートの外のファイルのうち、そのソースが相対パス（`#[path]`、`include_str!`、クレートのディレクトリーにつないだパス）で名指すものか、harness の命令の一覧が `tests/guests` の下で読むものに触れるときです。そのため、差分テストのゲストやスクリプトを足すだけでは走らず、JIT の単体テストが読む `packages/paludarium-wasm/jit-support.mjs` を変えると走ります。WebAssembly の検査の Safari の行は、変更が届くクレートが、Wasm のモジュール（`paludarium-wasm`）がリンクしないもの（harness、コマンド、ネイティブの JIT など）だけのとき、省きます。Linux の行は走ります。`scripts/ci-changes.py` はどちらも `cargo metadata` とソースから読みます。その自己テストは、実行時にパスを組み立てる単体テストのソースが、何を読むかを示していないと落ちます。

GitHub は、ホストのランナーがどれも受け取らなかったジョブを、注記（「not acquired by Runner」）を付け、1 つのステップも動かさずに取り消します。macOS の arm64 のランナーが足りないときに起きます。そのテストは動いていないので、`ci-ok` は落ちます。CI の実行で落ちたのが、`ci-ok` のほかはこのようなジョブだけのときは、`rerun-unacquired.yml` が `gh run rerun --failed` で落ちたジョブを走らせ直します。1 つの実行につき 2 回までで、ブランチの後の実行が置き換えたときは走らせ直しません。ステップを動かして落ちたジョブは決して走らせ直さず、そのときは何も走らせ直しません。なぜ走らせ直した、または走らせ直さなかったかは、そのログに出ます。判断は `scripts/ci-rerun.py --self-test` が確かめます。

そのため、`CI` の実行のこのようなジョブを手で走らせ直さないでください。ワークフローは、その実行が終わるとすぐに始まります。見るのは `CI` だけで、`Publish` や `release-acceptance` は見ません。先に手で走らせ直すと、ワークフローは最新でない試行を見ることになり、何も走らせ直しません。手で走らせ直すのは、ログに 2 回走らせ直し済みと出たとき、またはステップを動かして落ちたジョブの失敗が一時的なものだと考える理由があるときだけにしてください。

ゲストのプログラムは、ビルドの前に、依存がルートの方針の `cargo deny` を通らなければ
なりません。例外があるのは aube と coreutils だけです。coreutils の例外は、coreutils だけに
認めた 1 つで、`uu_tail` が使う `notify` 8.2.2 の CC0-1.0 のライセンスです。ビルドはその
ライセンスの全文を残します。aube の例外は、2 つのクレートのライセンスと、今のところ
`zstd` 0.13.3 と `zstd-safe` 7.3.0 への 3 つの RustSec のアドバイザリ（RUSTSEC-2026-0391、
RUSTSEC-2026-0398、RUSTSEC-2026-0403）です。aube はこの版を、`zstd` を版まで固定している
`decmpfs` から受け取るので、自分では上げられません。アドバイザリの例外は、`decmpfs` が
`zstd` 0.14 にしたリリースを出したら外します
（[SocketDev/decmpfs#16](https://github.com/SocketDev/decmpfs/issues/16)）。どのクレートにも
当たらなくなった例外は監査を失敗させるので、例外が要らなくなった aube の更新は、例外を
外すまでマージされません。aube には今のところ、`url` 2.5.8 への RUSTSEC-2026-0592 の
例外もあります。aube 2.10.0 の `Cargo.lock` は、この版を `hickory-net`、`hickory-resolver`、
`reqwest` を通して持っています。`url` 2.5.9 で直っているので、固定している aube のリリースが
`url` 2.5.9 以降を固定したら外します。例外はすべて
`tests/guests/programs/evidence.py` に並んでいて、`source-lock.json` はクレートの版まで
書いて例外を挙げています。

## 公開の前の受け入れの確かめ

新しい版を公開する前に、公開するのとまったく同じコードで、次のことがそろっていることを
確かめます。そろわなければ公開しません（[リリースの流れ](../release)）。

- probe の 8 項目が、Linux・macOS・Windows と、Node.js・Chromium・Firefox・Safari の
  すべてで通る。
- aube の 4 つの操作が、すべての環境で、本物の x86-64 Linux と同じ標準出力と終了コードになる。
  4 つの WebAssembly の環境では、操作のたびにファイルシステムを snapshot から作り直しても
  一致し、作り直したファイルシステムの snapshot は元と同じになる。
- 4 つの WebAssembly の環境で、JIT ありとなしの両方の結果が一致する。
- JIT ありのほうが、統計的に意味のある差で速い（下を参照）。

## JIT とインタプリタ {#jit-and-the-interpreter}

JIT は、インタプリタと同じ意味でなければなりません。JIT だけの意味論は持たず、同じ差分テストを
JIT ありとなしの両方で動かして比べます。JIT が変換できない命令はインタプリタで動き、
その実行は「JIT の成功」に数えません。4 つの WebAssembly の環境では、probe、aube、
ripgrep の検索、coreutils のケースをすべて両方で動かし、JIT ありの実行では、変換したコードが
実際に動いたことも確かめます。

### ネイティブの JIT

ネイティブの JIT も、独自の意味論を持ちません。単体テストは、コンパイルするすべての形と、
それをランダムに並べたものを、ランダムなレジスタ、フラグ、メモリから実行し、レジスタ、
フラグ、メモリをインタプリタのものと比べます。命令の手前で止まったときは、インタプリタが
その命令で fault を起こすことも求めます。プルリクエストごとに、すべてのブロックを最初の
実行でコンパイルした差分テストも動かします（`PALUDARIUM_TEST_JIT=1`、`differential-jit`
ジョブ）。ファジングの対象 `jit_native` は、任意の命令のバイト列について、コンパイルした
コードとインタプリタを比べます。単体テストの実行の半分は、スレッドの TLB のスロットを埋めてから
始めるので、コンパイルしたコードはスロットを通して読み書きします。MMU のテストは、`mprotect`、
`fork`、`clear_refs`、`UFFDIO_WRITEPROTECT` の後に、スロットがどのページの読み書きを許すかを
確かめます。`mprotect` と `UFFDIO_WRITEPROTECT` の後に、読み込みが埋め直したスロットを通す
書き込みは fault にならなければならず、`clear_refs` の後の書き込みは soft-dirty ビットを
立て直さなければなりません。

### 速さの測り方

Node.js の Worker で、probe 全体を JIT ありとなしで 10 回ずつ、決まった順番で交互に動かします。
毎回新しい Session を使い、JIT の変換の時間も含めます。1024 通りの符号の入れ替えによる
片側の正確な検定で p < 0.05 であり、平均で JIT ありのほうが速いことを求めます。
外れ値を外したり、合格するまで測り直したりはしません。

公開の前の測定（Node.js 26.12.0）では、平均で JIT なしが 5.75 秒、JIT ありが 4.55 秒
（約 21% 速い）、p = 1/1024 でした。ほかの CPU やブラウザでも速くなるとは主張していません。
