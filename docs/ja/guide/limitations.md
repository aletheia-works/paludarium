# 制限

paludarium は、まだ若いプロジェクトです。次のことは、今はできないか、確かめていません。

## できないこと

- **今のところ x87 の一部**：`FISTTP` は `CPUID` が示さない SSE3 の命令なので
  実装していません。`FNSTENV`、`FNSAVE`、`FXSAVE` が書く、最後の命令とそのメモリ
  オペランドの場所は保っていません。その欄は 0 で、Intel と AMD の CPU でも書く内容が
  異なります。オペランドが離れているときに `FPREM` と `FPREM1` が途中のどこで止まるかは
  CPU ごとに異なりますが、最後の剰余は同じです。
- **渡されていない動的リンクのプログラムのファイル**：Linux と同じくインタプリタと一緒に
  動かすので、musl と glibc の動的リンカーで動きます。インタプリタとライブラリは
  セッション自身のファイルから読むので、マウントするか渡す必要があります。
- **32-bit の x86、AVX、AVX-512、MMX**：対象外です。glibc が必須とするので `CPUID` は
  MMX を示しますが、その命令は `SIGILL` で止まります。MMX レジスタを使う SSE と SSE2 の
  命令（`CVTPI2PS`、`MOVQ2DQ`、`PSHUFW` など）も同じです。
- **x87 の超越関数の命令の最後のビット**：`FSIN`、`FCOS`、`FSINCOS`、`FPTAN`、
  `FPATAN`、`F2XM1`、`FYL2X`、`FYL2XP1` は、Intel と AMD の CPU が計算するものを正しく
  丸めた結果を返します（角度を取る 4 つは、どちらの CPU とも同じく、66 ビットで切った
  π/2 の倍数を引きます）。実際の CPU の結果はその最後の位の 1 単位以内で、100 個の値の
  うちいくつかで異なります。Intel のほうが AMD より多く、両者の間でも異なります。そのとき
  C1 は CPU 自身の結果に従います。小さな値の結果がその値そのものになるとき、Intel の CPU
  はどの丸めモードでもその値を返し、エミュレーターと AMD の CPU は丸めます。`FSINCOS`
  は AMD の CPU と同じく正弦で C1 を決めます（Intel の CPU は余弦で決めます）。そのため、
  これらを使う glibc と musl の `long double` の関数（`expl`、`logl`、`atan2l` など）は、
  実際の CPU と最後の 1、2 ビットが異なることがあります。マニュアルが結果を決めていない
  ところでは、エミュレーターは両方の CPU と同じく、`F2XM1` は ±1 を超える値を、`FYL2XP1`
  は 1 + x が正でない値を、そのまま残します。テストでは、CPU どうしが一致するところは
  すべてのビットを、それ以外ではこの範囲を確かめています。
- **`RCPPS`、`RCPSS`、`RSQRTPS`、`RSQRTSS` の正確な結果**：x86 が決めているのは誤差の
  範囲（1.5 × 2⁻¹²）だけで、CPU はそれぞれの表から答えます。エミュレーターは浮動小数点
  の除算（`RSQRT` はその前に平方根）で計算するので、下位のビットが実際の CPU と異なる
  ことがあります。テストで
  確かめているのは、この範囲と特殊な値で、ビットそのものではありません。
- **アクセスできないメモリへの、空のマスクの `MASKMOVDQU`**：エミュレーターは何も
  アクセスしませんが、実際の CPU はフォールトすることがあります（AMD EPYC ではフォールト
  し、`SIGSEGV` で終わります）。後ろのバイトでフォールトすると前のバイトは書かれたまま
  ですが、これは実際の CPU と比べていません。
- **`/proc/self/maps` の一部**：スタックの VMA は
  初めから全体の大きさで、Linux のように使うにつれて伸びません。
  ファイルの名前を変えても、別のマウント名前空間で開かれたものと、この名前空間に別に入った
  （`unshare` と `setns` はそのつど分かれます）プロセスが開いたものの名前は、マップ、コアの
  `NT_FILE` ノート、`/proc/<pid>/exe` では動きません。Linux の `d_move` はどれも動かします。
- **vDSO の一部**：その関数はシステムコールを呼びます。Linux の vDSO がそうするのは、
  ユーザー空間から読める時計がないときだけです。そのため、Linux の速い経路ならシステム
  コールを呼ばないところでも、seccomp のフィルター、ptrace のトレーサーのシステムコール
  での停止、システムコールの数え上げには呼び出しが見えます。`[vvar]` は 0 で、Linux では
  時刻が入っていますが、ここでは何も読みません。`__vdso_getrandom` と
  `__vdso_sgx_enter_enclave`（とその弱い別名）はありません。前者の約束事（C ライブラリーが
  求める不透明な状態）はシステムコールのものではなく、SGX はエミュレートしないためで、
  C ライブラリーは `getrandom(2)` を使います。`smaps` は、触った `[vdso]` のページを
  そのプロセス自身のもの（`Private_Clean`）として数えます。Linux ではすべてのプロセスで
  共有されます（`Shared_Clean`、`Pss` は 0）。`[vvar]` はテスト用マシンの Linux 7.0 の
  ものです。7.2 からは `VM_IO | VM_PFNMAP` ではなく `VM_MIXEDMAP` になり
  （c27e727c9a60）、`mlock` がページを用意し、`get_user_pages` で届くことがあり、ページ
  1 と 3 はバスエラーではなく 0 になります（43648f9f3a67）。
- **`/proc/self/smaps` と `smaps_rollup` の一部**：数える値は、エミュレーターのページのエントリーから
  出します。`Referenced` は数えたページすべてです。読み込んだプログラムの
  セグメントのページは、ページではなくセグメントに書き込んだ時点で匿名として数えます。
  ファイルのマッピングで読み込みのフォールトが起きても、マップするのは
  周りの 16 ページまでです（[機能](./features#system-calls)）。Linux は、ページ
  キャッシュの大きなフォリオがファイル、VMA、ページテーブルの中に収まるならフォリオ全体を
  マップします（`filemap_map_folio_range`）。エミュレーターのページキャッシュには、
  ファイルシステムごとに大きさを決める大きなフォリオがありません。`pagemap` も同じ
  ページを示します。ヒュージページもプロテクションキーも
  ないので、`THPeligible` はいつも 0 で、`ProtectionKey` はありません。`VmFlags` には
  `ht`、`dp`（`MAP_HUGETLB`、`MAP_DROPPABLE`）がありません。
  `write` で埋めたホストのファイルのページはクリーンです（下の「`write` で埋めたページ」）。
- **`/proc/<pid>/mem` の `i64::MAX` を超える位置**：`pread64` と `pwrite64` は、
  Linux v7.0 の `ksys_pread64` と `ksys_pwrite64` がどのファイルでもするのと同じく、
  これを拒みます（`EINVAL`）。Linux master は符号なしの位置のファイル
  （`FOP_UNSIGNED_OFFSET`）では受け付けます。ランナーのカーネルに master の変更が入るまで、
  v7.0 に従います。
- **`/proc/<pid>/pagemap` の一部**：エントリーは、`smaps` の値と同じくエミュレーターのページのエントリーから出します。
  読み込んだプログラムのセグメントやファイルのプライベートな
  マッピングのページは、ページではなくマッピングに書き込むまでファイルのもの（ビット 61）
  です。フレーム番号は、Linux が物理
  フレームを見せる `CAP_SYS_ADMIN` のある読み手にも 0 です。ユーザー空間は 4 段のページ
  テーブルと同じく 2^47 バイトで終わります。
- **`PAGEMAP_SCAN` の一部**：
  - CI のランナーの Linux 7.0 と違うところは Linux master に従います。
    - 書き込まれたページ（`PAGE_IS_WRITTEN`）は、書き込み保護に登録された VMA の
      中だけです。そこでは空のページも書き込まれています。Linux 7.0 は、書き込み保護
      されていない存在するページとマーカーをすべて書き込まれたとし、空のページはそうしません。
    - `PAGE_IS_ACCESSED` を受け付けます。読み込みの保護はないので、どのページも
      持ちません。
    - 知らない ioctl は `ENOTTY` です。Linux 7.0 は `EINVAL` を返します。
    - アドレス空間がなくなったあとのスキャンは `ESRCH` です。Linux 7.0 はページを
      見つけません。
  - 大きなページはないので、`PAGE_IS_HUGE` のページはありません。
  - ガードやポイズンのマーカーのページを保護しても、書き込まれたままです。Linux は
    マーカーの uffd-wp ビットを立てます。
  - 2 MiB の区画は、そのページのどれかにエントリーかマーカーがあるあいだページ
    テーブルを持ちます。Linux はそれ以外のときもページテーブルを残します。これが
    効くのは、バッファーなしの `PM_SCAN_WP_MATCHING` だけです。それはページ
    テーブルのあるすべてのページを保護します。
  - 確かめるときのユーザー空間は、4 段のページテーブルと同じく 2^47 バイトで
    終わります。
- **`/proc/<pid>/clear_refs` の一部**：何かを変えるのは 4（soft-dirty）と 5（常駐の
  最大値）だけです。1、2、3 は受け付けますが、参照のビットを持たないので、`smaps` の
  `Referenced` は常駐の大きさのままです。Linux ではページにまた触れるまで減ります。
- **4 段のページングだけ**：エミュレートするマシンは、ホストの CPU にかかわらず常に 4 段の
  ページテーブルを持ちます。ユーザー空間は 2^47 バイト未満で終わり、`TASK_SIZE_MAX` を使う
  検査ではすべて 2^47 - 4096 です。`ptrace` の `PTRACE_POKEUSER`、`PTRACE_SETREGS`、
  `PTRACE_ARCH_PRCTL` が受け取る `fs` と `gs` のベース（`EIO`、`EPERM`）と、デバッグレジスタの
  ハードウェアブレークポイントの範囲（`EINVAL`）がそうです。5 段のページング（LA57）の CPU の Linux は、
  `mmap` のヒントでそこを求めたプロセスにだけ 2^47 より上をマップしますが、`TASK_SIZE_MAX` は
  2^56 - 4096 なので、これらの検査は、その間の値を受け付けます。paludarium はそれを
  拒みます（[設計判断](../design/decisions)）。
- **ほかの `/proc` の一部**：作るのは、プロセスのディレクトリといくつかのシステムの
  ファイルだけです（[機能](./features) を参照）。ほかのシステムのファイル（`/proc/cpuinfo`、`/proc/net` とプロセスの `net`、
  `/proc/sys` のファイルのうち、`fs`、`kernel`、`net` にあるものと `vm/drop_caches`、
  `vm/unprivileged_userfaultfd` 以外など）と、
  読むプロセス自身のディレクトリのほかの名前
  （`stack`、`sched` など）は、ふつうのパスと同じように探すので、`--mount /:/` ではホストの
  `/proc` に届きます。ほかのプロセスのディレクトリでは、それらは `ENOENT` です。Linux は
  root に `stack` なども見せます。`wchan` は、待っているタスクでも `0` です。Linux は、タスクを
  読める読み手には待っているカーネルの関数の名前を見せますが、ここには名前を付けるカーネルの
  関数がありません。`hostname` と `domainname` をいくつか見張る epoll 自身のポーリングは、
  用意のできたものが 1 つ見つかるまで、記述子の番号の順に見ます。Linux は変わった順に見るので、
  いくつか変わっていると、見たことになるものが違うことがあります。`io` は、Linux の `kernel_read` と `kernel_write` が
  そのプロセスに数えるもの（`execve` がプログラムとインタープリターを読むこと、コアダンプの
  書き込み）を数えません。また、Linux がファイルの操作の前でも中でも返す errno
  （`EINVAL`、`EFAULT`。eventfd に小さすぎるバッファを渡したときなど）で失敗した読み書きは、
  前で断られたものとして数えません。
  `/proc/stat` は CPU 時間をすべて、`getrusage` と同じくユーザー時間として数えます。スレッドの時間は、システムコールのときにいた CPU（そのあとほかのスレッドの `sched_setaffinity` が
  移したなら、その CPU）の分になり、
  アイドルの時間は数えません。割り込みと softirq は数えず、コンテキストスイッチとして数えるのは
  スレッドが眠った回数だけです。ゲストのスレッドを横取りするものがないためです。そのため
  `status` は、それを `voluntary_ctxt_switches` として示し、`nonvoluntary_ctxt_switches` は
  0 です。`getrusage` と wait の rusage も同じく `ru_nvcsw` に示し、`ru_nivcsw` は 0 です。ほかのプロセスのスレッドは、どの待ちでも
  `S (sleeping)` です。Linux は割り込めない待ちの一部を `D (disk sleep)` と見せます。スレッドが
  ほかのプロセスに見せるのは最後のシステムコールかシグナルの確認で公開したものなので、
  呼び出しの間だけ変えたマスク（`rt_sigsuspend`、`ppoll`）は、スレッドがその中で停止している
  間しか見えません。メモリーの残っていないタスク（ゾンビや、ほかのスレッドより先に
  終わったリーダー）は、ディレクトリー以外のファイルが root のものになるので、root で
  ない読み手には `environ`、`auxv`、`pagemap` が `EACCES` です。これは差分テストが比べる
  x86-64 の CI ランナーのカーネルに合わせたもので、Linux 7.2 のコミット 6b1c66c9
  （"exec_state: relocate dumpable information"）より前の動きです。7.2 からは
  `task_dump_owner` が、メモリーより長く残る `exec_state` の dumpable フラグから持ち主を
  決めるので、これらのファイルはタスクのもののままで、開くと `ESRCH` です。ランナーが
  7.2 以降になったら paludarium もそれに合わせ、`gone-leader-files` のケースと単体テスト
  `a_task_without_memory_has_its_files_owned_by_root` もそのとき変わります。
  `meminfo` は `sysinfo` と同じ固定の 4 GiB を、何も使っていないものとして返します。
- **自分のルートの一部**：生成される `/proc` や `/dev`（またはその中のディレクトリ）への
  `chroot` は `EINVAL` を返します。Linux はそこをルートにします。`mount` は `proc`
  ファイルシステムをマウントせず、`/proc` や `/dev` に何もマウントしないため、新しいルートの
  `/proc` や `/dev` に生成されるファイルが見えるのは、先に `/proc` や `/dev`（またはその中の
  ディレクトリ）をそこへバインドマウントしたときだけです。書かれたままでルートより上へ
  登るパスでは、`..` を書かれた名前から取ります。Linux は、シンボリックリンクのあとの `..` をリンク先から取ります。`/proc`
  の `maps` と `smaps` は、開いたプロセスが開いたときに持っていたルートからファイルを
  名付けます。Linux は、読むたびに読み手のルートから名付けます。Linux master で新しく
  入った `fchroot` はありません（`ENOSYS`）。
- **`/dev` と `/proc` の中を指すリンク（一部）**：ほかの場所からその中を指す
  シンボリックリンクを生成されるファイルまでたどるのは、パスをたどる呼び出しです。
  `execve` と、それを通して名前を作ったり消したりする呼び出し（`mkdir`、`mknod`、
  `unlink`、`rename` など）はたどらずに `ENOENT` になり、独自のルートの下ではたどりません。
- **生成されるファイルの変更（一部）**：`/dev` とそのデバイスやリンク、`/proc`、`/proc` の
  システム全体のファイルは root のもので、新しいモードや所有者を与えられるのは root だけ
  ですが、それは `EPERM` になります。Linux はそれを保ちます。疑似端末のスレーブは自分の
  モードと所有者を保ちます。生成されるファイルに設定した時刻も保たず、`stat` はもとの時刻を
  返します。
- **デバイスのノードとホストの FIFO**：ゲストは root で動きますが、キャラクターデバイスと
  ブロックデバイスの `mknod` は `EPERM` です。paludarium には、それが表すデバイスがないから
  です。マウントしたホストのディレクトリに FIFO を作れるのは Linux のホストだけで、つながる
  のはゲストの中で開いたものだけです。同じノードを開いたホストのプログラムにはつながりません。
- **`O_DIRECT` のアラインメント**：`O_DIRECT` で開いたファイルの読み書きも、ほかと同じように
  通ります。ext4 などのディスクのファイルシステムでは、Linux はブロックの大きさに揃っていない
  バッファー、オフセット、長さを拒みます（`EINVAL`）が、エミュレーターは拒みません。
- **ネットワーク**：許可の一覧（`--allow-net`、`Config::with_network`、ブラウザでは
  [中継](./relay) の要る JavaScript の `network` の指定）がなければ、
  `socket()` はどのファミリーにも `EAFNOSUPPORT` を返します。一覧があっても、使えるのは
  TCP のクライアント、ゲスト自身のソケットのための TCP と UDP のサーバー、名前解決だけです
  （[ネットワーク](./features#network)）。
  - ゲストがサーバーになれるのは、ループバックの上で自身のソケットに対してだけです
    （[ループバックのサーバー](./features#loopback-servers)）。ホストもほかのマシンも
    接続できず、`bind` が取るのはループバックのアドレスと未指定のアドレスだけです
    （ほかは `EADDRNOTAVAIL`。Linux ではマシンのどのアドレスも取れます）。
  - UDP のソケットが届くのは、DNS の代わりと、ループバックの上のゲスト自身のソケット
    だけです。ほかのアドレスへのデータグラムは `ENETUNREACH` です。ポリシーが許さない
    ほかの相手へ接続したソケットと、ホストの経路が見えない WebAssembly で接続した
    ソケットは、すべてのアドレスでポートを持ったままで、Linux は経路の送り元のアドレスで取ります。そのため `getsockname` は
    未指定のアドレスを返し、そのポートをループバックのアドレスで `bind` すると
    `EADDRINUSE` になります（Linux では `bind` できます）。
    IPv6 のマルチキャストのデータグラムはどこにも届かず、ブロードキャストのものも veth の端を
    通るもの（後述）のほかは届きません。データグラムには
    いつも届いた時刻を付けます。Linux がそうするのは、マシンのどこかのソケットが
    タイムスタンプを取っている間だけで、どれも取っていなければ、`SO_TIMESTAMP` などで
    読むときにその時刻を付けます。DNS の代わりの答えには、読んだ時刻を付けます。
    raw ソケットは `EPERM`、ICMP のソケットは
    `EACCES`、ほかの種類（Linux がモジュールを読み込んで作る SCTP の
    `SOCK_SEQPACKET` など）は `ESOCKTNOSUPPORT` です。
  - ホストからマウントしたディレクトリの下で AF_UNIX のソケットがパスに `bind` できるのは、
    Linux のホストだけで、そこにソケットファイルを作ります。root しかソケットファイルを
    作れない macOS と、Windows では、そこのパスへの `bind` は `EPERM` です。ゲストの
    ソケットどうしはそのファイルを通してつながりますが、ホストのプログラムのソケット
    ファイルはソケットを見つけず（`ECONNREFUSED`）、ホストのプログラムもゲストの
    ソケットには届きません。`/proc` のないホスト（chroot や最小限のコンテナ）では、
    ファイルのモードからホスト自身の umask の分も引かれます。ソケットファイルの書き込みの
    許可は、root と同じく確かめません。
  - DNS の代わりが答えるのは `A` と `AAAA` だけで、EDNS は読まないので、データグラムの
    答えは 512 バイトまでです。ホストが引けない名前は `SERVFAIL` です。53 番ポートへの
    TCP の接続は、いつも DNS の代わりに届き、本物の DNS サーバーには届きません。
  - ホストを通した接続が開く前の `getsockname` は、`bind` したアドレス、なければ
    未指定のアドレスとポート 0 を返します。Linux では取ったポートを返します。
    `bind` したポートはホストに届かず、ホストの接続は自分のポートから出ます。`SIOCOUTQ` は、相手がまだ受け取りを確かめていない分では
    なく、ホストがまだ送りに取っていない分を数えます。ホストを通すと、`SO_SNDBUF` と `SO_RCVBUF` は
    `getsockopt` のために覚えますが、バッファの大きさは変えません（どちらの向きも
    256 KiB です）。`TCP_NODELAY` 以外のオプションはホストのソケットに届きません。
  - TCP のバイトには、いつも届いた時刻を付けます。Linux がセグメントにそうするのは、
    マシンのどこかのソケットがタイムスタンプを取っている間だけで、どれも取っていなければ、
    そのとき届いたセグメントにはタイムスタンプがありません。読まれずに待っているバイトは
    みな最後に届いた時刻を取ります。Linux がセグメントを前のものにつなげるのは、
    前のものの断片が上限（`MAX_SKB_FRAGS`）に満たない間だけなので、前のセグメントを
    読むと前の時刻になることがあります。
  - ホストを通すと、`MSG_OOB` はそのバイトをふつうのバイトとして送り、緊急データを
    見つけず（`EINVAL`）、`SIGURG` も来ません。
  - ループバックで、緊急のバイトは相手に届いたときに `SIGURG` を 1 回送ります。Linux は、
    いっぱいのバッファの後ろで待っているときのように、バイトが 64 KiB より先にある間に
    届くセグメントごとに、もう 1 回ずつ送ります。送り手の `__tcp_transmit_skb` が各
    セグメントに、その先頭から 65535 バイト先を指す仮の緊急ポインタを付け、受け手の
    `tcp_check_urg` がそれを新しいものと見なすためです。それが何セグメントになるかは
    Linux 自身の分割と窓の更新しだいで、既定のバッファでは数十になります。
  - ループバックでゲストが設定した `SO_SNDBUF` と `SO_RCVBUF` は、接続のバッファを
    おおまかに決めるだけです（[ループバックのサーバー](./features#loopback-servers)）。
    Linux はセグメントごとの余分も数え、受信の窓も独自の刻みで決めるので、誰も読まない
    送り手が待つまでに入るバイト数は違います。設定しない側は 256 KiB で、Linux は接続を
    調整しながら（メガバイト単位まで）大きくします。
  - `tcp_info`（`TCP_INFO`、`INET_DIAG_INFO`）は、ループバックが運んだものを Linux と同じく
    数えたものを持ちます。状態、オプション、ウィンドウスケール、リスナーのキュー、送った
    バイト・確認応答を受けたバイト・受け取ったバイト・まだ送っていないバイト、そして
    Linux が始めに持つスロースタートのしきい値、輻輳ウィンドウ、経路 MTU、広告する MSS、
    リオーダリングです。Linux の TCP が測ったり調整したりするものは、いちばん単純な場合の
    ループバック接続の値です。往復時間（30 µs）とそこから決まるタイムアウトとレート、
    ペーシング、そしてウィンドウ（大きくならないので、送信の MSS は 32 KiB のままで、大きく
    なったウィンドウのための確認応答もありません）です。ハンドシェイクで示した
    ウィンドウスケールは変わりません。データが来てからの時間は
    読んだときから数えます。セグメントの数は、536 バイトまでの書き込みに読み手が追いついている
    間は Linux と同じです（[ネットワーク](./features#network)）。それより
    大きい書き込みやいっぱいのウィンドウでは Linux より多くも少なくもなり、veth のペアを
    またぐ接続はループバックの接続として数えます。待つのは数だけです。Linux では Nagle の
    アルゴリズムや `MSG_MORE`、損失が留めるデータも、ここではすぐに相手に届き、`SIOCOUTQ` と
    両側の準備状態もそのとおりに伝えます。ハンドシェイクの再送と、損失プローブが送り直す
    セグメントのほかに、再送も損失もありません。相手のウィンドウ
    スケールは、相手がどんなバッファーを設定しても Linux の既定値とします。ホストが張った
    接続のセグメントは、32 KiB ずつで確認応答がそれぞれ 1 つとして見積もります。
- **ファイルのマッピング**：ファイルのマッピングは Linux と同じくファイルのページ
  キャッシュを見せます（`MAP_PRIVATE` のものは、まだ書いていないページで）。ただし、
  `MAP_SHARED` のマッピングへの書き込みがホストのファイルに届くのは、ゲストが
  そのファイルを読むか `stat` したとき、`msync` か `fsync` を呼んだとき、ファイルの最後のマッピングがなくなった
  ときだけです（Linux は自分の都合で書き戻します）。また、ホストのほかのプログラムが
  ファイルを変えても、マッピングには届きません。Windows のホストでは、`O_APPEND` で
  開いたディスクリプタから作った共有マッピングへの書き込みは、ファイルに届きません。
  マッピングしたファイルの終わり（その先のページは `SIGBUS` になります）は、ゲスト自身の
  ファイルの操作で決まる大きさです。ホストのプログラムが大きさを変えても、終わりは
  動きません。
- **`write` で埋めたページ**：`write`（やほかのシステムコール）で埋めたホストの
  ファイルのページは、データがそのままホストのファイルに届くので、すぐにクリーンになります。
  そのページをマッピングすると、`smaps` はクリーンなページに数えます。Linux では
  書き戻されるまでページキャッシュでダーティーのままで、それまで `smaps` は
  ダーティーなページに数えます。
- **下に伸びるマッピング**：`RLIMIT_AS` は、`mmap` を止めないのと同じく、そうした
  マッピングが伸びること（[機能](./features#system-calls)）も止めません。
- **ページフォールトの数**：`ru_minflt` は Linux と同じく、フォールトを起きたときに
  数えます。スレッドの最初のシステムコールより前の、最初のフォールトから数えます。`execve` のローダーはプログラムのセグメントのページをファイルのバイトで
  埋め、そのときにページごとに一つフォールトを数えます。Linux はファイルをマップし、
  プログラムがはじめてページに触れたときにフォールトを数え、読み込みのフォールトでは
  いくつものページを一度に読み込みます（`fault_around_bytes`）。これらのフォールトは
  `perf` のイベントにしません。ファイルのページはすべて
  ページキャッシュにあるとみなすので、メジャーフォールトはありません（`ru_majflt` は 0）。
  `/proc/<pid>/stat` の `minflt` と
  `cminflt` も同じ数を読むので、同じ制限があります。
- **perf のイベントの一部**：数えるのはソフトウェアのイベントだけです。cgroup の切り替え、
  トレースポイント、ブレークポイント、kprobe、uprobe は `ENOENT` で、ハードウェアの
  イベントも、PMU のあるホストでも `ENOENT` です。スレッドのコンテキスト
  スイッチと CPU の移動は、最後のシステムコールで最後に記録したものです。CPU 時間は
  イベントを読むときに測り、ページフォルトは起きたときに数えます。
  CPU のイベントは経った時間を数え、フォルトもスイッチも移動も数えません。`SIGSEGV` や
  `SIGBUS` になるフォルトは、Linux は `page-faults` に数えますが、ここでは数えません。
  コンテキスト
  スイッチはスレッドが眠ることで、プリエンプションは数えません（`rseq` のスレッドが
  仮想 CPU をほかに譲るときは数えます）。`rseq` のないスレッドがほかの CPU へ移るのは、
  新しい CPU マスクで許す最も小さい CPU が変わったときだけです。サンプリングする
  イベントのサンプルは、Linux では起きるたびに取りますが、ここではスレッドがシステム
  コールに入るとき、またはエミュレーターのチェックポイントに来たときに、それまでの分を
  取ります。そのためサンプルの命令、レジスタ、スタック、フレームはそのときのもので
  （フォルトのアドレスはそのフォルトのものですが、スレッドの最後の 4096 より前のものは
  0 です）、カーネルのもの（システムコール中のフォルト、スイッチ、マイグレーション）は
  命令が 0 でカーネルのフレームがありません。`freq` はティックごと
  ではなく、そのときの速さに従います。`cpu-clock` と `task-clock` のイベントは、Linux の
  hrtimer のイベントと同じく、ティックの割り込みが `perf_event_max_sample_rate` を `HZ`
  （1000）で割った数になると抑えられ、次のティック、もう一度有効にされたとき、周期を
  設定されたときに抑えが解けます。ティックはイベント自身の数えた時間のものです。後の
  二つの `PERF_RECORD_UNTHROTTLE` は、次のサンプルとともに、数えるスレッドが書きます。
  止まるのは抑えられたイベントだけで、Linux はグループ全体を止めます。時間のかかりすぎる
  サンプルでサンプルレートを下げること（`perf_sample_event_took`。その上限を
  `perf_cpu_time_max_percent` が決めます）はしません。ほかのイベントは hrtimer や
  ハードウェアのものではないので抑えられません。CPU のイベントはサンプルもサイドバンドの記録も
  取りません。サイドバンドの記録では、`execve` はプログラムを読み込んでから、新しい
  マッピングをスタックの二つを先に、残りをアドレスの順に書きます。一時的なスタックの
  記録は、4 段のページテーブルのユーザー空間の頂上に、引数のページの長さで置きます。
  Linux はそれがあった場所を与えます。Linux は位置独立の
  プログラムやインタープリターの最初のセグメントを、切り詰める前にイメージ全体の
  長さで書きます。プログラムが触れて下へ伸びるスタックは何も書きません。マッピングの
  inode の世代は 0 です。エミュレーターがページキャッシュを持たないファイル（ホストのものや、
  起動時からのメモリー上のファイルシステムのもの）からは、ページがすべてキャッシュにある
  ものとしてビルド ID を読みます。Linux は読んでいないか追い出したページからは与えません。
  ホストが始められなかったスレッドには `FORK` と `EXIT` の記録を書き、
  `EXIT` は CPU 0 のものとします。Linux の失敗した `clone` はどちらも書きません。
  `NAMESPACES`、`CGROUP`、`KSYMBOL`、`BPF_EVENT`、`TEXT_POKE`、`SWITCH`、
  `AUX` の記録は書きません。そうしたときのオーバーフローは、
  `sigtrap` では SIGTRAP を一つ送ります。Linux はスレッドが自分のコードへ戻るたびに
  一つ送ります。その `si_addr` は最初のフォルトのものです。
  `REFRESH` の最後のオーバーフローがイベントを無効にするとき、数えるのはそこで止まりますが、
  その時間（時計のものを除きます）と、グループのほかのイベントは、そのときまで進みます。ユーザーページの数と
  時間は、`mmap`、イベントの有効化、リセットのときのもので、Linux はイベントが
  スケジュールされるたびに更新します。`cap_user_time` は設定しません。マッピングの
  確認と置き場所の確認の両方が失敗するときは、ここではマッピングの確認のエラーに
  なります。cgroup の
  モード（`PERF_FLAG_PID_CGROUP`）は `EBADF` です。ioctl の `SET_FILTER`、`SET_BPF`、
  `QUERY_BPF`、`MODIFY_ATTRIBUTES` は `ENOTTY` です。`remove_on_exec` は、
  Linux master が 7.2 から（037a3c43edfb）するように、イベントをグループから外し、そうした
  イベントは新しいグループを率いられません（`ENODEV`、fa091f46c383）。テストのマシンの
  Linux 7.0 はグループに残し、リーダーとしても受け付けるので、これらは単体テストだけで
  確かめています。`execve` を待つイベントと、それぞれのスレッドが開いたイベントは、
  エミュレートするマシンごとに置き、スレッドグループとスレッドで照合して、閉じたときに除きます。
  タスクが終わったイベントも、master と同じく新しいグループを率いられません（`ENODEV`）。
  テストのマシンの 7.0 は受け付けます。グループのメンバーは、どのソフトウェアのイベントでも、
  リーダーが数える間は数えます。Linux では、リーダーと別のソフトウェアの PMU のメンバー
  （`task-clock` のグループの `cpu-clock` のメンバー、その逆、どちらかと `dummy`）は、自分の
  PMU のコンテキスト（`find_get_pmu_context`）を持ち、それがリーダーのものとは別に
  スケジュールされるので、x86-64 のテストのマシンでは、リーダーの時間のうち実行ごとに変わる
  一部（なしからほぼすべてまで）だけ動きます。テストは一つの PMU のイベントだけを
  グループにします。Linux master の
  176 バイトの構造体の SIMD レジスタのフィールドは、master と同じく確かめますが、Linux とは
  比べていません。テストのマシンの Linux 7.0 は 144 バイトまでしか知らず、0 でないものには
  `E2BIG` を返します。`kernel.perf_event_paranoid` は
  最初 Linux の 2 です（Debian と Ubuntu のカーネルの既定はそれより大きい）。
- **BPF はマップと、AF_UNIX と UDP のソケットだけのソケットフィルター**：`bpf` が作るのは配列、
  ハッシュ、LRU ハッシュ、最長一致のトライ、キュー、スタック、ブルームフィルタ、マップの
  配列とマップのハッシュで、読み込むのはソケットフィルターだけです。ソケットフィルターは、
  `SO_ATTACH_BPF` でも古典的なものを `SO_ATTACH_FILTER` でアタッチしても、AF_UNIX の
  データグラムかパケットのソケット、UDP のソケット、TCP の待ち受けソケットに届く SYN で
  だけ動きます。ここの TCP の接続にはまだセグメントがないため、ハンドシェイクの最後の
  ACK にも、接続したソケットに届くデータ、ACK、FIN にも、フィルターはまだ動きません。Linux は
  それぞれにフィルターをかけます（`tcp_filter`）。それらを捨てたり削ったりするフィルター
  や、SYN を残してその ACK を捨てるフィルターは、Linux では違う結果になります。UDP のソケット
  では、ここではどのデバイスも通らない DNS スタブの答えにはフィルターは動きません。
  Linux が veth ペアにフラグメントに分けて送るデータグラムはひとまとまりで届きます。
  ただしフィルターが見る線形部分とチェックサムは、組み立て直したもののとおりです。IPv4
  の ID、IPv6 のフローラベルと `skb->hash` は Linux と同じく乱数ですが、Linux と同じ
  引き方ではありません。JIT はなく、インタープリタが動かします。ヘルパーの値は、プロセッサが
  0、ネットワーク名前空間のクッキーはどの名前空間でも 1（最初のもの）、起動時からの時計と
  粗い時計は単調時計、`CLOCK_TAI` は実時間です。検証器の書き換えは、命令の数を数えるだけで
  行いません。インタープリタは読み込んだままの命令を動かします。Linux の検証器は、決して
  通らない分岐をここの検証器より多く知っていて（下記）、そこからしか届かないコードを取り除きます。
  ここではそのコードも、そこで 64 ビットとして読むレジスタも、そこでの検索が引くマップも数えるので、
  そうしたコードのあるプログラムは、fdinfo のメモリ（`memlock`）もソケットへの課金も Linux と
  違うことがあります。ほかの
  プログラムの型は、それを組み込まずにビルドしたカーネルと同じく `EINVAL` です。検証器は、
  Linux が受け入れるかもしれない次のものを、自分の行（"paludarium: ... are not verified
  yet"、`EINVAL`。ヘルパーの呼び出しの行は "unknown func %s#%d" で始まり、libbpf と
  bpftool はそのヘルパーがないと判断します）で断ります。Linux がソケットフィルターに与える
  ヘルパーのうち [機能](./features) に挙げたもの以外（`bpf_tail_call`、
  `bpf_perf_event_output`、`bpf_trace_printk`、リングバッファ、スピンロックなど）、マップの
  マップ、キュー、スタック、ブルームフィルタのためのマップのヘルパー、検証器が値を知らない
  ヘルパーの大きさ、0 とわからないスカラーを渡す `bpf_get_netns_cookie`、kfunc、コンテキストの
  ソケット（`__sk_buff.sk`）とマップ自身のフィールド（`struct bpf_map`）、`fd_array` からの
  マップと `excl_prog_hash` を付けて作ったマップ、BTF ID と関数の `BPF_LD_IMM64`（そのため
  コールバックも）、`may_goto`、間接ジャンプ、オフセットの決まらないポインタ、条件ジャンプのある
  プログラムの
  `BPF_F_TEST_REG_INVARIANTS` です。後ろ向きの辺は Linux の行（"back-edge from insn %d to
  %d"）で断ります。Linux は特権のある読み込み手からの有限のループを受け入れます。再帰呼び出しは、
  master のように経路をたどる前に（"recursive call from %s() to %s()"、`EINVAL`）ではなく、
  テストのマシンの 7.0 と同じく、たどる経路が 9 フレームの深さになったところで断ります（"the
  call stack of 9 frames is too deep"、`E2BIG`）。差分テストはこの行をそのカーネルと比べるため
  で、そのカーネルに master の確かめ方が入ったら、ここでもそうします。スカラーは、
  検証器が知る値か、何もわからないかのどちらかで、Linux のように範囲を持ちません。そのため、
  Linux なら一方へだけ進むとわかるジャンプの両方をたどります。状態の刈り込みもしないので、
  分岐の多いプログラムは早く上限に届くことがあります。検索の結果は、64 ビットの `BPF_JEQ` か
  `BPF_JNE` で即値 0 と比べるまで null かもしれないものとして扱います。Linux は、定数のキーで
  引いた配列の要素があることや、二つのポインタの比較からもわかります。master とテストのマシンの Linux 7.0 の
  判断が違うところでは断ります。master は JIT ができればより大きなスタックを受け入れ、
  どの演算子をかけたポインタも数にし、巻き戻しのための exit を受け入れます。命令のフィールドの検査（"uses reserved fields" のエラー）は、master の順に、どの経路を辿るよりも前にします。Linux 7.0 は経路がその命令に届いたときに確かめるので、いくつも誤りのあるプログラムでは、別のエラーを先に出すことがあります。規則は特権のある読み込み手のものだけです（ポインタを
  漏らしてよく、書く前のスタックを読んでよく、Spectre への対策をしません）。そのため
  `CAP_PERFMON` のない読み込み手は、型がわかったところで `EPERM` になります。ここには BTF の
  オブジェクトも鍵もないので、関数と行の情報、CO-RE の再配置、`fd_array_cnt`、署名は
  断ります。ログには、Linux がレベル 1 と 2 で書く命令ごとと状態ごとのトレースも、master が
  エラーのあとに書く診断もありません。そのため長さ（`log_true_size`）は Linux より短く
  なります。ほかのプログラムのコマンド（`BPF_PROG_TEST_RUN` など）、BTF（`BPF_BTF_LOAD`）、
  link、アタッチ、プログラム、BTF、link の ID
  （`BPF_PROG_GET_NEXT_ID`、`BPF_PROG_GET_FD_BY_ID` など）、トークン、イテレータ、統計は、
  Linux にあってここにないコマンドとして `ENOSYS` です。Linux にコマンドのない番号は、Linux と
  同じく `EINVAL` です。`BPF_OBJ_PIN` がピンするのはマップだけで、プログラムの
  ディスクリプタは、オブジェクトでないものと同じく `EINVAL` です。BPF ファイルシステムの
  拡張属性は Linux master に従います。master には 7.2（9722955b5430）から `trusted.` と
  `security.` のものがあり、テストマシンの Linux 7.0 にはありません（そこではどの呼び出しも
  `EOPNOTSUPP` です）。そのためこれはユニットテストだけが確かめ、ランナーが 7.2 になれば
  差分テストのケースで比べられます。そのため libbpf の最小のプログラムでの確認はソケットフィルターを
  読み込み、ほかのプログラムの型は見つけません。`bpftool feature` はソケットフィルターと、
  検証器が確かめるヘルパーだけを見つけます。master の `BPF_COMMON_ATTRS`（ビット 16）を
  立てたコマンドも `EINVAL` です。試験機の Linux 7.0 にはこのフラグがないからです。master なら
  4 番目と 5 番目の引数から `struct bpf_common_attr` を読み、コマンドを実行します。ほかのマップの型は、それを組み込まずにビルドした
  カーネルと同じく `EINVAL` です。
  CPU ごとの型（`BPF_MAP_TYPE_PERCPU_ARRAY`、`PERCPU_HASH`、`LRU_PERCPU_HASH`）は、
  値が使いうる CPU ごとに一つあり、テストのマシンとエミュレータで CPU の数え方が違うので、
  どのみち Linux と比べられません。ハッシュはキーをバイトの順に返します。Linux の順は
  バケットとランダムなシードで決まります。そのバッチは要素一つずつをバケットとして扱うので、
  `in_batch` と `out_batch` は要素を数えます。LRU ハッシュは、どのコマンドも使う一つの CPU の
  リストを持ちます。Linux では CPU ごとにローカルなリストがあるので、一つのマップの更新が
  いくつもの CPU から来ると、いっぱいのときに手放すキーが違うことがあります（差分テストは
  一つの CPU に固定して動きます）。トライは、Linux の数え方と同じく要素が来るたびにメモリを
  取ります。ただ、Linux は作るときに CPU ごとのノードのキャッシュも埋めるので、値が
  メガバイト単位のトライは、Linux では `ENOMEM` になることがあり、ここではなりません。マップのメモリは、上流の Linux
  ではなく、テストのマシンのカーネル（Ubuntu の Linux 7.0）の構造体の大きさに従います。その
  `struct bpf_map` には、Ubuntu が Linux 7.2 から取り込んだ `u32 excl`（0fb6c9ed6493。7.3 で
  削除）があるので、配列のヘッダーは 312 バイトで、上流の v7.0 の 304 バイトより大きくなります。
  Linux master の配列のヘッダーも別のフィールドで 312 バイトですが、ハッシュのヘッダー
  （832 バイト）と要素は、ここの 896 バイトと 48 バイトより小さくなります。要素は書き込む
  までマシンから取らず、メモリの cgroup にも課金しません。`ENOMEM` になるのはマシンの
  4 GiB より大きいマップだけで、Linux は実際にあるメモリが尽きても `ENOMEM` を返すことが
  あります。事前に確保するハッシュは、ホストの CPU ごとに予備の要素を数えます。Linux が
  数えるのは使いうる CPU で、それより多いことがあります。確かめ方は、テストのマシンの
  Linux 7.0 と違うところでは
  Linux master に従います。キーと値が 4 MiB から 64 バイト引いた大きさ以上のハッシュは `E2BIG`
  です（7.0 は 4 MiB から 48 バイト引いた大きさまで受け付けます）。`BPF_F_RDONLY` と
  `BPF_F_WRONLY` の両方は、マップを作ったあとで断ります（7.0 は NUMA ノードと型より前に断るので、
  ここでは別のエラーが先に来ることがあります）。マップの ID はエミュレートする
  マシンのものなので、1 から始まり、ホストのマップは見えません。マップの SHA-256
  （`bpf_map_info.hash`）は `EINVAL` です。
- **仮想 CPU**：`rseq` を登録したスレッドは、ホストの CPU ではなく仮想 CPU で動きます。
  そのため、領域と `getcpu` が示す CPU は、ホストがそのスレッドを動かしている CPU では
  ありません。`/proc/<pid>/stat` は CPU 0 を示します。クリティカルセクションは、CPU が
  変わったときや、自分の CPU でほかのスレッドが動いたあとに中止されます。Linux でも割り込まれ
  うる場面です。ホストがスレッドをプリエンプトしても中止されませんが、それはほかの `rseq` の
  スレッドからは見えません。ほかのスレッドが設定した CPU マスクは、そのスレッドが次に止まった
  ときに効きます。システムコールの中のスレッドは CPU を持たないので、領域は最後に動いた CPU を
  示します。`rseq` のないスレッドは仮想 CPU では動かず、数にも入りません。タイムスライスの
  延長はありません。それなしでビルドした Linux と同じく、`RSEQ_FLAG_SLICE_EXT_DEFAULT_ON` は
  `EINVAL`、`rseq_slice_yield` は `ENOSYS` です。
- **保護キー**：仮想 CPU には保護キーがありません（`CPUID` は PKU を報告しません）。そのため
  `pkey_alloc` は、そういう CPU での Linux と同じく `ENOSPC` を返し、プログラムは保護キーなしで
  続けます。`RDPKRU` と `WRPKRU` は、そういう CPU と同じく `SIGILL` でプログラムを止めます。
- **セグメントレジスタの一部**：`lfs`、`lgs`、`lss`、`lar`、`lsl`、`verr`、`verw` は
  `SIGILL` でプログラムを止めます。CPU は 64 ビットモードでしか動かないので、互換モードの
  セグメント（`__USER32_CS` や、Linux が 64 ビットにしない `modify_ldt` のコードセグメント）
  への far の `jmp`、`call`、`ret` は、Linux ならそこで 32 ビットのコードを実行するところを、
  移る命令で `SIGILL` になります。`cs` がそれである `rt_sigreturn` のフレームは不正な
  フレームです。REX.W の付いた far の `jmp` と `call` は、Intel の CPU と同じく `m16:64` の
  ポインタを取ります。AMD の CPU は `m16:32` を読みます。
  `set_thread_area` は実装していないので、GDT のスレッドローカルのエントリは空のままで、CPU
  番号のセグメントのリミットは 0 です。`%ss` への `mov` や `pop` は、CPU と違い、次の命令の
  シングルステップのトラップを遅らせません。`modify_ldt` のあとに `%ds` と `%es` を読み込み
  直すのは呼んだスレッドだけで、Linux はアドレス空間のすべてのスレッドで読み込み直します。
  null のセレクタは `%fs` と `%gs` のベースを消しますが、Zen 2 より前の AMD の CPU は
  ベースを残します。
- **io_uring の一部**：実行するのは `IORING_OP_NOP`、`IORING_OP_EPOLL_CTL`、
  `IORING_OP_READ`、`_WRITE`、`_READV`、`_WRITEV`、`_FSYNC`、`_READ_FIXED`、`_WRITE_FIXED`、
  `IORING_OP_FILES_UPDATE`、`IORING_OP_PROVIDE_BUFFERS`、`_REMOVE_BUFFERS`、`IORING_OP_ASYNC_CANCEL` だけで、ほかの操作は `EOPNOTSUPP` で完了します。setup のフラグ `IORING_SETUP_IOPOLL`、`_SQPOLL`、
  `_SQ_AFF`、`_ATTACH_WQ`、`_R_DISABLED`、`_SQE128`、`_CQE32`、`_NO_MMAP`、
  `_REGISTERED_FD_ONLY` は `EINVAL` です。`io_uring_register` は `IORING_REGISTER_PROBE`、
  `IORING_REGISTER_BUFFERS`、`IORING_UNREGISTER_BUFFERS`、`IORING_REGISTER_BUFFERS2`、
  `IORING_REGISTER_BUFFERS_UPDATE`、`IORING_REGISTER_FILES`、
  `IORING_UNREGISTER_FILES`、`IORING_REGISTER_FILES_UPDATE`、
  `IORING_REGISTER_FILE_ALLOC_RANGE`、`IORING_REGISTER_FILES2`、
  `IORING_REGISTER_FILES_UPDATE2`、`IORING_REGISTER_PBUF_RING`、
  `IORING_UNREGISTER_PBUF_RING`、`IORING_REGISTER_PBUF_STATUS`、
  `IORING_REGISTER_SYNC_CANCEL`、`IORING_REGISTER_RING_FDS`、
  `IORING_UNREGISTER_RING_FDS` だけです（ほかは `EINVAL`）。そのため、
  パーソナリティは登録できません。`IORING_REGISTER_BUFFERS_UPDATE` は、差分テストを走らせる
  カーネルである Linux 7.0 と同じく、スロットごとに `iovec` をタグより先に読み、
  `IORING_RSRC_UPDATE_EXTENDED` を断ります。Linux master はタグを先に読み、そのフラグの
  `struct io_uring_regbuf_desc` を受け付けます。テストを走らせるカーネルが追いつけば master に
  合わせます。プロセス全体が
  終わると、そのスレッドが投入してファイルを待っている要求は、Linux master の
  `io_task_group_exiting` と同じく取り消されます。差分テストを走らせるカーネルである
  Linux 7.0 は、ひとりで終わるスレッドのときと同じく、ファイルの準備ができてから取り消します。
  登録したバッファーのヒュージページは 4 KiB のページごとに RLIMIT_MEMLOCK を数えます
  （Linux は 1 回だけ数えます）。リングは共有でしかマップできません（`MAP_PRIVATE` は `EINVAL`）。
  機能は Linux 6.12 のものなので、待ちの `min_wait_usec` は何も変えないのに
  `IORING_FEAT_MIN_TIMEOUT` を報告します。疑似端末の読み出しは、パイプの読み出しのように
  ファイルを待つのではなく、`io_uring_enter` の中で待ちます。
  読めないファイル（epoll のインスタンス、リング）は、Linux が先に準備を待つところで、すぐに
  `EINVAL` で失敗します。`IORING_ASYNC_CANCEL_OP` と `IORING_OP_LAST` 以降の操作を持つ
  `IORING_OP_ASYNC_CANCEL` は、差分テストを走らせるカーネルである Linux 7.0 と同じく要求を
  見つけません（`ENOENT`）。Linux master の `io_async_cancel_prep` は `EINVAL` で断ります。
  テストを走らせるカーネルが追いつけば master に合わせます。位置のないファイル（パイプ、ソケット、端末、eventfd）はポーリング
  できるものとみなし、それで読み出しがリングのバッファーを使う時点と、転送がそれを待つか
  どうかが決まります。プログラムのメモリにあるバッファーのリングは、登録したバッファーと違って
  固定しません。カーネルは使うたびにそのマッピングを通して読み書きするので、外したリングを読み
  出しが見つけると `EFAULT` で失敗します。Linux は固定したページを使います。
- **ネイティブ AIO の一部**：読み書きと同期は、Linux のバッファー付き I/O と同じく、
  どれも `io_submit` が取ったときに実行されます。`O_DIRECT` で開いたファイルのものも
  Linux のように裏では実行されず、同期のイベントは、Linux ではワーカーが少し後に入れるのに、
  呼び出しが戻るときにはリングにあります。どの呼び出しにもよらずに準備できたファイル
  （期限が来た timerfd、ホストからの入力）を待つ poll は、Linux ではすぐに完了するのに、
  どれかのプロセスの次の呼び出しか、呼び出しがファイルを待っているあいだか、動いている
  スレッドの次のチェックポイントで完了します。どのスレッドもファイルを待たない呼び出しで
  眠っているあいだは、どれかが起きたときに完了します。poll が
  2 つのキューで待つファイル（Linux は準備できていなければ `EINVAL` で断ります）は、
  ファイルの種類から推します。読み書き両方で開いた FIFO と、キャラクターデバイス（端末）です。
  リングが保てる要求はちょうどイベント数より 1 少なく、Linux では CPU ごとの数のために
  それより早く止まることがあります。`IOCB_FLAG_IOPRIO` の I/O 優先度は確かめるだけで何も
  変えません。
- **一部のシステムコール**：実装していないシステムコールは `ENOSYS` を返すので、
  プログラムによってはその機能なしで続けられます。
  - `pwritev2` の `RWF_NOAPPEND` は、Windows のホストでは `O_APPEND` のファイルの追記を
    止められないので、そこではそのようなファイルに `EOPNOTSUPP` を返します。
    通常のファイルの `RWF_NOWAIT` の読み込みで、ページがキャッシュにない（Linux の
    `EAGAIN`）ことはありません。macOS と Windows のホストでは、ホストのファイルはその
    ファイルシステムによらず ext4 と同じく `RWF_NOWAIT` と `RWF_DONTCACHE` を受け付けます。
    Linux のホストで見分けるのは ext4、xfs、btrfs、f2fs だけです（ほかのファイルシステムは
    どちらも断ります）。
  - `MADV_COLLAPSE` は、通常のファイルのマッピングを断ります（`EINVAL`）。Linux の
    その規則は v6.12 のあとで変わりました。v6.12 は、だれも書き込み用に開いていない
    ファイルだけをまとめ（`READ_ONLY_THP_FOR_FS`）、そのあとのカーネルは、large folio
    のあるファイルシステムのどのファイルもまとめます。結果はホストのページキャッシュ
    にもよります。まだ読み込まれていないページと、汚れたページです。汚れたページは
    一度書き戻され、そうでなければ `EAGAIN` です。まとめた区間は 512 個のふつうの
    ページのままなので、`/proc/<pid>/smaps` はそこに `AnonHugePages` も
    `ShmemPmdMapped` も示しません。プライベートな anonymous メモリの区間にページ
    テーブルがあるかは、そのページのどれかにエントリかマーカーがあるかで見ます。
    shmem では、まとめる VMA 自身の `userfaultfd` の登録だけを見ます。Linux は、
    どのプロセスでもファイルのどれかの VMA が欠けたページについて登録されていれば
    穴を断ります。sysfs の `shmem_enabled` は `deny` でないものとします。
    Linux は、空いた huge page がない（`ENOMEM`）か使用中のページがある（`EAGAIN`）
    ためにまとめられないこともありますが、ここでは起きません。
  - `CAP_SYS_ADMIN` があるとき、`MADV_HWPOISON` はファイルや共有メモリのページを断ります
    （`EIO`）。Linux はそれをページキャッシュで、すべてのマッピングとファイルに対して毒に
    します。`fork` が共有するページは呼んだ側のエントリだけを毒にしますが、Linux はすべての
    プロセスからマップを外します。ゼロページには毎回 `EBUSY` を返しますが、Linux は最初の
    ときにマシンのゼロページを毒のあるものとします。`CAP_SYS_ADMIN` があるときの振る舞いは、
    native ではホストのメモリに毒を入れてしまうので、どれも差分テストで確かめていません。
  - `process_madvise` は、呼んだプロセス自身のメモリには `madvise` が受け付ける指定しか
    受け付けず、ほかのプロセスの範囲は、`MADV_COLLAPSE` を除き、マップされているかを確かめる
    だけです。Linux が知らない指定は、Linux master と同じく範囲を見る前に断ります
    （`EINVAL`）。CI のカーネルは範囲ごとに確かめるので、範囲がないか空の範囲だけのときは
    0 を返します。
  - SIGKILL 以外の命取りのシグナルは、それをブロックしていない唯一のスレッドが、
    すでにシグナルを保留していて動いていないときや、終わりかけているときでも、送った
    時点で `process_mrelease` にとってプロセスを終わりかけにします。Linux の
    `wants_signal` はそのようなスレッドを選ばないので、スレッドのどれかがシグナルを
    受け取るまで印を付けません。
  - `fork` の子では、ローダーが書き込んだあと何も書き込んでいない、プログラム自身の
    ELF セグメントのページを、`move_pages` はそこにあるものとして示します。Linux は
    `anon_vma` のない VMA のページテーブルを子にコピーしないので、子が触れるまでは
    `-ENOENT` です。ここではローダーのコピーがそのページの唯一の内容だからです。
  - プログラムの ELF セグメントの中身は、`execve` でローダーが読んだバイトです。
    プログラム自身のファイルは動いているあいだ書き込めません（`ETXTBSY`）が、Linux は
    インタープリターのファイルを読み込み後に書き込めるように戻します。そのあとそのファイルに
    書き込んでも、まだ何も書き込んでいないセグメントのページには見えません。`execve` の
    時点でファイルの終わりより後ろだったページは、ファイルが伸びても `SIGBUS` のままです。
    Linux はどちらもページキャッシュからマップします。
  - `memfd_secret` のページのフォールトは、フォールトしたプロセスの最後のシステムコールの
    ときの `RLIMIT_MEMLOCK` で決めます（システムコールの前は、作ったプロセスのものです）。
    数えるのは `memfd_secret` のファイルのページと `io_uring` の登録したバッファーだけです。
    Linux のユーザーの `locked_vm` は、`perf` のバッファなども数えます。ページをフォールトのときに数える変更
    （97d34aa65c29「mm/secretmem: properly account locked pages」）のないカーネルは、
    代わりにマッピングをロックしたものとして数えます。上限を超えると `mmap` が `EAGAIN` で、
    そのマッピングの `MS_INVALIDATE` の `msync` は `EBUSY` です。ここでは、変更のある
    カーネルと同じく成功します。
  - CPU 時間のインターバルタイマー（`ITIMER_VIRTUAL` と `ITIMER_PROF`）と `RLIMIT_CPU` は、
    どれもプロセスの CPU 時間のすべてを数えます。ここではそのすべてがユーザーの時間だからです
    （Linux の `ITIMER_VIRTUAL` はシステムの時間を数えず、`RLIMIT_CPU` は数えます）。WebAssembly のように
    ホストがスレッドの CPU 時間を測れないところでは、それは経過時間なので、スレッドが
    眠ったり待ったりした時間も、起きたときにまとめて数えます。タイマーを確かめるのは、
    Linux のようにティックごとではなく、スレッドがシステムコールをするときと、命令を
    100,000 個実行するごとです。ティックは CI ランナーの `CONFIG_HZ` に合わせて 1 ms と
    します。CPU 時間の時計の POSIX タイマーも、同じように数えて確かめます。プロセスの
    CPU 時計での眠りも同じで、眠っているスレッドがティックごとに確かめます。それが経過時間の
    ところでは眠っている時間も数えるので、ほかにスレッドのないプロセスでも、頼んだ時間が
    経てば眠りが終わります。ほかのプロセスの CPU 時間でのタイマーも、そのプロセスの
    スレッドがシステムコールをするときなどに、同じように確かめます。プロセスの CPU 時間は、
    自分のスレッドが読んだり設定したりするときも外からのときも、動いている各スレッドのその
    時点の値です。Linux では、呼び出したスレッドのほかは最後のティックの時点の値で、CI
    ランナーでは多くて 1 ms 前です（スレッド自身の時計は Linux でもその場の値です）。そのため
    その分だけ Linux より進んでいることがあります。スレッドの CPU 時間の細かさは、ホストが
    ほかのスレッドの時間を示す細かさで、Linux では 1 ns、macOS では 1 µs、Windows では
    スケジューラのティック（約 15.6 ms）です。
  - 時刻は設定できません。`settimeofday`、`clock_settime`、何かを変える `adjtimex` と
    `clock_adjtime` は、`CAP_SYS_TIME` を持つ呼び出し元にも `EPERM` を返します。Linux は時計、
    タイムゾーン、NTP の状態を設定します。そのため NTP の状態は読むだけです。ネイティブの
    Linux ではホストのもので、それ以外では Linux が起動したときのままです。ホストの状態は
    呼び出しのたびに読むので、その間にホストの時刻デーモンが変えれば（たとえば chrony は
    ティックを数マイクロ秒動かします）、二つの読み取りは異なります。そのためネイティブでの
    実行との比較は、ホストが状態を変えない間だけ一致します。ホストのサンドボックスがその読み取りも
    拒む場合（`CAP_SYS_TIME` のない Docker の既定の seccomp プロファイル）、ネイティブの
    `adjtimex` は `EPERM` を返しますが、ここでは Linux が起動したときの状態を読みます。負の時計 ID で表す CPU 時計での `clock_settime` は、時刻を読まずに `EINVAL` を
    返します。Linux は時刻を読み、タスクを探して `EPERM` を返します。補助の時計
    （`CLOCK_AUX`）もありません。
  - ホストの I/O ポートは使えません。レベル 0 を超える `iopl` と、ポートを使えるようにする
    `ioperm` は、`CAP_SYS_RAWIO` を持つ呼び出し元にも、ポートへのアクセスをロックダウンした

  外れます。外したマウントの開いたファイルは使えますが、その中の作業ディレクトリや
  ディスクリプタはパスで使うので、もうそこにはたどり着きません。マウント ID は 21 からの
  空いているいちばん小さいもので、ルートの親は 1 と表示します。バインドマウントは
  ソースをパスで持つので、ほかの名前空間での名前の変更では古いパスのままで、ソースを
  消すと何も見えなくなります。Linux は消えた
  ディレクトリを持ち続け、mountinfo に `//deleted` と付けます。ディスクリプタのマウント
  ID（`AT_EMPTY_PATH` 付きの `statx`、fdinfo）は、それを開いたパスから求めます。
  fanotify のマウントへのマーク（`FAN_MARK_MOUNT`）にとってのディスクリプタのイベントの
  マウントも同じです。そのパスがもうそのファイルのファイルシステムに届かない（その後に
  名前が変わった、置き換わった）とき、イベントはそのファイルシステムの最初のマウントの
  ものになります。
- **Landlock**：ABI バージョン 8 までです。記録のフラグは受け付けますが、何も記録しません。
  `LANDLOCK_RESTRICT_SELF_TSYNC` では、ほかのスレッドが自分の確認に新しいドメインを
  使うのは、次にカーネルに入るときからです。Linux は、すべてのスレッドが受け取るまで
  待ちます。それらのスレッドへのシグナルにはすぐに効き、`/proc` にはそれぞれの次の
  システムコールの後から見えます。`F_SETOWN` は送り手を記録しないので、`F_SETOWN` に
  よる `SIGIO` と `SIGURG` はスコープの対象になりません。名前の変更での Landlock の
  確認は許可の確認の後で、Linux は前です。違いが出るのは両方が断るときだけです。
  `/proc` の下のファイルへのルールは、`execve` には効きません。開くときは、パスが
  指すファイルを開く前に確かめ（作ったファイルは作った後に確かめ）ます。その間に別の
  スレッドが名前を変えると、確かめたファイルと開いたファイルが違うことがあります。
- **seccomp**：`SECCOMP_FILTER_FLAG_WAIT_KILLABLE_RECV` でリスナーの答えを待ち
  続ける呼び出しは、致命的なシグナルで起きるのではなく、10 ミリ秒ごとにそれを
  確かめます。何も記録しません
  （`SECCOMP_FILTER_FLAG_LOG`、`SECCOMP_RET_LOG`）。strict モードでも、Linux の
  `TIF_NOTSC` のように `rdtsc` を例外にはしません。`SECCOMP_FILTER_FLAG_TSYNC` の
  後、ほかのスレッドの新しいフィルターが `/proc` に見えるのは、そのスレッドの次の
  システムコールの後からです。
- **資格情報**：スレッドが変えた ID とケーパビリティは、ファイル、シグナル、資源の上限、
  優先度、ソケットの資格情報、コアファイルでは確かめますが、ほかのところではまだ
  確かめていません。
  `F_SETOWN` は設定した側の資格情報を記録しないので、
  `SIGIO` と `SIGURG` は、Linux の `sigio_perm` と違い、だれが設定しても持ち主に届きます。
  `PR_SET_PDEATHSIG` のシグナルは、親プロセスが終わったときにそのリーダーの ID で送りますが、
  Linux は子を作ったスレッドが終わったときにそのスレッドの ID で送ります。
  ファイルのうち、`/proc` と `/dev` の下は確かめません。`fs.protected_hardlinks`、
  `fs.protected_symlinks`、`fs.protected_fifos`、`fs.protected_regular` は、
  カーネルの既定値の 0 として振る舞います。多くのディストリビューションは
  これらを上げています。set-user-ID や
  set-group-ID のプログラムは持ち主やグループになり、ファイルケーパビリティの
  あるプログラムはそれを得ます。ほかのプロセスが呼んだ側と作業ディレクトリを
  共有していても（`CLONE_FS`）同じです。Linux なら `CAP_SETUID` がなければ実 ID を
  実効 ID にし、ケーパビリティも呼んだ側が持っていた以上には与えません。
  `execveat` の `AT_EXECVE_CHECK`（Linux 6.14）は `EINVAL` です。これはユーザー空間が
  `SECBIT_EXEC_RESTRICT_FILE` のもとでファイルを実行する前に確かめるためのものです。
  その確かめのための securebits は保って示しますが、ここでは何もそれに従いません。
- **ソケットのメッセージ**：`sendmsg` と `recvmsg` は、Linux と同じように
  `SCM_RIGHTS` でディスクリプタを、`SCM_CREDENTIALS` で資格情報を受け渡します。
  違いは次のとおりです。
  - 読まれていないメッセージだけが持っているソケットは、ほかのソケットがなくなると
    すぐに閉じられます。Linux のガベージコレクタは、ワークキューから少しあとに
    閉じます。
- **ソケットのオプション**：`setsockopt` は、効き目を再現していないオプションを
  `ENOPROTOOPT` で断ります。Linux は受け付けます。AF_UNIX とインターネット以外の
  ソケットのフィルターなど、Linux にあるほかのオプションです。セキュリティモジュールは再現していないので、`SO_PASSSEC` は
  `SCM_SECURITY` を運ばず、`SO_PEERSEC` は `ENOPROTOOPT` です。モジュールのない
  Linux と同じです。SELinux のある Linux は送り手や相手のコンテキストを渡し、
  AppArmor のある Linux は `SO_PEERSEC` で相手のラベルを渡します。
  `SO_RCVTIMEO` と `SO_SNDTIMEO` は 1000 Hz の刻みに丸めます。
  Linux は自分の `CONFIG_HZ` に丸めます。
  ここではケーパビリティを確かめないので、`CAP_NET_ADMIN` の要るオプション
  （`SO_DEBUG`、`SO_SNDBUFFORCE` など）も root と同じく設定できます。
- **シグナル駆動の入出力**：ホストの標準入力は 10 ms ごとに見るので、何もなかったところに
  入力が来るたびに `SIGIO` を 1 回送ります。Linux のパイプや端末は、入力のひとまとまりごとに
  送ります。標準出力と標準エラーも同じように見て、いっぱいだったところに空きができる
  たびに 1 回送ります。Linux のパイプは、読み手が読むたびに書き手へ送ります。見るための
  10 ms より短い間だけ満杯や空だったストリームは見逃され、送らないことがあります。ただし、
  読み書きがゲストに `EAGAIN` を返したあとは必ず送ります。スレッドがない WebAssembly では
  送りません。
- **signalfd へのエッジトリガーの `epoll`**：プロセスのほかのスレッドに積まれた
  シグナルのエッジは、そのスレッドがシグナルを取り込んだとき（次のシステムコールか、
  待っている間なら 10 ms 以内）に来ます。Linux の `signalfd_notify` は送られたときに
  ファイルを起こすので、待たない `epoll_wait` はそれより先に呼ばれることがあります。
- **userfaultfd の一部**：登録するのは、ないページと、書き込み保護と、shmem の
  マイナーフォールトです。捨てる操作は、どのページを
  落とすより先にすべての範囲を知らせます。Linux は VMA ごとに知らせて落とします。
  1 つの `userfaultfd` の登録したマッピングが接していれば、Linux の VMA が
  つながったときと同じく、`UFFD_EVENT_REMOVE` の 1 つの範囲になります。
  `MADV_REMOVE` は、最初のマッピングが確かめを通れば範囲全体を一度知らせます。書き込み保護のモードをほかのモードに置き換える登録は、範囲の
  ページの保護を外します。Linux はその印を PTE に残します。shmem の uffd-wp
  マーカーの上の `MADV_GUARD_INSTALL` は、マーカーをガードに置き換えます。Linux は
  エントリーを外すとき（zap）にマーカーを残すので、シグナルが来るまで呼び出しをやり直します。shmem のファイルで登録
  するのは memfd と tmpfs マウント（ゲストがマウントしたものか `/dev/shm`）のファイル
  です（`UFFD_FEATURE_WP_ASYNC` で書き込み保護だけなら、どのファイルも登録します）。
  起動したときからあるメモリ上のファイルシステムのファイル（`/tmp` を含みます）は、
  tmpfs を名乗りますが、ゲストがディスクに持つファイルを表すので断ります（`EINVAL`）。
  ホストの tmpfs のファイルはここで持っていません。shmem のファイルの
  プライベートなマッピングに `UFFDIO_ZEROPAGE` が入れるゼロページは、そのマッピング
  自身のゼロのページで、`/proc/<pid>/pagemap` と `smaps` もそう数えます。Linux は
  そのゼロページを対応付けます。`UFFDIO_MOVE` の
  動かし元の穴は、ここでその周りの 2 MiB にどれも触れていなければ、Linux にそこの
  ページテーブルがないときと同じく、動かし先を見る前に `ENOENT` です。Linux は
  ページテーブルをほかのときに解放したり残したりもします。
- **dnotify の一部**：`/proc/sys/fs/dir-notify-enable` はないので、Linux の既定の 1 と
  同じく、dnotify はいつも使えます。
- **`/proc/locks` の一部**：ロックを待つものの行（`-> `）はありません。PID は読む側の PID
  名前空間のものです（Linux では `/proc` をマウントした名前空間のもの）。ホストのプログラムが
  ホストのファイルに掛けた `flock` のロックは、ゲストのロックとぶつかりますが、並びません。
- **ファイルのリースの一部**：`execve` がプログラム、そのインタープリター、スクリプトを開くときと、
  fanotify のイベントが渡すディスクリプターを開くときは、Linux と違ってリースを破りません。
  リースは `FAN_OPEN_PERM` を尋ねる前に破ります（Linux では尋ねた後）。`truncate` では
  Landlock の検査の後に破ります（Linux では前）。
  委任（`F_GETDELEG` と `F_SETDELEG`）は `EINVAL` です。
- **fanotify の一部**：`FAN_PRE_ACCESS` は
  `EOPNOTSUPP` です（ここのファイルシステムはどれも認めません）。`FAN_FS_ERROR` は
  来ません。ここにはエラーを知らせるファイルシステムがないためです。Linux では ext4 が
  知らせ、7.0 からは `fserror_report` を通して XFS、Btrfs、F2FS、iomap の I/O、fsverity
  も知らせます。Linux の tmpfs と procfs は知らせません。
  ディレクトリへの追い出せるマークは追い出しません。Linux では、ディレクトリの
  子の dentry がどれも使われていなければなくなります。Linux ならまだ書き戻すファイルや、
  マウントが載っているファイルへのものは、それでも追い出します。開くことは、開く前に自分で
  調べたときに見つけたファイルを保ちます。そのため、開くまでにパスが別のファイルを指して
  いれば、その別のファイルのマークはその間になくなることがあります。Linux では、検索と開く
  ことが同じファイルを見ます。グループのマージ用ハッシュで
  どのイベントが同じバケットに入るかは、Linux がカーネルのアドレス（プロセスと、FID でない
  モードのパス）を混ぜるところをエミュレーター独自のハッシュで決めます。そのため、Linux と
  同じく衝突するのは、1 つのタスクが 1 つのディレクトリで出す名前のイベントだけです。ディレクトリが子を見ているかは fanotify の
  マークだけで決めます。Linux は inotify のものも数えます。ディスクリプタが持っていない
  ファイル（exec が動かすプログラム）は、そのときのパスで開き直すので、なくなっていれば
  開けません。
- **inotify の一部**：スーパーブロックが消えるとき、そのファイルのウォッチは Linux と同じく、
  ファイルがどれかのグループの最初のマークを得た順に `IN_UNMOUNT` を受け取ります。ただし、
  1 回だけの dnotify のウォッチがシグナルの後にディレクトリへ残すマークは、ディスクリプタの
  テーブルが終わるとき、ウォッチを求めたファイルを通してだけ消えます。Linux はそのディレクトリの
  どのディスクリプタを通しても消えるので、ディレクトリがその順での位置を長く保つことが
  あります。`/proc/self/fdinfo` では、epoll のファイルはディスクリプタの順に並びます。Linux はファイルのアドレスの
  順です。eventfd の番号はエミュレータの中で数えます。Linux の `eventfd-id` はシステム
  全体で数えます。マウントしたディレクトリにホストが加えた変更は見えず、ディスクリプタの
  場所もそれを追いません。
- **名前空間**：ユーザーの名前空間には `projid_map` も `user.max_*` の上限もありません。
  その対応表のファイルは、書き込みを開いたときの資格情報で確かめます。Linux は、親で要る
  `CAP_SETUID` と `CAP_SETGID` には書き手の資格情報も見ます。ダンプできないプロセスの
  `/proc` のファイルは最初の名前空間のルートのものです。Linux では、そのプロセスの
  名前空間がルートを対応させていればそのルートのものです。ネットワーク名前空間には、ループバックと、要求が作る veth の端のほかにインターフェースが
  ありません。veth の端は IPv4 のアドレスと経路を持ち、TCP と UDP は組を通って相手の
  名前空間のアドレスへ届きます。IPv6 のアドレスも持ち、リンクローカルのアドレスと
  その経路も作り、要求が足す IPv6 の経路（IPv4 と同じくゲートウェイのあるものも）、
  IPv6 の TCP と UDP、その近隣も受け取りますが、代理のエントリは `EOPNOTSUPP` です。
  IPv6 のゲートウェイの近隣の状態は、Linux の `rt6_check_neigh` が同じメトリックの
  経路の間でするようには引き当てを左右しません。IPv6 のマルチパスの経路のネクストホップのうち、
  求められたデバイスを通るものは、Linux 7.0 と同じくフローのハッシュで一つを選びます。
  Linux master は、引き当てたネクストホップを使います（`ip6_pol_route` の `have_oif_match`）。
  IPv6 のパケットの答えは、パケットが出た端を通ってだけ返るので、マルチパスの経路が別の端から
  返す答えは失われます（Linux では届きます）。
  経路のない UDP の connect は、Linux master が "ipv6: fix device binding after failed
  datagram connect" からするように、ソケットのデバイスを元に戻します。その修正のない
  CI のカーネルでは、スコープ ID が与えたデバイスが残ります。
  `lo` に結び付いた IPv4 のソケットが、`lo` を通る経路のないアドレスへ送ると `ENETUNREACH`
  です。Linux はリンク上にあるものとして送り、捨てます。近隣探索は、ルーター要請、MLD の報告、重複アドレス検出が送るグループ
  （`ff02::2`、`ff02::16`、要請ノードのもの）の近隣を作らず、求められない広告も
  リダイレクトも送りません。遅延中の近隣が送る問い合わせは相手に何も教えません。
  Linux では端のリンクローカルのアドレスから送り、相手にそのアドレスの近隣を作ります。
  重複アドレス検出は問い合わせを送らず、重複も見つけず、始まって
  から 1.5 秒で終わります（`rtr_solicit_delay` の半分の後、問い合わせ 1 回と再送の
  時間）。Linux では
  ランダムな遅れの後、1 から 2 秒で終わります。リンクローカルのアドレスはいつも
  Ethernet のアドレスから作り（EUI-64、`addr_gen_mode` 0）、IPv6 はルーター要請も
  MLD の報告も送りません。端を通る通信は
  カウンタを動かしません。名前空間は別の名前空間へ転送せず、ソケットが IPv6 のグループに
  加わらないので（`IPV6_ADD_MEMBERSHIP`）、端を通る IPv6 のマルチキャストの宛先には何も
  届きません。IPv4 のグループはゲストの名前空間の中だけのものです。最初の名前空間には
  ホストのネットワークへのデバイスがなく、グループへの経路もないので、デバイスを指さずに
  入ろうとすると `ENODEV` です。IGMP と MLD のパケットは送りません。raw ソケットは `EPERM` で、パケット
  ソケット（`AF_PACKET`）もないので、ゲストからは見えないものです。送り元のフィルター
  （`IP_ADD_SOURCE_MEMBERSHIP`、`IP_MSFILTER`、`MCAST_*`）は `ENOPROTOOPT` です。ICMP の port unreachable の頻度を
  抑えないので（`icmpv4_xrlim_allow`、`icmpv6_xrlim_allow`）、相手の閉じたポートへのデータグラムのたびに、
  接続したソケットの次の送信は `ECONNREFUSED` になります。組を通る接続は、端が
  落ちても、消えても、移っても、使っていたアドレスや経路が消えても続きます。Linux では
  パケットが止まります。ARP にも近隣探索にも誰も答えないアドレスへの接続は、connect
  ごとに 3 秒後に失敗します。Linux では、近隣を解決している間の試みは一緒に失敗します。
  端の近隣に答えがあるかどうかは、解決を始めるときか遅延中になるときに相手が答えるか
  どうかで決まります。Linux は問い合わせのたびに改めて問います。そのため、近隣を待つ
  パケットは、後から答えがあっても送られません。`NTF_MANAGED` のものを改めて探査する
  こともありません。通信は近隣を確認しないので（`dst_confirm`、`MSG_CONFIRM`）、
  遅延中のものはいつも探査します。消える端のアドレスは、寿命を、その名前空間での最後の netlink の
  要求、読み出し、poll のときのもので伝えます。Linux は消えるときのもので伝えます。
  作るときに取るのはそれぞれの端の名前、アドレス、MTU
  だけで（ほかの属性は `EOPNOTSUPP`）、`ifinfomsg` のフラグは取りません。変えるときに
  取るのは `IFF_UP` と名前空間だけです。アドレスを指さなかった veth の端のアドレスは、
  カーネルの乱数ではなく emulator 自身の列から取ります。リンクの監視はすぐに働きます。
  Linux では 1 秒遅れることがあります。そのため動作状態は、伝えるときに決まります。送受信のキューはそれぞれ 1 つで、Linux では
  ありうる CPU ごとに 1 つです。`IFLA_AF_SPEC` はなく、統計は 0 です。インターフェースの
  リクエストと netlink は `IFF_UP` のほかのフラグを変えません。最初の名前空間でも `lo` しか見えません。
  Linux ではホストのインターフェースが見えます。
  netlink には `NETLINK_ROUTE`、`NETLINK_SOCK_DIAG`、`NETLINK_GENERIC` しかありません
  （ほかは `EPROTONOSUPPORT`）。ソケット診断が伝えるのは AF_UNIX、TCP、UDP のソケット
  だけです。AF_NETLINK と AF_PACKET にはハンドラーがなく（`ENOENT`）、Linux がモジュール
  として読み込む raw ソケット、SCTP、MPTCP のハンドラーもありません。`SOCK_DESTROY` は
  `EOPNOTSUPP` です。ダンプは古いソケットから順に挙げます。Linux の順はハッシュ表に
  従います。AF_UNIX のソケットが送って待っているものは、ここで送信バッファーに数える量で
  数えます。Linux はバッファーの本当の大きさで数えます。TCP のソケットについては、
  メモリはバッファーのほかを 0 と伝えます。キープアライブのタイマーは今から `TCP_KEEPIDLE` まるごとで終わるとし、再送の
  時刻と回数があるのはループバックのハンドシェイクだけです。ホストが張った接続には、
  終わったあとの `TIME_WAIT` がありません。送るバイトがまだ残る閉じたソケットは
  `FIN_WAIT1` の保持として見えます。Linux ではソケットそのものが残ります。どのソケットの
  cgroup もルートの 1 で、トラフィッククラスは 0 です。BPF のマップを指すリクエスト
  （`INET_DIAG_REQ_SK_BPF_STORAGES`）は、ここにはマップの記述子がないので `EINVAL` です。
  Linux では、開いていない記述子なら `EBADF` です。汎用 netlink のファミリーは `nlctrl` だけで、Linux ではホストの
  カーネルとモジュールのもの（`ethtool`、`nl80211`、`devlink` など）があります。そのため
  それらを引くと `ENOENT` で、それらがグループをいくつ使っても、ソケットのグループは 64 です。
  `NETLINK_ROUTE` にあるのはリンク、アドレス、経路、近隣のリクエストと、近隣の表の
  ダンプだけです。近隣の表の設定（`RTM_SETNEIGHTBL`）、MCTP の近隣（`AF_MCTP` の
  `RTM_NEWNEIGH` と `RTM_DELNEIGH`）、ブリッジの転送データベース（`AF_BRIDGE` の
  `RTM_GETNEIGH`、`RTM_NEWNEIGH`、`RTM_DELNEIGH`）、ルール、設定のもの（`RTM_GETNETCONF`）、キューイング規律などは
  `EOPNOTSUPP` で、`lo` の名前の変更、ほかの属性の設定もそうです。入力の経路の
  引き当て（`RTA_IIF`）は、Linux の組み込みの値と同じく、転送も逆経路のフィルターも
  切ったところから始まります。Linux の新しい名前空間は IPv4 の設定を最初の名前空間から
  受け継ぎ、ホストが変えていることがあります（Docker は転送を入れ、Ubuntu は逆経路の
  フィルターを 2 にします）。ファイルのない `accept_local`、`send_redirects`、
  `shared_media`、`route_localnet` は組み込みの値とします。`/proc/sys/net` にあるのは、`ip_forward` と、`all`、`default`、`lo`、veth の端の
  `forwarding`、`rp_filter`、`disable_ipv6` だけで、Linux にはもっとたくさんあります。
  最初の名前空間の値はホストのものではなく Linux の組み込みの値なので、新しい名前空間も
  そこから始まります。IPv6 の `forwarding` はルーターのマルチキャストや
  エニーキャストのアドレスに加わりません。`all` のものに書くと、デバイスのものを
  インデックスの順に伝えますが、Linux は増えた順です。netconf の通知は、ファイルのない
  設定（プロキシ ARP と NDP、マルチキャストとブロードキャストの転送、リンクの落ちた
  経路を無視する設定）を、Linux の組み込みの値と同じく 0 として伝えます。MTU が 1280
  より小さい veth の端にも `ipv6/conf/<デバイス>` のファイルがありますが、Linux では
  IPv6 がないのでありません（IPv6 のアドレスは、Linux と同じく作りません）。経路は
  `lo` か veth の端を通るか、拒むかです。IPv6 のゲートウェイを通る IPv4 のネクストホップ（`RTA_VIA`）、
  カプセル化、ネクストホップのオブジェクト、
  realm、有効期限、送り元の接頭辞、ルーターの優先度、エニーキャスト・マルチキャスト・NAT の
  種類（IPv6 ではブロードキャストも）は `EOPNOTSUPP` です。ポリシーのルール
  （`RTM_NEWRULE`）も `EOPNOTSUPP` なので、ローカル、メイン、既定の表のほかは引き当てに
  使われません。新しいネットワーク名前空間では、ローカルな経路のないアドレスへの接続と
  データグラムは、どの経路に当たっても `ENETUNREACH` のままです。Linux では `lo` へ
  送り出されて捨てられるか、拒む経路のエラーになります。
  経路のメトリクス（`RTA_METRICS`）は保って見せますが、ソケットの動きは変えません。
  経路が何を持っていても、MTU、ホップ制限、ウィンドウ、輻輳制御は既定のままです。経路が
  指せる輻輳制御は `cubic` と `reno` だけで（ほかは `EINVAL`）、Linux では
  `CAP_NET_ADMIN` を持つ呼び出し元なら、先にそのモジュールを読み込みます。
  アドレスは寿命が尽きたときに消えます。Linux の確認は遅延可能な処理で、1 秒まで遅れ
  （`round_jiffies_up`）、暇なマシンではさらに数秒待つことがあります。そのファミリーの
  アドレスを足すか変えると、すぐに走ります。bind や送信をするソケットが寿命の尽きた
  ものを見つけたときは、その名前空間の netlink のソケットが次に読む、poll する、書く
  ときに伝えます。Linux は確認が走ったときに伝えます。寿命が尽きた IPv6 の経路は、
  すぐに表から消えます。Linux では引き当てでは飛ばしますが、ガベージコレクション
  （`gc_interval`、30 秒）までダンプには残り、7.3 からはそれを伝える通知に `RTA_DEL_REASON` を付けます。
  永続の IPv6 のアドレスに変更が寿命を与えると、Linux 7.3 からと同じく接頭辞の経路にも
  同じ寿命を与えます。7.3 より前ではすぐに尽きたものになります。
  `IFA_F_MANAGETEMPADDR` で一時アドレスは作らず、
  `IFA_F_MCAUTOJOIN` はグループに加わりません。
  相手のアドレスはポイントツーポイントのものにならず、`lo` の IPv6 のアドレスが仮
  （tentative）になることもありません。Linux のものは、ループバックならすぐ終わる重複アドレス検出の
  処理が動くまで仮です。`lo` が落ちている間の、名前空間自身のアドレス（`lo` か veth の
  端のもの）への接続とデータグラムは `ENETUNREACH` です。Linux では送り出されて捨てられます。`lo` のアドレスでない、
  接頭辞の中の IPv6 のアドレスへのものも `ENETUNREACH` です。Linux では接頭辞の経路が
  そこへ送って捨てます。`lo` が落ちている間の IPv6 の経路の引き当ても
  `ENETUNREACH` です。引き当ての
  `rta_cacheinfo` は参照を 1 つと数えます。Linux はキャッシュされた経路を使うほかのものも
  数えます。`RTM_F_NOTIFY` は、その引き当ての答えにだけ印を付けます。Linux はキャッシュ
  された経路に印を付けるので、その経路を通るあとの引き当てにも印が付きます。通知はリンクとその IPv6 の情報、アドレス、経路、近隣、
  名前空間の ID のものだけで、ほかのグループには送りません。`lo` を落としたときに消える、
  `lo` を通る IPv4 の経路は、Linux と同じく何も伝えません。通信が近隣を作るのは UDP、
  TCP のハンドシェイク、返る ICMP の port unreachable だけです。paludarium が `lo` や
  veth の端に送るパケットはそれだけです（いっぱいの
  backlog に再送したハンドシェイクは、その答えの近隣を作りません）。近隣は時間切れでは
  消えません（`gc_thresh1` に届きません）。ダンプはファミリーごとに新しい近隣から
  返します。Linux はハッシュ表の順に返し、その順は乱数のキーで決まります。同じ
  ハッシュのバケットの代理のエントリは、`pneigh_create` が先頭に置くのに合わせて新しい
  ものから返しますが、ある x86-64 のランナーの Linux は 2 つを逆の順に返しました。
  デバイスのない代理のエントリは名前空間とともに消えます。Linux 7.0 では代理の表が
  すべての名前空間に共通で、それを残すため、あとで同じ場所に作られた名前空間から
  見えます（Linux の master では名前空間ごとに表があります）。ループバックの近隣の
  タイマーで動くのは到達可能なもののだけです。確認から到達可能時間が過ぎると古くなり、
  探査前の遅延（5 秒）のうちに使われていれば遅延中になります。古くなったことは、
  寿命が尽きたアドレスと同じく、名前空間の netlink のソケットが次に読む、poll する、
  書くときに伝えます。遅延中や探査中のものは探査せず、到達可能にも失敗にもなりません。`NTF_USE` や `NTF_MANAGED` で未解決になったものは
  最初の探査を数えますが、次を送らず、失敗にもなりません。`NTF_EXT_MANAGED` のものを
  ときどき探査することもありません。ループバックの近隣の状態とリンク層のアドレスは
  通信に何も影響しません。Linux の `lo` は、有効でない近隣へのパケットを解決するまで持ちます。
  参照はリクエストとタイマーのものだけを数えます。IPv6 の代理のエントリは
  要請ノードのグループに入りません（`pndisc_constructor`）。`lo` の IPv6 が無効だと
  いう理由で断るリクエストもありません（`ndisc_allow_add`）。近隣の表のダンプは表の
  既定の値を返し、sysctl（`net.ipv4.neigh.*`、`net.ipv6.neigh.*`）でもホストのものでも
  変わりません（ガベージコレクションのしきい値は 128、512、1024 です。AWS のランナーの
  Linux は 2 つめと 3 つめを 15360 と 16384 に上げています）。
  到達可能な時間は基準の時間です。Linux では、その半分から 1.5 倍までの乱数です。
  エントリの大きさとキューのパケットでの長さは、x86-64 の `struct neighbour` と
  `SKB_TRUESIZE` のものです。表はその名前空間の近隣を数え、統計は 0、ハッシュの
  キーとマスクは新しい表のもの、フラッシュとキーの作り直しからの時間は emulator が
  始まってからのものです。Linux はすべての名前空間のものを数えます。表そのものの
  パラメーターの参照は 1 です。
  機能のページに挙げていないオプションは `ENOPROTOOPT` です。
  名前空間の ID を与えるのは `RTM_NEWNSID` と、相手が別の名前空間にある veth の端を
  伝えるとき、veth の端をそこへ移すときです。Linux の `peernet2id_alloc` は、キューのリース、devlink の
  インスタンス、PSP のデバイス、ovpn のピア、openvswitch の vport にもひとりでに ID を
  与えますが、ここにはそのどれもありません。なくなる名前空間の
  `RTM_DELNSID` は、最後に持っていたものが手放したときに送ります。Linux は
  ワークキューから少し遅れて送ります。リンクのメッセージの統計は 0 です。その `IFLA_AF_SPEC` は、
  `CONFIG_MCTP` を組み込んだ Ubuntu のカーネルと同じく MCTP の設定を載せます。
  組み込んでいないカーネルは載せず、`AF_MCTP` のアドレスと経路のダンプを扱う処理も
  ないので、それらのダンプには IPv4 と IPv6 のアドレスと経路を返し、MCTP のアドレスも
  経路も取りません。ほかのインターフェースはないので、MCTP のメッセージはループバック
  自身のエンドポイント ID の間だけを行き来します。タグの鍵はホストの単調時計で期限が
  切れます。`AF_MCTP` のソケットが持つ `SOL_SOCKET` のオプションは `SO_SNDBUF`、
  `SO_RCVBUF`、`SO_RCVTIMEO` だけで（ほかは `ENOPROTOOPT`）、タイムスタンプはなく、
  Linux がどのソケットにも答える `ioctl` の要求は、paludarium がどのソケットにも持つもの
  だけです。ループバックに MCTP のアドレスがないときのハードウェアアドレスでの送信は、
  Linux 7.0 と同じく `EHOSTUNREACH` です。その後のカーネルは `MCTP_ADDR_NULL` から
  送ります。
  IPv4 と IPv6 の設定は、sysctl が組み込みのままのカーネルのものです。Linux の新しい
  名前空間はホストのものを写します。IPv6 の作成時刻は 0、到達可能時間は 30 秒です。
  Linux では乱数で決まります。最初の名前空間の `127.0.0.1` と `::1` は時刻 0 に
  作られたことになります。Linux では起動の途中で作られます。`NETLINK_EXT_ACK` を
  付けても、paludarium にない機能（IPv6 のゲートウェイを通る IPv4 のネクストホップや、種類を持つリンクなど）のために
  拒んだリクエストにはメッセージを載せません。Linux ならそれを受け付けます。
  `NLM_F_CREATE` なしで置き換える IPv6 の経路がないときの
  「Can not replace route - no match found」は、そのプレフィックスに経路がないときだけ
  載せます。Linux は木のノードを探します。足りない属性を報告する属性
  （`NLMSGERR_ATTR_MISS_TYPE`）とクッキーは、受け付けるリクエストがどれも求めないので
  載せません。`NLM_F_BULK` を拒む（「Bulk delete is not supported」）のはアドレスと
  経路の削除だけです。リンクのダンプの
  `IFLA_LINKINFO` は受け取るだけで何もしません。Linux はモジュールが知る種類の
  デバイスだけを見せます。リンクのポリシーが取る `IFLA_GSO_MAX_SIZE` と
  `IFLA_GSO_IPV4_MAX_SIZE` の最小値は、Ubuntu のカーネルと同じく 321
  （`MAX_TCP_HEADER` + 1）です。ほかのビルドでは違うことがあります。
  受信バッファがいっぱいのソケットへの答えは、待たずに
  `ENOBUFS` で捨てます。ほかの名前空間は、paludarium に分けるものが
  ありません（IPC 名前空間の System V の共有メモリ・セマフォー・メッセージキューと
  POSIX メッセージキュー、マウント名前空間のマウントを除きます）。cgroup 名前空間には
  `/proc/self/cgroup` がなく、time 名前空間には `/proc/<pid>/timens_offsets` がなく、
  時計は最初の名前空間のものです。PID 名前空間はそれぞれの番号を 1 度だけ配ります。
  Linux では `pid_max` で一回りして使い回します。同じ理由で、`clone3` の `set_tid` は、
  最初の名前空間でタスクが一度持った ID を、空いた後でも取れません（`EEXIST`）。Linux では
  また取れます。その番号は、ホストのものによらず、Linux の `pid_max` の最大の 4194304
  より小さい値です。受け手の名前空間の外から積んだシグナル（`rt_sigqueueinfo`）は、`si_code`
  によらず `si_pid` を 0 にします。名前空間のファイルは `NS_GET_*` の `ioctl` を持たず、
  新しい名前空間の番号は、空いた番号を使い回す Linux のものとは違います。
- **Linux と macOS 以外のホストでマウントしたディレクトリのファイル**：`SEEK_DATA`
  や `SEEK_HOLE` の `lseek` はファイル全体をデータとして扱います。Linux では穴を
  見つけます。Windows では `st_blocks` も大きさを 512 バイトのブロックに切り上げた
  値で、Linux ではホストのファイルシステムが確保した分を数えます。ほかの Unix の
  ホストは自分の値を返します。Linux と macOS のホストでは、どちらもホストから得ます。
  `FIOQSIZE` はどのホストでも `st_blocks` をバイトにした値です。Linux ではファイルシステムが
  その時点で確保した分で、遅延割り当ての ext4 や overlayfs では `st_blocks` より遅れて
  数えます。
- **ブロックの大きさ**：`st_blksize`、`stx_blksize`、`FIGETBSZ` は、Linux と同じく
  `/proc` と端末（疑似端末のスレーブも）では 1024 です（[システムコール](./features#system-calls)）。
  ほかのファイルはどれも 4096 です。Linux では、マウントしたディレクトリは
  ホストのファイルシステムのもの（たいていは 4096）です。マウントしたディレクトリの
  `statfs` は、ここでもホストの値を返します。ホストの端末は疑似端末（devpts）と
  みなします。Linux のコンソール（`/dev/tty1`、devtmpfs）は 4096 です。ブロックの
  大きさのないファイルシステム（多くのコンテナの overlayfs など）では、Linux の
  `FIGETBSZ` は `EINVAL` です。
- **Windows の標準入力**：Windows のホストは入力が届いているかを見分けられないので、
  `poll`・`select`・`epoll` はホストの標準入力をいつも読めると見ます。`O_NONBLOCK` を
  付けた読み込みも、`EAGAIN` にならずに入力を待ち、読み込みの待ちはホストで待つので、
  シグナルでも終わりません（`EINTR` になりません）。Linux と macOS の
  ホストと WebAssembly では、入力があるときか終わったときだけ読めます。
- **ノンブロッキングの標準出力**：`O_NONBLOCK` を付けた標準出力や標準エラーへの書き込みが
  `EAGAIN` になるのは、ホストにまったく空きがないときだけです。少しでも空きがあれば、残りを
  ホストで待って全部を書きます。Linux は入る分だけを書いて、その数を返します。途中で
  止めるにはホストのディスクリプタ自身の `O_NONBLOCK` が要りますが、そのフラグはホストの
  ほかのプロセスと共有しています。Windows のホストは見分けられないので、`EAGAIN` には
  なりません。
- **疑似端末の一部**（[機能](./features#system-calls)）：片側の書き込みは、
  すぐにもう片側の行規則に届きます。Linux はワークキューから渡すので、ここでは
  書き込みの一部だけが読めることはありません。`O_ASYNC` も書き込み（やエコー）の
  たびに 1 回送りますが、Linux はワークキューが渡すひとかたまりごとに送り、その数は
  積まれる `F_SETSIG` のシグナルに表れます。それぞれの側は Linux の既定の
  フリップバッファと同じ 640 KiB まで持ちますが、その裏の Linux のメモリの勘定は
  ありません。`/dev/console` がないので、`TIOCCONS` の行き先に書かれることは
  ありません。制御端末がホストのものなら、`vhangup` は何もしません。Linux なら
  それを切断します。ホスト自身の端末はこの疑似端末ではありません。そこにつながるゲストの
  標準入出力は `TCGETS` と `TIOCGWINSZ` にだけ答えます。
- **ホストの標準入出力への `FIONREAD` と `SIOCOUTQ`**：どちらも `ENOTTY` を返します。
  Linux では、その先にあるものについて答えます。`FIONREAD` はパイプ、端末、ソケット、
  通常のファイルについて、`SIOCOUTQ` は端末とソケットについてです。ゲスト自身のパイプ、
  ソケット、通常のファイルは Linux と同じに数えます。
- **コアファイル**：コアは、カーネルの既定の `core_pattern`（作業ディレクトリの
  `core`）と同じように書きます。コアをクラッシュの処理系（systemd-coredump、apport）
  に渡すホストの設定は再現しません。
- **メモリの上限**：上限を超える書き込みをしたプロセスが終わります。Linux の
  OOM killer は、いちばんメモリを使っているプロセスを選びます。
- **ネイティブの JIT**：試験的な機能で、`--jit` を付けたときだけ使います。使えるのは
  x86-64 の Linux のホストだけで、それ以外のネイティブ版はインタプリタで動きます。
  コンパイルするのは、ブロックの先頭から続く、単純な形を持つ命令だけです
  （[アーキテクチャ](../design/architecture#the-native-jit)）。
- **stable の Rust での WebAssembly 版**：nightly の Rust が必要です。ネイティブの crate は
  最新の stable の Rust でビルドできますが、それより古い stable ではできません
  （[対応環境](platforms#rust-toolchain)）。

## 確かめていないこと

- 確かめたのは、[対応している機能](./features) に挙げたプログラムと、命令ごとのテストです。
  ほかのプログラムが完全に同じように動くことは、まだ保証していません。
- ファジングは、決まった時間の中で問題が見つからなかったことを示すもので、どんな入力でも
  安全だという証明ではありません。
- 差分テストの基準を取った CPU は、記録してある一部の AMD と Intel の CPU です。
  まだ観測していない CPU のプロファイルでは、テストがわざと止まるようにしてあります。
- メモリ、タスク（スレッドとプロセス）、開けるファイルの数は、埋め込む側が上限を
  指定しない限り無制限です。上限がなければ、信頼できないプログラムはホストのメモリを
  使い切るおそれがあります。メモリの上限が数えるのはゲストのページで、ファイルの
  中身、パイプやソケットのバッファ、エミュレーター自身のメモリは数えません（[コマンドライン](./cli)、[Rust](./rust)、
  [JavaScript](./javascript)）。
- CI での Safari の自動テストは、セッションを作れないことがあります。safaridriver が
  Safari の起動を待って時間切れになるか、起動した Safari の準備ができないままになるかです。
  テストのドライバーは、終わるように言われた Safari が終わるまで最大 15 秒待ってからセッションを頼みます。
  CI では、そのときまだ動いている Safari をプロセス ID とともにログに残し、終わらせます。
  どちらかで失敗したときにはもう 1 回だけ頼みます。3 回目はありません。ほかのもの（テストやその結果）は
  やり直さず、やり直すたびにそのエラーと時間をログに残します。この失敗は出たり出なかったりするので、
  通った実行があっても、なくなったことにはなりません。
- WebDriver のセッションを終えても、safaridriver がそのセッションのために起動した Safari は動き続けます。
  そのため、テストのドライバーはセッションのたびに（セッションを頼んで失敗したときも）、頼む前には動いていなかった
  Safari に終了を頼み、終わるまで最大 15 秒待ちます。もとから動いていた Safari（自分で使っている Safari など）には
  頼みません。終わらない Safari はログに残し、強制終了はしません。
- 前の safaridriver の補助プロセスがまだ `webinspectord` につながっているとき、または最後のクライアントが離れて
  `webinspectord` が終わろうとしているときに safaridriver を起動すると、何も表示せずに終わります。
  そのため、テストのドライバーは safaridriver を止めたあと、その補助プロセスとそれぞれの `webinspectord` が終わるまで
  最大 15 秒待ちます。動き続けるもの（ほかのクライアントのために動いている `webinspectord` など）はログに残し、
  強制終了はしません。

## 不具合を見つけたら

CPU のフォールトでゲストが終わったときは、シグナル、アドレス、命令のバイト列が
表示されます。`--report-enosys` を付けて動かし直すと、`ENOSYS` を返したシステムコールも
わかります（[コマンドライン](./cli#足りないものを探す)）。それらを添えて、
[Issue](https://github.com/aletheia-works/paludarium/issues) で知らせてください。
