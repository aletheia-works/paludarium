# 制限

paludarium は、まだ若いプロジェクトです。次のことは、今はできないか、確かめていません。

## できないこと

- **今のところ x87 の一部**：超越関数の命令（`FSIN`、`FCOS`、`FSINCOS`、`FPTAN`、
  `FPATAN`、`F2XM1`、`FYL2X`、`FYL2XP1`）と 10 進数（`FBLD`、`FBSTP`）はまだ実装して
  いないので、プログラムはそこで `SIGILL` で止まります。x87 の例外はつねにマスクされた
  ときの動きをします。マスクされていない例外は状態ワードの要約を立てるだけで、`SIGFPE` には
  なりません。16 ビット形式（`0x66` プレフィックス付き）の `FNSTENV` と `FLDENV` も実装
  していません。`FISTTP` は `CPUID` が示さない SSE3 の命令なので実装していません。
  オペランドが離れているときに `FPREM` と `FPREM1` が途中のどこで止まるかは CPU ごとに
  異なりますが、最後の剰余は同じです。
- **渡されていない動的リンクのプログラムのファイル**：Linux と同じくインタプリタと一緒に
  動かすので、musl と glibc の動的リンカーで動きます。インタプリタとライブラリは
  セッション自身のファイルから読むので、マウントするか渡す必要があります。
- **32-bit の x86、AVX、AVX-512、MMX**：対象外です。glibc が必須とするので `CPUID` は
  MMX を示しますが、その命令は `SIGILL` で止まります。MMX レジスタを使う SSE と SSE2 の
  命令（`CVTPI2PS`、`MOVQ2DQ`、`PSHUFW` など）も同じです。
- **`RCPPS`、`RCPSS`、`RSQRTPS`、`RSQRTSS` の正確な結果**：x86 が決めているのは誤差の
  範囲（1.5 × 2⁻¹²）だけで、CPU はそれぞれの表から答えます。エミュレーターは浮動小数点
  の除算（`RSQRT` はその前に平方根）で計算するので、下位のビットが実際の CPU と異なる
  ことがあります。テストで
  確かめているのは、この範囲と特殊な値で、ビットそのものではありません。
- **アクセスできないメモリへの、空のマスクの `MASKMOVDQU`**：エミュレーターは何も
  アクセスしませんが、実際の CPU はフォールトすることがあります（AMD EPYC ではフォールト
  し、`SIGSEGV` で終わります）。後ろのバイトでフォールトすると前のバイトは書かれたまま
  ですが、これは実際の CPU と比べていません。
- **`/proc/self/maps` の一部**：エミュレーターには vDSO も `vsyscall` のページも
  ないので、`[vvar]`、`[vdso]`、`[vsyscall]` の行はありません。スタックの VMA は
  初めから全体の大きさで、Linux のように使うにつれて伸びません。プログラムと
  インタープリターのセグメントの名前は起動時のパスで、`(deleted)` も付きません。
  Linux は名前の変更を追い、シンボリックリンクを解決します。ほかのプロセスの
  `/proc/<pid>/maps`、`smaps`、`[anon:<名前>]` の名前（`PR_SET_VMA`）はありません。
- **ほかの `/proc` の一部**：作るのは、プロセスのディレクトリといくつかのシステムの
  ファイルだけです（[機能](./features) を参照）。ほかのシステムのファイル（`/proc/cpuinfo`、
  `fs/mqueue` 以外の `/proc/sys` など）と、読むプロセス自身のディレクトリのほかの名前
  （`auxv`、`limits` など）は、ふつうのパスと同じように探すので、`--mount /:/` ではホストの
  `/proc` に届きます。ほかのプロセスのディレクトリでは、それらは `ENOENT` です。Linux は
  root に `fd`、`maps`、`statm` なども見せます。`stat` のページフォールト、常駐メモリ、
  開始時刻、コードの範囲は 0 なので、`ps` の `RSS` は出ず、`STIME` と `START` は
  `/proc/stat` の起動時刻です。`/proc/stat` は CPU 時間、割り込み、コンテキストスイッチを
  数えず、割り込みの番号ごとの数も並べません。
  スレッドの `stat` の CPU 時間はプロセスのものです。ほかのプロセスの状態は、待っているか
  どうかではなく、スレッドがシステムコールの中にいるかどうかから決めます。スレッドが
  ほかのプロセスに見せるのは最後のシステムコールかシグナルの確認で公開したものなので、
  呼び出しの間だけ変えたマスク（`rt_sigsuspend`、`ppoll`）は見えません。`meminfo` は
  `sysinfo` と同じ固定の 4 GiB を、何も使っていないものとして返します。
- **デバイスのノードとホストの FIFO**：ゲストは root で動きますが、キャラクターデバイスと
  ブロックデバイスの `mknod` は `EPERM` です。paludarium には、それが表すデバイスがないから
  です。マウントしたホストのディレクトリに FIFO を作れるのは Linux のホストだけで、つながる
  のはゲストの中で開いたものだけです。同じノードを開いたホストのプログラムにはつながりません。
- **ネットワーク**：許可の一覧（`--allow-net`、`Config::with_network`、ブラウザでは
  [中継](./relay) の要る JavaScript の `network` の指定）がなければ、
  `socket()` はどのファミリーにも `EAFNOSUPPORT` を返します。一覧があっても、使えるのは
  TCP のクライアント、ゲスト自身のソケットのための TCP と UDP のサーバー、名前解決だけです
  （[ネットワーク](./features#network)）。
  - ゲストがサーバーになれるのは、ループバックの上で自身のソケットに対してだけです
    （[ループバックのサーバー](./features#loopback-servers)）。ホストもほかのマシンも
    接続できず、`bind` が取るのはループバックのアドレスと未指定のアドレスだけです
    （ほかは `EADDRNOTAVAIL`。Linux ではマシンのどのアドレスも取れます）。
  - UDP のソケットが届くのは、DNS の代わりと、ループバックの上のゲスト自身のソケット
    だけです。ほかのアドレスへのデータグラムは `ENETUNREACH` です。ポリシーが許さない
    ほかの相手へ接続したソケットと、ホストの経路が見えない WebAssembly で接続した
    ソケットは、すべてのアドレスでポートを持ったままで、Linux は経路の送り元のアドレスで取ります。そのため `getsockname` は
    未指定のアドレスを返し、そのポートをループバックのアドレスで `bind` すると
    `EADDRINUSE` になります（Linux では `bind` できます）。
    マルチキャストとブロードキャストのデータグラムは、どこにも届きません。データグラムには
    いつも届いた時刻を付けます。Linux がそうするのは、マシンのどこかのソケットが
    タイムスタンプを取っている間だけで、どれも取っていなければ、`SO_TIMESTAMP` などで
    読むときにその時刻を付けます。DNS の代わりの答えには、読んだ時刻を付けます。
    raw ソケットは `EPERM`、ICMP のソケットは
    `EACCES`、ほかの種類（Linux がモジュールを読み込んで作る SCTP の
    `SOCK_SEQPACKET` など）は `ESOCKTNOSUPPORT` です。
  - ホストからマウントしたディレクトリの下で AF_UNIX のソケットがパスに `bind` できるのは、
    Linux のホストだけで、そこにソケットファイルを作ります。root しかソケットファイルを
    作れない macOS と、Windows では、そこのパスへの `bind` は `EPERM` です。ゲストの
    ソケットどうしはそのファイルを通してつながりますが、ホストのプログラムのソケット
    ファイルはソケットを見つけず（`ECONNREFUSED`）、ホストのプログラムもゲストの
    ソケットには届きません。`/proc` のないホスト（chroot や最小限のコンテナ）では、
    ファイルのモードからホスト自身の umask の分も引かれます。ソケットファイルの書き込みの
    許可は、root と同じく確かめません。
  - DNS の代わりが答えるのは `A` と `AAAA` だけで、EDNS は読まないので、データグラムの
    答えは 512 バイトまでです。ホストが引けない名前は `SERVFAIL` です。53 番ポートへの
    TCP の接続は、いつも DNS の代わりに届き、本物の DNS サーバーには届きません。
  - ホストを通した接続が開く前の `getsockname` は、`bind` したアドレス、なければ
    未指定のアドレスとポート 0 を返します。Linux では取ったポートを返します。
    `bind` したポートはホストに届かず、ホストの接続は自分のポートから出ます。`SIOCOUTQ` は、相手がまだ受け取りを確かめていない分では
    なく、ホストがまだ送りに取っていない分を数えます。ホストを通すと、`SO_SNDBUF` と `SO_RCVBUF` は
    `getsockopt` のために覚えますが、バッファの大きさは変えません（どちらの向きも
    256 KiB です）。`TCP_NODELAY` 以外のオプションはホストのソケットに届きません。
  - TCP のバイトには、いつも届いた時刻を付けます。Linux がセグメントにそうするのは、
    マシンのどこかのソケットがタイムスタンプを取っている間だけで、どれも取っていなければ、
    そのとき届いたセグメントにはタイムスタンプがありません。読まれずに待っているバイトは
    みな最後に届いた時刻を取ります。Linux がセグメントを前のものにつなげるのは、
    前のものの断片が上限（`MAX_SKB_FRAGS`）に満たない間だけなので、前のセグメントを
    読むと前の時刻になることがあります。
  - ホストを通すと、`MSG_OOB` はそのバイトをふつうのバイトとして送り、緊急データを
    見つけず（`EINVAL`）、`SIGURG` も来ません。
  - ループバックで、緊急のバイトは相手に届いたときに `SIGURG` を 1 回送ります。Linux は、
    いっぱいのバッファの後ろで待っているときのように、バイトが 64 KiB より先にある間に
    届くセグメントごとに、もう 1 回ずつ送ります。送り手の `__tcp_transmit_skb` が各
    セグメントに、その先頭から 65535 バイト先を指す仮の緊急ポインタを付け、受け手の
    `tcp_check_urg` がそれを新しいものと見なすためです。それが何セグメントになるかは
    Linux 自身の分割と窓の更新しだいで、既定のバッファでは数十になります。
  - ループバックでゲストが設定した `SO_SNDBUF` と `SO_RCVBUF` は、接続のバッファを
    おおまかに決めるだけです（[ループバックのサーバー](./features#loopback-servers)）。
    Linux はセグメントごとの余分も数え、受信の窓も独自の刻みで決めるので、誰も読まない
    送り手が待つまでに入るバイト数は違います。設定しない側は 256 KiB で、Linux は接続を
    調整しながら（メガバイト単位まで）大きくします。
  - `tcp_info`（`TCP_INFO`、`INET_DIAG_INFO`）は、ループバックが運んだものを Linux と同じく
    数えたものを持ちます。状態、オプション、ウィンドウスケール、リスナーのキュー、送った
    バイト・確認応答を受けたバイト・受け取ったバイト・まだ送っていないバイト、そして
    Linux が始めに持つスロースタートのしきい値、輻輳ウィンドウ、経路 MTU、広告する MSS、
    リオーダリングです。Linux の TCP が測ったり調整したりするものは、いちばん単純な場合の
    ループバック接続の値です。往復時間（30 µs）とそこから決まるタイムアウトとレート、
    ペーシング、送受信の MSS とウィンドウ（大きくなりません）、送ったバイトと受け取ったバイトを
    32 KiB ずつに分けたセグメント数（それぞれに確認応答が 1 つ）です。ハンドシェイクで示した
    ウィンドウスケールは変わりません。データが来てからの時間は
    読んだときから数えます。ハンドシェイクの再送のほかに再送も損失もないので、それらの数は 0 です。相手のウィンドウ
    スケールは、相手がどんなバッファーを設定しても Linux の既定値とします。ホストが張った
    接続も、ループバックのものと同じように伝えます。
- **ファイルのマッピング**：ファイルのマッピングは Linux と同じくファイルのページ
  キャッシュを見せます（`MAP_PRIVATE` のものは、まだ書いていないページで）。ただし、
  `MAP_SHARED` のマッピングへの書き込みがホストのファイルに届くのは、ゲストが
  そのファイルを読むか `stat` したとき、`msync` か `fsync` を呼んだとき、ファイルの最後のマッピングがなくなった
  ときだけです（Linux は自分の都合で書き戻します）。また、ホストのほかのプログラムが
  ファイルを変えても、マッピングには届きません。Windows のホストでは、`O_APPEND` で
  開いたディスクリプタから作った共有マッピングへの書き込みは、ファイルに届きません。
  マッピングしたファイルの終わり（その先のページは `SIGBUS` になります）は、ゲスト自身の
  ファイルの操作で決まる大きさです。ホストのプログラムが大きさを変えても、終わりは
  動きません。
- **下に伸びるマッピング**：下に伸びる VMA はメインのスタックだけです。`MAP_GROWSDOWN` で
  作ったマッピングは普通のマッピングなので伸びず、そこへの `PROT_GROWSDOWN` 付きの
  `mprotect` は、Linux なら変更されるところ `EINVAL` になります。
- **仮想 CPU**：`rseq` を登録したスレッドは、ホストの CPU ではなく仮想 CPU で動きます。
  そのため、領域と `getcpu` が示す CPU は、ホストがそのスレッドを動かしている CPU では
  ありません。`/proc/<pid>/stat` は CPU 0 を示します。クリティカルセクションは、CPU が
  変わったときや、自分の CPU でほかのスレッドが動いたあとに中止されます。Linux でも割り込まれ
  うる場面です。ホストがスレッドをプリエンプトしても中止されませんが、それはほかの `rseq` の
  スレッドからは見えません。ほかのスレッドが設定した CPU マスクは、そのスレッドが次に止まった
  ときに効きます。システムコールの中のスレッドは CPU を持たないので、領域は最後に動いた CPU を
  示します。`rseq` のないスレッドは仮想 CPU では動かず、数にも入りません。タイムスライスの
  延長はありません。それなしでビルドした Linux と同じく、`RSEQ_FLAG_SLICE_EXT_DEFAULT_ON` は
  `EINVAL`、`rseq_slice_yield` は `ENOSYS` です。
- **保護キー**：仮想 CPU には保護キーがありません（`CPUID` は PKU を報告しません）。そのため
  `pkey_alloc` は、そういう CPU での Linux と同じく `ENOSPC` を返し、プログラムは保護キーなしで
  続けます。`RDPKRU` と `WRPKRU` は、そういう CPU と同じく `SIGILL` でプログラムを止めます。
- **io_uring の一部**：実行するのは `IORING_OP_NOP` と `IORING_OP_EPOLL_CTL` だけで、ほかの
  操作は `EOPNOTSUPP` で完了します。setup のフラグ `IORING_SETUP_IOPOLL`、`_SQPOLL`、
  `_SQ_AFF`、`_ATTACH_WQ`、`_R_DISABLED`、`_SQE128`、`_CQE32`、`_NO_MMAP`、
  `_REGISTERED_FD_ONLY` は `EINVAL` です。`io_uring_register` は `IORING_REGISTER_PROBE`
  だけで（ほかは `EINVAL`）、リングの記述子、ファイル、バッファー、パーソナリティは登録
  できません。リングは共有でしかマップできず（`MAP_PRIVATE` は `EINVAL`）、`poll` と `epoll` は
  その記述子を見張れません。要求はすべて `io_uring_enter` の中で完了するので、ある数より多くの
  完了を待つと、シグナルかタイムアウトでしか終わりません。機能は Linux 6.12 のものなので、
  リングの記述子は登録できないのに `IORING_FEAT_REG_REG_RING` を、待ちの `min_wait_usec` は何も
  変えない（処理中の要求はありません）のに `IORING_FEAT_MIN_TIMEOUT` を報告します。
- **ネイティブ AIO の一部**：読み書きと同期は、Linux のバッファー付き I/O と同じく、
  どれも `io_submit` が取ったときに実行されます。`O_DIRECT` で開いたファイルのものも
  Linux のように裏では実行されず、同期のイベントは、Linux ではワーカーが少し後に入れるのに、
  呼び出しが戻るときにはリングにあります。待っている poll を確かめるのは、プロセスの
  スレッドが呼び出しをするとき（どの呼び出しでも）と待っているあいだだけなので、カーネルを
  一度も呼ばずにリングからイベントを取るプログラムには、その完了が見えません。poll が
  2 つのキューで待つファイル（Linux は準備できていなければ `EINVAL` で断ります）は、
  ファイルの種類から推します。読み書き両方で開いた FIFO と、キャラクターデバイス（端末）です。
  リングが保てる要求はちょうどイベント数より 1 少なく、Linux では CPU ごとの数のために
  それより早く止まることがあります。`IOCB_FLAG_IOPRIO` の I/O 優先度は確かめるだけで何も
  変えず、`mremap` が動かしたリングは丸ごと動いたときだけ新しいアドレスで見つかります
  （Linux は一部の移動を断ります）。
- **一部のシステムコール**：実装していないシステムコールは `ENOSYS` を返すので、
  プログラムによってはその機能なしで続けられます。
  - `pwritev2` の `RWF_NOAPPEND` は、Windows のホストでは `O_APPEND` のファイルの追記を
    止められないので、そこではそのようなファイルに `EOPNOTSUPP` を返します。
    通常のファイルの `RWF_NOWAIT` の読み込みで、ページがキャッシュにない（Linux の
    `EAGAIN`）ことはありません。macOS と Windows のホストでは、ホストのファイルはその
    ファイルシステムによらず ext4 と同じく `RWF_NOWAIT` と `RWF_DONTCACHE` を受け付けます。
    Linux のホストで見分けるのは ext4、xfs、btrfs、f2fs だけです（ほかのファイルシステムは
    どちらも断ります）。
  - `madvise` は、Linux が受け付ける次の指定を断ります（`EINVAL`）。`MADV_COLLAPSE`、
    `MADV_HWPOISON`、`MADV_SOFT_OFFLINE` です。`MADV_REMOVE` と `MADV_GUARD_INSTALL` は、
    ロックしたマッピングのメモリも受け付けます。Linux では `EINVAL` です。ここでは
    マッピングごとのロックの状態を持たないためです。`/proc/<pid>/smaps` は `VmFlags` を
    出さないので、ガードを置いた VMA の `gu` フラグも出しません。`/proc/<pid>/pagemap` は
    なく、ガードページを示せません。
    `MADV_POPULATE_READ` と `MADV_POPULATE_WRITE` は、`memfd_secret` のマッピングのページも
    割り当てます。Linux では `EINVAL` です。
  - `process_madvise` は、呼んだプロセス自身のメモリには `madvise` が受け付ける指定しか
    受け付けず、ほかのプロセスの範囲はマップされているかを確かめるだけです。Linux が知らない
    指定は、Linux master と同じく範囲を見る前に断ります（`EINVAL`）。CI のカーネルは範囲ごとに
    確かめるので、範囲がないか空の範囲だけのときは 0 を返します。
  - `process_mrelease` は、SIGKILL を送られたプロセスを、送られたときから終わりかけている
    ものとみなします。ほかの命取りのシグナルでは、そのスレッドのどれかが受け取るまでそう
    みなしません（それまでは `EINVAL`）。Linux は、プロセスを終わらせるシグナルならどれでも
    送ったときに印を付けます。
  - `fork` の子では、ローダーが書き込んだあと何も書き込んでいない、プログラム自身の
    ELF セグメントのページを、`move_pages` はそこにあるものとして示します。Linux は
    `anon_vma` のない VMA のページテーブルを子にコピーしないので、子が触れるまでは
    `-ENOENT` です。ここではローダーのコピーがそのページの唯一の内容だからです。
  - いくつかのメッセージのあとで `recvmmsg` を終わらせたエラーは捨てます。Linux はこれを
    ソケットのエラーとして残し、次の呼び出しと `SO_ERROR` で返します。また `recvmmsg` は、
    ソケットに残っているエラーを先に返しません。
  - `memfd_secret` のファイルのページは `RLIMIT_MEMLOCK` に数えません。Linux では、それを
    超えるページフォールトは `SIGBUS` です。また、そのマッピングの `MS_SYNC` の `msync` は
    成功します。Linux では、ファイルに `fsync` がないので `EINVAL` です。
  - CPU 時間のインターバルタイマー（`ITIMER_VIRTUAL` と `ITIMER_PROF`）と `RLIMIT_CPU` は、
    どれもプロセスの CPU 時間のすべてを数えます。ここではそのすべてがユーザーの時間だからです
    （Linux の `ITIMER_VIRTUAL` はシステムの時間を数えず、`RLIMIT_CPU` は数えます）。WebAssembly のように
    ホストがスレッドの CPU 時間を測れないところでは、それは経過時間なので、スレッドが
    眠ったり待ったりしている時間も数えます。タイマーを確かめるのは、
    Linux のようにティックごとではなく、スレッドがシステムコールをするときと、命令を
    100,000 個実行するごとです。ティックは CI ランナーの `CONFIG_HZ` に合わせて 1 ms と
    します。CPU 時間の時計の POSIX タイマーも、同じように数えて確かめます。プロセスの
    CPU 時計での眠りも同じで、眠っているスレッドがティックごとに確かめます。それが経過時間の
    ところでは眠っている時間も数えるので、ほかにスレッドのないプロセスでも、頼んだ時間が
    経てば眠りが終わります。ほかの
    プロセスやスレッドの CPU 時計（負の時計 ID）での `timer_create` は `EINVAL` を返します。
    Linux はタイマーを作ります。`clock_gettime` も、それらの時計では `EINVAL` を返します。
    Linux はそれを読みます。`clock_nanosleep` も `EINVAL` を返します。Linux はその時計で眠ります。
  - `ustat` が見つけるのはマウントのデバイスだけです。パイプ・ソケット・memfd・名前空間の
    ファイルの `st_dev` では `EINVAL` を返します。Linux はその疑似ファイルシステムの
    スーパーブロックを見つけ、その数（0）を返します。`/proc` と `/dev` のファイルの
    `st_dev` は、そのパスがあるマウントのものなので、`ustat` はそのマウントの数を返します。
    Linux は procfs や devtmpfs の数を返します。
  - ファイルハンドル（`name_to_handle_at` と、`/proc/self/fdinfo` にある inotify の
    ウォッチのもの）の世代は 0（memfd では 1）です。tmpfs は inode ごとに乱数で選びます。ホストの
    ディレクトリのファイルは NFS のエクスポートがないファイルシステムのものとして扱います
    （`EOPNOTSUPP`、`AT_HANDLE_FID` では型 `FILEID_INO64_GEN` の識別子）。Linux はその
    ファイルシステム（たとえば ext4）のハンドルを返します。`open_by_handle_at` が読み解く
    のは pidfs のハンドルと、`CAP_DAC_READ_SEARCH` があればメモリー上のルートの tmpfs の
    ハンドルで、まだ名前がリンクしているファイルのものだけです（Linux は削除したが開いて
    いるファイルも開きます）。ほかのマウント（ホストのディレクトリ、memfd）では `ESTALE`
    です。`CAP_DAC_READ_SEARCH` のない呼び出しは、`O_DIRECTORY` を付けたディレクトリでも
    そこでは `EPERM` です。Linux 6.10 以降は、マウントに対して `CAP_SYS_ADMIN` を持つ
    呼び出しを通します。名前空間のファイルには nsfs のハンドルがない（`EOPNOTSUPP`。
    Linux 6.18 は型 `FILEID_NSFS` のハンドルを返します）ので、nsfs では何も読み解けません
    （`ESTALE`）。pidfs のハンドルは、pidfd を一度も持たなかったプロセスも開きます。
    Linux は `ESTALE` を返します。`PIDFD_THREAD` の pidfd の inode はプロセス全体のものです。
    `O_EXCL` を付けてハンドルから開いた pidfd には、CI の Linux 7.0 と同じく `PIDFD_THREAD`
    が残りません。Linux 7.2 以降は残します。
  - System V IPC には `/proc/sysvipc` がなく、共有メモリ・セマフォー・メッセージキューの
    上限は Linux の既定値で、`/proc/sys/kernel` から変えられません。メッセージキューで
    待っている送信者は、キューが変わるたびにすべて確かめ直します。Linux は、それぞれの
    メッセージが入る間だけ、待ち始めた順に起こします。
  - POSIX メッセージキューのファイルシステムは、ほかの場所にはマウントできません。
    `/dev/mqueue` はいつも最初の IPC 名前空間のもので、`/proc/self/mountinfo` には
    並びません。そこでは `open`、`stat`、`access`、`getdents`、`unlink`、`rmdir`、`statfs`、
    `mkdir`、`mknod`、`symlink`、`link`、`rename`、`chmod`、`chown`、`utimensat`、`truncate` が
    Linux と同じに動きます。ただし、パスが `/dev/mqueue` そのものを指すときだけです。ほかの
    場所のシンボリックリンクを通ってそこに着くパスは、ホストで引きます。最初の名前空間の
    ルートの時刻は、そこでキューを作るか消すまではホストの起動時刻です。Linux では、起動の
    途中でカーネルがそれを作った、少しあとの時刻です。
  - `SIGEV_THREAD` のクッキーは、netlink ソケットの受信バッファーを 960 バイト（CI の
    ランナーのカーネルでの `truesize`）取りますが、そのソケットのほかのデータグラムは長さの
    分だけ取ります。Linux はそれらも `truesize` で数えます。そのため、いっぱいになるまでに
    Linux より多くのデータグラムが入ることがあります。
  - `/proc/sys/fs/mqueue` のファイルは、書ける者を開くときに確かめます。Linux は書き込みの
    たびに書く者を確かめ直します。また、サイズとして値の長さを示します。Linux は 0 です。
  - セットで待っているセマフォーの操作は、1 つの待ち行列で待ち始めた順に試します（0 を
    待つものが先）。Linux はセマフォーごとの待ち行列と、複数のセマフォーへの操作の待ち行列を
    分けて持つので、両方の種類の待ちが混ざると、どちらも通れる 2 つの待ちのどちらが先に
    通るかが違うことがあります。
  - Yama の `ptrace_scope` は常に 1 です。それを読んだり変えたりする
    `/proc/sys/kernel/yama/ptrace_scope` はありません。
  - `mincore` は、ファイルのページをファイルの範囲内なら常にメモリにあるとします。
    Linux はページキャッシュを調べます。`MAP_POPULATE` や `MAP_LOCKED`、メモリのロックで
    読み込んだページも、触るまでは数えません。
  - メモリのロックは状態を残しません。そのためロックには `RLIMIT_MEMLOCK` を適用
    しません（適用するのは `SHM_LOCK` だけで、`CAP_IPC_LOCK` を手放したゲストにだけ
    関係します）。ロックしたメモリへの
    `MADV_DONTNEED`、`MADV_COLD`、`MADV_PAGEOUT` は、Linux の `EINVAL` と違って成功します。ファイルの終わりより後ろの
    ファイルのマッピングのページへの `mlock` は、Linux の `ENOMEM` と違って成功します。
    `/proc` にもロックしたメモリは出ません。
  - 共有のマッピングに `mbind` で付けたメモリのポリシーは、そのマッピングのものに
    なります。Linux はそのポリシーを共有メモリそのものに付け、マッピングしている
    すべてのプロセスで使います。`/proc/<pid>/numa_maps` はありません。
  - System V の共有メモリのセグメントの `shm_atime`、`shm_dtime`、`shm_lpid` は、
    `shmat` と `shmdt` でだけ変わります。Linux は、`fork` がつないだ領域を写すとき、
    `munmap` や `mprotect` がそれを分けるとき、それを持つプロセスが終わるときや exec する
    ときにも変えます。`shmdt` が見つけるのは、スレッドの IPC 名前空間のセグメントにつないだ
    領域だけです。Linux は、`setns` や `unshare` でスレッドがほかの名前空間に移る前に
    つないだ領域も外します。つないだ領域の一部を隣のかけらと同じ保護に戻す `mprotect` は、
    独立したかけらを作り、それも 1 つのつながりと数えます。最近の Linux は、2 つの境目を
    動かします。
- **拡張属性**：マウントしたホストのディレクトリは、拡張属性のないファイルシステムとして
  振る舞います。読むと見つからず（`ENODATA`）、書くと `EOPNOTSUPP` です。メモリ上では、
  `system.*` の属性はなく（`EOPNOTSUPP`）、`security.capability` の値は確かめず、スティッキー
  ディレクトリでも `user.*` を持ち主に限りません。
- **名前を変えるときのフラグ**：Windows のホストでは、マウントしたディレクトリでの
  `renameat2` は、そのフラグのない Linux のファイルシステムと同じく
  `RENAME_NOREPLACE` も `RENAME_EXCHANGE` も受け付けません（`EINVAL`）。
- **ファイルの持ち主**：マウントしたホストのディレクトリでは、`chown` で変えた
  ファイルの持ち主とグループ、そしてゲストがそこに作ったファイルの持ち主とグループを、
  エミュレータが動いている間だけ覚えます。ホストのファイルには書きません。次に動かすと、
  そこのファイルはまたすべて root のものに見えます。
- **Landlock**：ABI バージョン 8 までです。記録のフラグは受け付けますが、何も記録しません。
  `LANDLOCK_RESTRICT_SELF_TSYNC` では、ほかのスレッドが自分の確認に新しいドメインを
  使うのは、次にカーネルに入るときからです。Linux は、すべてのスレッドが受け取るまで
  待ちます。それらのスレッドへのシグナルにはすぐに効き、`/proc` にはそれぞれの次の
  システムコールの後から見えます。`F_SETOWN` は送り手を記録しないので、`F_SETOWN` に
  よる `SIGIO` と `SIGURG` はスコープの対象になりません。名前の変更での Landlock の
  確認は許可の確認の後で、Linux は前です。違いが出るのは両方が断るときだけです。
  `/proc` の下のファイルへのルールは、`execve` には効きません。開くときは、パスが
  指すファイルを開く前に確かめ（作ったファイルは作った後に確かめ）ます。その間に別の
  スレッドが名前を変えると、確かめたファイルと開いたファイルが違うことがあります。
  `mount`、`umount2`、`pivot_root` はありません（`ENOSYS`）。Linux はドメインの中の
  スレッドにはこれらを断ります（`EPERM`）。
- **seccomp**：`SECCOMP_FILTER_FLAG_WAIT_KILLABLE_RECV` でリスナーの答えを待ち
  続ける呼び出しは、致命的なシグナルで起きるのではなく、10 ミリ秒ごとにそれを
  確かめます。何も記録しません
  （`SECCOMP_FILTER_FLAG_LOG`、`SECCOMP_RET_LOG`）。strict モードでも、Linux の
  `TIF_NOTSC` のように `rdtsc` を例外にはしません。`SECCOMP_FILTER_FLAG_TSYNC` の
  後、ほかのスレッドの新しいフィルターが `/proc` に見えるのは、そのスレッドの次の
  システムコールの後からです。
- **資格情報**：スレッドが変えた ID とケーパビリティは、ファイル、シグナル、資源の上限、
  優先度、ソケットの資格情報、コアファイルでは確かめますが、ほかのところではまだ
  確かめていません。
  `F_SETOWN` は設定した側の資格情報を記録しないので、
  `SIGIO` と `SIGURG` は、Linux の `sigio_perm` と違い、だれが設定しても持ち主に届きます。
  `PR_SET_PDEATHSIG` のシグナルは、親プロセスが終わったときにそのリーダーの ID で送りますが、
  Linux は子を作ったスレッドが終わったときにそのスレッドの ID で送ります。
  ファイルのうち、`/proc` と `/dev` の下は確かめません。`fs.protected_hardlinks`、
  `fs.protected_symlinks`、`fs.protected_fifos`、`fs.protected_regular` は、
  カーネルの既定値の 0 として振る舞います。多くのディストリビューションは
  これらを上げています。`execve` はファイルのケーパビリティ
  （`security.capability`）を読まず、`nosuid` のマウントもありません。
  set-user-ID や set-group-ID のプログラムは、ほかのプロセスが呼んだ側と作業
  ディレクトリを共有していても（`CLONE_FS`）持ち主やグループになります。Linux なら
  `CAP_SETUID` がなければ実 ID を実効 ID にします。`/proc/self/status` は呼んだ
  スレッドの資格情報を示しますが、Linux はスレッドグループのリーダーのものを
  示します。`PR_CAPBSET_DROP` と `PR_CAP_AMBIENT` がないので、どのスレッドも
  バウンディングセットにすべてのケーパビリティを持ち、アンビエントセットには持ちません。
- **ソケットのメッセージ**：`sendmsg` と `recvmsg` は、Linux と同じように
  `SCM_RIGHTS` でディスクリプタを、`SCM_CREDENTIALS` で資格情報を受け渡します。
  違いは次のとおりです。
  - 読まれていないメッセージだけが持っているソケットは、ほかのソケットがなくなると
    すぐに閉じられます。Linux のガベージコレクタは、ワークキューから少しあとに
    閉じます。
- **ソケットのオプション**：`setsockopt` は、効き目を再現していないオプションを
  `ENOPROTOOPT` で断ります。Linux は受け付けます。フィルターなど Linux にある
  ほかのオプションです。セキュリティモジュールは再現していないので、`SO_PASSSEC` は
  `SCM_SECURITY` を運ばず、`SO_PEERSEC` は `ENOPROTOOPT` です。モジュールのない
  Linux と同じです。SELinux のある Linux は送り手や相手のコンテキストを渡し、
  AppArmor のある Linux は `SO_PEERSEC` で相手のラベルを渡します。
  `SO_RCVTIMEO` と `SO_SNDTIMEO` は 1000 Hz の刻みに丸めます。
  Linux は自分の `CONFIG_HZ` に丸めます。
  ここではケーパビリティを確かめないので、`CAP_NET_ADMIN` の要るオプション
  （`SO_DEBUG`、`SO_SNDBUFFORCE` など）も root と同じく設定できます。
- **シグナル駆動の入出力**：ホストの標準入力は 10 ms ごとに見るので、何もなかったところに
  入力が来るたびに `SIGIO` を 1 回送ります。Linux のパイプや端末は、入力のひとまとまりごとに
  送ります。標準出力と標準エラーも同じように見て、いっぱいだったところに空きができる
  たびに 1 回送ります。Linux のパイプは、読み手が読むたびに書き手へ送ります。見るための
  10 ms より短い間だけ満杯や空だったストリームは見逃され、送らないことがあります。ただし、
  読み書きがゲストに `EAGAIN` を返したあとは必ず送ります。スレッドがない WebAssembly では
  送りません。
- **signalfd へのエッジトリガーの `epoll`**：プロセスのほかのスレッドに積まれた
  シグナルのエッジは、そのスレッドがシグナルを取り込んだとき（次のシステムコールか、
  待っている間なら 10 ms 以内）に来ます。Linux の `signalfd_notify` は送られたときに
  ファイルを起こすので、待たない `epoll_wait` はそれより先に呼ばれることがあります。
- **inotify の一部**：何もアンマウントしない（`umount2` がない）ので、`IN_UNMOUNT` は
  送りません。
  `/proc/self/fdinfo` では、epoll のファイルはディスクリプタの順に並びます。Linux はファイルのアドレスの
  順です。eventfd の番号はエミュレータの中で数えます。Linux の `eventfd-id` はシステム
  全体で数えます。マウントしたディレクトリにホストが加えた変更は見えず、ディスクリプタの
  場所もそれを追いません。
- **名前空間**：ユーザーの名前空間には `projid_map` も `user.max_*` の上限もありません。
  その対応表のファイルは、書き込みを開いたときの資格情報で確かめます。Linux は、親で要る
  `CAP_SETUID` と `CAP_SETGID` には書き手の資格情報も見ます。ダンプできないプロセスの
  `/proc` のファイルは最初の名前空間のルートのものです。Linux では、そのプロセスの
  名前空間がルートを対応させていればそのルートのものです。ファイルケーパビリティは、
  ユーザーの名前空間の中でもありません。ネットワーク名前空間には、ループバックのほかにインターフェースがなく（別の
  名前空間に届く `veth` の組もありません）、インターフェースのリクエストと netlink は
  `IFF_UP` のほかのフラグを変えません。最初の名前空間でも `lo` しか見えません。
  Linux ではホストのインターフェースが見えます。
  netlink には `NETLINK_ROUTE`、`NETLINK_SOCK_DIAG`、`NETLINK_GENERIC` しかありません
  （ほかは `EPROTONOSUPPORT`）。ソケット診断が伝えるのは AF_UNIX、TCP、UDP のソケット
  だけです。AF_NETLINK と AF_PACKET にはハンドラーがなく（`ENOENT`）、Linux がモジュール
  として読み込む raw ソケット、SCTP、MPTCP のハンドラーもありません。`SOCK_DESTROY` は
  `EOPNOTSUPP` です。ダンプは古いソケットから順に挙げます。Linux の順はハッシュ表に
  従います。AF_UNIX のソケットが送って待っているものは、ここで送信バッファーに数える量で
  数えます。Linux はバッファーの本当の大きさで数えます。TCP のソケットについては、
  メモリはバッファーのほかを 0 と伝えます。キープアライブのタイマーは今から `TCP_KEEPIDLE` まるごとで終わるとし、再送の
  時刻と回数があるのはループバックのハンドシェイクだけです。ホストが張った接続には、
  終わったあとの `TIME_WAIT` がありません。送るバイトがまだ残る閉じたソケットは
  `FIN_WAIT1` の保持として見えます。Linux ではソケットそのものが残ります。どのソケットの
  cgroup もルートの 1 で、トラフィッククラスは 0 です。BPF のマップを指すリクエスト
  （`INET_DIAG_REQ_SK_BPF_STORAGES`）は、ここにはマップの記述子がないので `EINVAL` です。
  Linux では、開いていない記述子なら `EBADF` です。汎用 netlink のファミリーは `nlctrl` だけで、Linux ではホストの
  カーネルとモジュールのもの（`ethtool`、`nl80211`、`devlink` など）があります。そのため
  それらを引くと `ENOENT` で、それらがグループをいくつ使っても、ソケットのグループは 64 です。
  `NETLINK_ROUTE` にあるのはリンク、アドレス、経路のリクエストだけです。
  近隣、ルール、キューイング規律などは
  `EOPNOTSUPP` で、入力の経路の引き当て（`ip route get ... iif` が送る `RTA_IIF`）、
  `lo` の名前の変更、ほかの属性の設定もそうです。経路は
  `lo` を通るか拒むかのどちらかです。IPv6 のゲートウェイ、マルチパスの経路、メトリクス
  （`ip route add ... mtu` が送る `RTA_METRICS`）、カプセル化、ネクストホップのオブジェクト、
  realm、有効期限、送り元の接頭辞、ルーターの優先度、エニーキャスト・マルチキャスト・NAT の
  種類（IPv6 ではブロードキャストも）は `EOPNOTSUPP` です。ポリシーのルール
  （`RTM_NEWRULE`）も `EOPNOTSUPP` なので、ローカル、メイン、既定の表のほかは引き当てに
  使われません。新しいネットワーク名前空間では、ローカルな経路のないアドレスへの接続と
  データグラムは、どの経路に当たっても `ENETUNREACH` のままです。Linux では `lo` へ
  送り出されて捨てられるか、拒む経路のエラーになります。
  アドレスはいつも永続です。寿命（`IFA_CACHEINFO`）と `IFA_RT_PRIORITY` は保たず、
  相手のアドレスはポイントツーポイントのものにならず、IPv6 のアドレスが仮（tentative）に
  なることもありません。Linux のものは、ループバックならすぐ終わる重複アドレス検出の
  処理が動くまで仮です。`lo` が落ちている間のそのアドレスへの接続とデータグラムは
  `ENETUNREACH` です。Linux では送り出されて捨てられます。`lo` のアドレスでない、
  接頭辞の中の IPv6 のアドレスへのものも `ENETUNREACH` です。Linux では接頭辞の経路が
  そこへ送って捨てます。`lo` が落ちている間の IPv6 の経路の引き当ても
  `ENETUNREACH` です。経路の引き当ては宛先のほかの条件（`RTA_SRC`、`RTA_OIF`、`RTA_MARK`
  など）を見ず、その `rta_cacheinfo` は参照を 1 つと数えます。Linux はキャッシュされた
  経路を使うほかのものも数えます。通知はリンクとその IPv6 の情報、アドレス、経路のもの
  だけで、近隣、netconf などのグループには送らず、ほかの名前空間のソケットにも
  送りません（`NETLINK_LISTEN_ALL_NSID` はありません）。`lo` を落としたときに消える、
  `lo` を通る IPv4 の経路は、Linux と同じく何も伝えません。
  `NETLINK_PKTINFO`、`NETLINK_NO_ENOBUFS` など、機能のページに挙げていないオプションは
  `ENOPROTOOPT` です。リンクのメッセージの統計は 0 です。その `IFLA_AF_SPEC` は、
  `CONFIG_MCTP` を組み込んだ Ubuntu のカーネルと同じく MCTP の設定を載せます。
  組み込んでいないカーネルは載せず、`AF_MCTP` のアドレスと経路のダンプを扱う処理も
  ないので、それらのダンプには IPv4 と IPv6 のアドレスと経路を返し、MCTP のアドレスも
  経路も取りません。`AF_MCTP` のソケットはないので（`EAFNOSUPPORT`）、MCTP の
  アドレスと経路は何も運びません。
  IPv4 と IPv6 の設定は、sysctl が組み込みのままのカーネルのものです。Linux の新しい
  名前空間はホストのものを写します。IPv6 の作成時刻は 0、到達可能時間は 30 秒です。
  Linux では乱数で決まります。アドレスの作成時刻は 0 です。`NETLINK_EXT_ACK` は
  エラーにもダンプの `NLMSG_DONE` にも属性を足しません。リンクのダンプの
  `IFLA_LINKINFO` は受け取るだけで何もしません。Linux はモジュールが知る種類の
  デバイスだけを見せます。リンクのポリシーが取る `IFLA_GSO_MAX_SIZE` と
  `IFLA_GSO_IPV4_MAX_SIZE` の最小値は、Ubuntu のカーネルと同じく 321
  （`MAX_TCP_HEADER` + 1）です。ほかのビルドでは違うことがあります。
  `rtnetlink` の知る最後より後の型のメッセージには
  `NLMSG_ERROR` で `EOPNOTSUPP` を返します。Linux 7.0 では送信そのものが
  `EOPNOTSUPP` になります。受信バッファがいっぱいのソケットへの答えは、待たずに
  `ENOBUFS` で捨てます。netlink のソケットへの `write` は、ソケットを開いたスレッドの
  ケーパビリティだけで動きます。ほかの名前空間は、paludarium に分けるものが
  ありません（IPC 名前空間の System V の共有メモリ・セマフォー・メッセージキューと
  POSIX メッセージキューを除きます）。マウント名前空間には `mount` がありません
  （`/proc/self/mountinfo` のマウント ID は変わりません。Linux では新しい名前空間の
  写しに新しい ID が付きます）。cgroup 名前空間には
  `/proc/self/cgroup` がなく、time 名前空間には `/proc/<pid>/timens_offsets` がなく、
  時計は最初の名前空間のものです。PID 名前空間はそれぞれの番号を 1 度だけ配ります。
  Linux では `pid_max` で一回りして使い回します。同じ理由で、`clone3` の `set_tid` は、
  最初の名前空間でタスクが一度持った ID を、空いた後でも取れません（`EEXIST`）。Linux では
  また取れます。その番号は、ホストのものによらず、Linux の `pid_max` の最大の 4194304
  より小さい値です。受け手の名前空間の外から積んだシグナル（`rt_sigqueueinfo`）は、`si_code`
  によらず `si_pid` を 0 にします。名前空間のファイルは `NS_GET_*` の `ioctl` を持たず、
  新しい名前空間の番号は、空いた番号を使い回す Linux のものとは違います。
- **Linux と macOS 以外のホストでマウントしたディレクトリのファイル**：`SEEK_DATA`
  や `SEEK_HOLE` の `lseek` はファイル全体をデータとして扱います。Linux では穴を
  見つけます。Windows では `st_blocks` も大きさを 512 バイトのブロックに切り上げた
  値で、Linux ではホストのファイルシステムが確保した分を数えます。ほかの Unix の
  ホストは自分の値を返します。Linux と macOS のホストでは、どちらもホストから得ます。
  `FIOQSIZE` はどのホストでも `st_blocks` をバイトにした値です。Linux ではファイルシステムが
  その時点で確保した分で、遅延割り当ての ext4 や overlayfs では `st_blocks` より遅れて
  数えます。
- **ブロックの大きさ**：`st_blksize`、`stx_blksize`、`FIGETBSZ` は、Linux と同じく
  `/proc` と端末（疑似端末のスレーブも）では 1024 です（[システムコール](./features#system-calls)）。
  ほかのファイルはどれも 4096 です。Linux では、マウントしたディレクトリは
  ホストのファイルシステムのもの（たいていは 4096）です。マウントしたディレクトリの
  `statfs` は、ここでもホストの値を返します。ホストの端末は疑似端末（devpts）と
  みなします。Linux のコンソール（`/dev/tty1`、devtmpfs）は 4096 です。ブロックの
  大きさのないファイルシステム（多くのコンテナの overlayfs など）では、Linux の
  `FIGETBSZ` は `EINVAL` です。
- **Windows の標準入力**：Windows のホストは入力が届いているかを見分けられないので、
  `poll`・`select`・`epoll` はホストの標準入力をいつも読めると見ます。`O_NONBLOCK` を
  付けた読み込みも、`EAGAIN` にならずに入力を待ち、読み込みの待ちはホストで待つので、
  シグナルでも終わりません（`EINTR` になりません）。Linux と macOS の
  ホストと WebAssembly では、入力があるときか終わったときだけ読めます。
- **ノンブロッキングの標準出力**：`O_NONBLOCK` を付けた標準出力や標準エラーへの書き込みが
  `EAGAIN` になるのは、ホストにまったく空きがないときだけです。少しでも空きがあれば、残りを
  ホストで待って全部を書きます。Linux は入る分だけを書いて、その数を返します。途中で
  止めるにはホストのディスクリプタ自身の `O_NONBLOCK` が要りますが、そのフラグはホストの
  ほかのプロセスと共有しています。Windows のホストは見分けられないので、`EAGAIN` には
  なりません。
- **疑似端末の一部**（[機能](./features#system-calls)）：片側の書き込みは、
  すぐにもう片側の行規則に届きます。Linux はワークキューから渡すので、ここでは
  書き込みの一部だけが読めることはありません。`O_ASYNC` も書き込み（やエコー）の
  たびに 1 回送りますが、Linux はワークキューが渡すひとかたまりごとに送り、その数は
  積まれる `F_SETSIG` のシグナルに表れます。それぞれの側は Linux の既定の
  フリップバッファと同じ 640 KiB まで持ちますが、その裏の Linux のメモリの勘定は
  ありません。`/dev/console` がないので、`TIOCCONS` の行き先に書かれることは
  ありません。制御端末がホストのものなら、`vhangup` は何もしません。Linux なら
  それを切断します。ホスト自身の端末はこの疑似端末ではありません。そこにつながるゲストの
  標準入出力は `TCGETS` と `TIOCGWINSZ` にだけ答えます。
- **ホストの標準入出力への `FIONREAD` と `SIOCOUTQ`**：どちらも `ENOTTY` を返します。
  Linux では、その先にあるものについて答えます。`FIONREAD` はパイプ、端末、ソケット、
  通常のファイルについて、`SIOCOUTQ` は端末とソケットについてです。ゲスト自身のパイプ、
  ソケット、通常のファイルは Linux と同じに数えます。
- **コアファイル**：コアは、カーネルの既定の `core_pattern`（作業ディレクトリの
  `core`）と同じように書きます。コアをクラッシュの処理系（systemd-coredump、apport）
  に渡すホストの設定は再現しません。コアの `NT_FILE` ノートは、マップしたファイルを
  マップしたときのパスで、プログラムを起動したときのパスで示します。Linux は名前の
  変更を追い、シンボリックリンクを解決します。
- **メモリの上限**：上限を超える書き込みをしたプロセスが終わります。Linux の
  OOM killer は、いちばんメモリを使っているプロセスを選びます。
- **ネイティブの JIT**：試験的な機能で、`--jit` を付けたときだけ使います。使えるのは
  x86-64 の Linux のホストだけで、それ以外のネイティブ版はインタプリタで動きます。
  コンパイルするのは、ブロックの先頭から続く、単純な形を持つ命令だけです
  （[アーキテクチャ](../design/architecture#the-native-jit)）。
- **stable の Rust**：nightly の Rust が必要です。

## 確かめていないこと

- 確かめたのは、[対応している機能](./features) に挙げたプログラムと、命令ごとのテストです。
  ほかのプログラムが完全に同じように動くことは、まだ保証していません。
- ファジングは、決まった時間の中で問題が見つからなかったことを示すもので、どんな入力でも
  安全だという証明ではありません。
- 差分テストの基準を取った CPU は、記録してある一部の AMD と Intel の CPU です。
  まだ観測していない CPU のプロファイルでは、テストがわざと止まるようにしてあります。
- メモリ、タスク（スレッドとプロセス）、開けるファイルの数は、埋め込む側が上限を
  指定しない限り無制限です。上限がなければ、信頼できないプログラムはホストのメモリを
  使い切るおそれがあります。メモリの上限が数えるのはゲストのページで、ファイルの
  中身、パイプやソケットのバッファ、エミュレーター自身のメモリは数えません（[コマンドライン](./cli)、[Rust](./rust)、
  [JavaScript](./javascript)）。
- Safari の自動テストは、ブラウザの起動を待つ間に時間切れになることがありました。
  対策を入れて、10 回続けて成功していますが、今後揺れないことの保証ではありません。

## 不具合を見つけたら

CPU のフォールトでゲストが終わったときは、シグナル、アドレス、命令のバイト列が
表示されます。`--report-enosys` を付けて動かし直すと、`ENOSYS` を返したシステムコールも
わかります（[コマンドライン](./cli#足りないものを探す)）。それらを添えて、
[Issue](https://github.com/aletheia-works/paludarium/issues) で知らせてください。
